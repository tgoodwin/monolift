# Usefulness Scenarios v1 - gpt-5.4 run

## Framing anchor from the PLOS '25 paper

The paper's utility claim is narrower than "microservices are good." Monolift is useful when it gives the operator a low-commitment, reversible way to change placement in response to workload conditions, while preserving the source program's structure and API. The paper's strongest claims are incremental adoption, rapid exploration of alternative placements, and dynamic switching between local and remote execution when workload shape changes.

This run therefore treats an archetype as useful when lifting creates one of three concrete advantages the paper cares about:

- a better placement lever for work that already has a natural queue, cadence, shard key, or owner boundary
- a cleaner failure domain than the current monolithic placement
- a meaningful "keep it local when quiet, move it out when stressed" story

This run adds one cost lens that is only implicit in the paper: operator attention. If a lift mostly creates a new service to manage without creating a new placement or isolation lever, it is low-payoff even if it is technically liftable.

## Cross-cutting findings

- Ease of auto-lift does not line up cleanly with usefulness. `periodic-invocation` and `bounded-worker-pool` are both easy and useful, but `serialized-actor`, `ttl-cache`, and `keyed-partitioned-state` show many liftable regions whose payoff is much more conditional.
- The paper's dynamic-placement story is strongest for `bounded-worker-pool`, `periodic-invocation`, and some `session-affinity-state` regions. These archetypes naturally support "keep local until demand or contention says otherwise."
- Several archetypes are better thought of as isolation tools than scaling tools. `serialized-actor` and `fanout-publisher` often pay off because they shrink blast radius or clarify ownership, not because they increase parallelism.
- Thin wrappers over already-externalized state are often low-payoff. Gitea's session providers and some cache wrappers are examples: the compiler may be able to lift them, but the user may gain little because the durable substrate already exists.
- Caddy remains the important negative control. The reverse-proxy hot path proves that utility includes declining to distribute protocol-critical coordination even when channels, mutexes, or maps are present (`evaluation/caddy/modules/caddyhttp/reverseproxy/reverseproxy.go:50-51`, package-global `inFlightRequests`; `reverseproxy.go:102`, `Handler`).

## Alignment and mild departure from the paper

This run is aligned with the paper's main utility thesis: Monolift helps when placement should follow workload character rather than the application's package tree. The only mild extension is that this run treats operator burden as a first-class cost in usefulness ranking. That does not contradict the paper; it sharpens the paper's "pay-as-you-go" claim by asking whether the new lift creates enough leverage to justify a new service boundary.
