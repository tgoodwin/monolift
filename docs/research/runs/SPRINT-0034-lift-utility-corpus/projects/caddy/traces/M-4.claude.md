## Activation path for caddy/M-4

### Entrypoint

`cmd/caddy/main.go:40` — `func main()` is the binary entrypoint. It does nothing but delegate to `caddycmd.Main()`. Before `main` runs, Go's package init order causes the blank import `_ "github.com/caddyserver/caddy/v2/modules/standard"` (line 37) to transitively import `modules/caddytls`, which fires `caddytls.init()` and registers `InternalIssuer` in the module registry.

### Step 1: main delegates into the command package

- **From:** `cmd/caddy/main.go:41` — body of `main`.
- **To:** `cmd/main.go:66` — `caddycmd.Main()`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Trivially resolvable. Both names are package-qualified and unambiguous; no type analysis required.

### Step 2: cobra command tree is built and dispatched

- **From:** `cmd/main.go:72` — `defaultFactory.Build().Execute()`.
- **To:** `cmd/commandfactory.go:22` — `(*rootCommandFactory).Build` runs the constructor (`cobra.go:11`) plus every option appended via `defaultFactory.Use(...)`, including the closure registered for the "run" subcommand at `cmd/commands.go:597-599` (added by `RegisterCommand` during `init()`).
- **Edge type:** `init-function` (the registry of subcommands is populated by package-level `init()` calls in `commands.go:121` etc.) plus `closure-stored-in-slice` (each option is a `func(*cobra.Command)` appended to `factory.options`).
- **Resolution notes:** A static analyzer must (a) honor Go's `init` ordering to know `commands.go init` ran, (b) follow each `defaultFactory.Use(fn)` call to observe what gets stored in `f.options`, and (c) realize `Build` calls every stored function. CHA/RTA can do this — the slice is package-private and only mutated through `Use`.

### Step 3: cobra.Execute selects the "run" subcommand and calls its RunE field

- **From:** External `cobra.Command.Execute` (in `github.com/spf13/cobra`) — invokes `cmd.RunE` of whichever subcommand argv selects.
- **To:** the function value bound at `cmd/commands.go:166` — `cmd.RunE = WrapCommandFuncForCobra(cmdRun)`.
- **Edge type:** `function-value-in-struct-field`
- **Resolution notes:** `RunE` is a `func(*cobra.Command, []string) error` field on `cobra.Command`. The compiler must (a) see every assignment of the form `someCmd.RunE = …` in the program, (b) treat each assigned function value as a possible callee at any cobra-internal `RunE(...)` invocation. The dispatch keying (argv → subcommand) is data-dependent, so a sound analysis conservatively unions all RunE assignments. The actual call site is in external code, but cobra is a regular Go dependency and is in the linked binary.

### Step 10: certmagic dispatches to Issuer.Issue

- **From:** Inside `certmagic` (external): `(*Config).ManageAsync` → `manageOne` → `getRenewalInfo`/`obtainCert` → `Issuer.Issue(ctx, csr)`.
- **To:** `modules/caddytls/internalissuer.go:103` — `func (iss InternalIssuer) Issue(ctx context.Context, csr *x509.CertificateRequest)`.
- **Edge type:** `interface-method-dispatch`
- **Resolution notes:** The actual indirect call is `Issuer.Issue(...)` over the interface `certmagic.Issuer` (declared in the certmagic module). The set of concrete `Issuer` values reaching this site flows from `certmagic.Config.Issuers`, which `caddytls` populates in two places:
  - **Explicitly-configured issuers:** `modules/caddytls/automation.go:233` — `ap.Issuers = append(ap.Issuers, issVal.(certmagic.Issuer))`, where `issVal` came out of `tlsApp.ctx.LoadModule(ap, "IssuersRaw")` at line 228. `LoadModule` ends in `LoadModuleByID` (`context.go:364`), which uses a **string ID** from the JSON config to index a registry built by `caddy.RegisterModule` calls (themselves invoked from package-level `init()`, e.g. `internalissuer.go:33-35`).
  - **Default fallback:** `modules/caddytls/automation.go:480` constructs `[]certmagic.Issuer{new(ACMEIssuer)}`; the default-with-internal-fallback code at `modules/caddyhttp/autohttps.go:740` constructs `[]certmagic.Issuer{internalIssuer}`.
  These flow into `ap.makeCertMagicConfig(...issuers...)` (`automation.go:251`) and from there into `certmagic.New(certCache, cfg)` (line 256).

  A whole-program analyzer can resolve this if it (a) seeds the registry from every `caddy.RegisterModule` call, (b) treats `LoadModuleByID` as potentially returning any registered `certmagic.Issuer` implementer (`*caddytls.ACMEIssuer`, `*caddytls.InternalIssuer`, `*caddytls.ZeroSSLIssuer`), and (c) propagates that conservative type set through `ap.Issuers` into `certmagic.Config.Issuers`. Without modeling the registry, the path is dynamic at this hop.

### Summary

- **Path length:** 10 steps (compressing the three-call chain in step 6 as one). The unique resolution challenges are: cobra's `RunE` plumbing (steps 2-4), the `caddy.App` interface dispatch on `Start` (step 7), the boundary into external `certmagic` (step 9), and the `certmagic.Issuer` dispatch back to `InternalIssuer.Issue` (step 10).
- **Edge types encountered:** `direct-function-call`, `init-function`, `closure-stored-in-slice`, `function-value-in-struct-field`, `closure-capture`, `interface-method-dispatch`, `method-call-on-concrete-type`, plus a `registry-lookup-by-string-id` mechanism (Caddy's `RegisterModule` + `LoadModuleByID`) that gates which concrete `certmagic.Issuer`s flow into the dispatch site.
- **Hardest edge:** **Step 10** — the call from external `certmagic` code into `InternalIssuer.Issue` via the `certmagic.Issuer` interface. It is hard for two compounding reasons: (a) the call site lives outside the evaluated tree (in the certmagic dependency), and (b) the set of concrete issuers reaching that site is determined by Caddy's plugin registry, populated by `init()`-time `caddy.RegisterModule` calls and resolved through a JSON-configured string ID at `LoadModuleByID` (`context.go:364-376`). A sound static analyzer can collapse this to a finite type set, but only if it explicitly models the module registry as a side-effecting init step.
- **Static-analysis feasibility:** Feasible end-to-end with a whole-program callgraph that (i) treats Go `init()` as effectful (so `caddy.RegisterModule` populates a known registry), (ii) treats `LoadModuleByID(id, …)` as a dispatch over the registered set rather than reflection, and (iii) is willing to descend into the external `certmagic` module (which is in the linked binary). No `reflect.Call`, no plugin .so loading, no runtime function-pointer construction is required on the path. The `reflect` use in `LoadModuleByID` is only for shape-checking the value returned by `modInfo.New`, not for the dispatch itself, so it does not break sound CHA/RTA. The minor non-static element is JSON-driven module-ID selection, which is data-dependent but bounded.
- **Alternative paths:** `InternalIssuer` is also reachable through the auto-HTTPS path (`modules/caddyhttp/autohttps.go:740` — `newPolicy.Issuers = []certmagic.Issuer{internalIssuer}`), which produces a longer prefix (`HTTP app → autoHTTPS → AutomationPolicy.Provision → certmagic.Config`) but the tail (steps 9-10) is identical. The trace above through the TLS app is shorter.
