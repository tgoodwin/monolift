### Entrypoint

`cmd/caddy/main.go:40` — `func main()` is the binary entrypoint of the Caddy server. It does nothing but delegate to `caddycmd.Main()`, which drives a cobra CLI. The `run` subcommand is what actually loads config and starts the HTTP server.

### Summary

- **Path length:** 9 steps.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field`, `interface-method-dispatch`, `struct-literal-field-assignment`, `goroutine-launch`, `method-call-on-concrete-type`, `closure-capture`.
- **Hardest edge:** Step 8 (`routes.go:337` → `templates.go:410`). The concrete `MiddlewareHandler` is chosen at provisioning time by a string-keyed registry lookup whose key is read from user JSON. A static analyzer must (a) enumerate the universe of `caddy.RegisterModule(X{})` calls reachable from the binary's import graph, (b) filter to those whose `CaddyModule().ID` falls under `http.handlers.*` and whose type satisfies `caddyhttp.MiddlewareHandler`, and (c) treat any of them as a possible callee at this dispatch site. The fan-out is real but bounded; the wrapping closure (`wrapMiddleware`) and the stored `Route.Handlers` slice add an extra layer of escape-tracking on top.
- **Static-analysis feasibility:** Resolvable in principle. Every edge is either fully static or an interface dispatch whose receiver universe is bounded by the set of types passed through `caddy.RegisterModule` in linked-in `init()` functions (no reflection on arbitrary types, no `plugin.Open`, no runtime-supplied function pointers from outside the binary). The price is precision: a sound call graph at Steps 4 and 8 will over-approximate to all registered `caddy.App` / `MiddlewareHandler` implementations respectively. Alternative paths to the same region root exist via the error-handler chain (`modules/caddyhttp/server.go:422` `s.errorHandlerChain.ServeHTTP`) and via subroute handlers (`modules/caddyhttp/subroute.go`), but both are longer and converge on the same `wrapMiddleware → MiddlewareHandler.ServeHTTP` dispatch.
