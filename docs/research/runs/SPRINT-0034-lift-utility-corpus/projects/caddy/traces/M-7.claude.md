## Activation path for caddy/M-7

### Entrypoint

`cmd/caddy/main.go:40` — `func main()`. The binary's only job is to call into the shared `caddycmd.Main` entry; the blank-imported `modules/standard` package side-effect-loads every default module (including the `fileserver` package whose `init()` self-registers `FileServer`).

### Step 1: main delegates to the shared CLI entry

- **From:** `cmd/caddy/main.go:41` — `caddycmd.Main()`
- **To:** `cmd/main.go:66` — `func Main()`
- **Edge type:** `direct-function-call`
- **Resolution notes:** Trivially resolvable: a fully-qualified package call with no receiver. The compiler already binds this at link time.

### Step 2: CLI entry dispatches to a Cobra subcommand

- **From:** `cmd/main.go:72` — `defaultFactory.Build().Execute()`
- **To:** `cmd/commandfuncs.go:172` — `func cmdRun(fl Flags)`
- **Edge type:** `function-value-in-struct-field` (registered as `cmd.RunE = WrapCommandFuncForCobra(cmdRun)` at `cmd/commands.go:166`)
- **Resolution notes:** The `run` subcommand stores `cmdRun` as a `func` value inside a `*cobra.Command.RunE` field at package init. To resolve this edge a static analyzer must (a) track Cobra's command tree to know the `run` subcommand exists, and (b) find the assignment `cmd.RunE = WrapCommandFuncForCobra(cmdRun)` to know which function value lives in that field. Selection of *which* subcommand fires depends on `os.Args`, but the universe of possible callees is statically the closed set of `cmd*` functions referenced from `commands.go`.

### Step 3: cmdRun loads the config and starts the runtime

- **From:** `cmd/commandfuncs.go:267` — `caddy.Load(config, true)`
- **To:** `caddy.go:115` — `func Load(cfgJSON []byte, forceReload bool) error`, which forwards to `unsyncedDecodeAndRun` → `caddy.go:419` `func run(newCfg *Config, start bool)`
- **Edge type:** `direct-function-call`
- **Resolution notes:** Plain cross-package call; statically trivial.

### Step 4: run starts each provisioned App

- **From:** `caddy.go:454` — `err := a.Start()` inside `for name, a := range ctx.cfg.apps`
- **To:** `modules/caddyhttp/app.go:475` — `func (app *App) Start() error` (the HTTP app)
- **Edge type:** `interface-method-dispatch` (call through the `caddy.App` interface)
- **Resolution notes:** `ctx.cfg.apps` is `map[string]App`. The HTTP app implementation is selected at config-load time by `ctx.LoadModule` keyed on the JSON id `"http"` (see `LoadModuleByID` at `context.go:364`, which calls `modInfo.New()` — a function value stored in a global `modules` registry). A purely static call-graph analysis must over-approximate `a.Start()` to all implementers of `caddy.App` in the build; type-flow analysis pinned by the registered id `"http"` (set in `caddyhttp.App.CaddyModule()`) narrows it to `*caddyhttp.App`.

### Step 5: HTTP app installs the caddy Server as the net/http handler

- **From:** `modules/caddyhttp/app.go:489` — `&http.Server{ … Handler: srv, … }`
- **To:** `modules/caddyhttp/server.go:310` — `func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request)`
- **Edge type:** `struct-literal-field-assignment` (storing an interface value into `http.Server.Handler`); the actual call later is `interface-method-dispatch` from `net/http`'s server loop into `Handler.ServeHTTP`.
- **Resolution notes:** Two static facts compose: (a) `*caddyhttp.Server` satisfies `http.Handler` (one `ServeHTTP(http.ResponseWriter, *http.Request)` method), and (b) it is stored into `http.Server.Handler` here. `net/http` then invokes `c.server.Handler.ServeHTTP(rw, req)` deep in stdlib's `(*conn).serve`. A whole-program analyzer needs cross-binary tracking through stdlib to bridge this, but the receiver type is statically determined by this assignment.

### Step 6: Server.ServeHTTP enters the compiled middleware chain

- **From:** `modules/caddyhttp/server.go:497` — `return s.primaryHandlerChain.ServeHTTP(w, r)` (called from `serveHTTP` at `server.go:471`, itself reached from `Server.ServeHTTP` at `server.go:389`)
- **To:** `modules/caddyhttp/routes.go:332` — the `HandlerFunc` closure returned by `wrapMiddleware`
- **Edge type:** `interface-method-dispatch` (via `caddyhttp.Handler`); the concrete value is a `HandlerFunc` produced by `wrapMiddleware`/`wrapRoute` and stored in the `Server.primaryHandlerChain` field at provision time (`app.go:381`: `srv.primaryHandlerChain = srv.wrapPrimaryRoute(primaryRoute)`).
- **Resolution notes:** `primaryHandlerChain` is an unexported field of type `Handler` (`server.go:273`). The values flowing into it come from `RouteList.Compile` (`routes.go:238`) which composes `wrapRoute` closures — each of which eventually calls a `wrapMiddleware` closure. Function-value flow analysis through a struct field plus closure tracking is required.

### Step 7: middleware closure dispatches to the route's handler

- **From:** `modules/caddyhttp/routes.go:337` — `return mh.ServeHTTP(w, r, next)` inside the closure returned by `wrapMiddleware`
- **To:** `modules/caddyhttp/fileserver/staticfiles.go:268` — `func (fsrv *FileServer) ServeHTTP(w http.ResponseWriter, r *http.Request, next caddyhttp.Handler) error`
- **Edge type:** `interface-method-dispatch` (call through `caddyhttp.MiddlewareHandler`); `mh` was captured by `closure-capture` from the loop at `routes.go:181` (`r.middleware = append(r.middleware, wrapMiddleware(ctx, midhandler))`), where `midhandler` came from `r.Handlers` populated at `routes.go:164–165` by a type assertion on the result of `ctx.LoadModule(r, "HandlersRaw")`.
- **Resolution notes:** **This is the dynamic boundary.** `ctx.LoadModule` (`context.go:188`) uses `reflect` plus a string-keyed `modules` registry to instantiate the handler. The string id `"http.handlers.file_server"` lives in the JSON config — not in the source. To bind `mh` to `*FileServer` statically, an analyzer must either (a) over-approximate to *every* `MiddlewareHandler` implementer in the build (the `init()` registrations in `modules/standard` form the closed candidate set), or (b) parse the config alongside the binary. The `init`-time registration in `modules/caddyhttp/fileserver/staticfiles.go:42` (`caddy.RegisterModule(FileServer{})`) plus the closed-namespace constraint (`caddy:"namespace=http.handlers inline_key=handler"` tag at `routes.go:91`) lets a class-hierarchy analysis prove `*FileServer` is one of the legal targets.

### Summary

- **Path length:** 9 steps from `main()` to the region root.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field` (Cobra `RunE`), `interface-method-dispatch` (×3: `caddy.App`, `http.Handler`, `caddyhttp.Handler`/`MiddlewareHandler`), `struct-literal-field-assignment` (handler-into-`http.Server`), `closure-capture` (middleware chain build), `method-call-on-concrete-type` (×2 inside `fileserver`). An auxiliary `init-function` edge (`fileserver.init` → `caddy.RegisterModule`) is what makes Step 7's resolution feasible at all.
- **Hardest edge:** Step 7 — the `mh.ServeHTTP` interface call inside `wrapMiddleware`'s closure. The receiver is materialized via reflection from a string id supplied by the config (`ctx.LoadModule` → `LoadModuleByID` → `modInfo.New()`). Static resolution requires either (a) class-hierarchy over-approximation across all registered `MiddlewareHandler` implementations enumerated by the side-effect imports in `modules/standard`, or (b) reading the config to pin the id `"http.handlers.file_server"`. Step 4 (`a.Start()`) has the same shape but with a smaller candidate set (`caddy.App` implementers).
- **Static-analysis feasibility:** Reachable, but only with both type-flow analysis through unexported struct fields (`Server.primaryHandlerChain`, `Route.middleware`, `Route.Handlers`) and a model of Caddy's reflective module registry. A pure call-graph algorithm without registry/config awareness will lose precision at Steps 4 and 7 (interface dispatch over reflection-instantiated values), but will still place `*FileServer` among the candidate targets because `staticfiles.go:42`'s `init` registration is observable in source. There is no truly unresolvable dynamic gap (no `reflect.Call`, no plugin loading from `.so`, no runtime-supplied function pointers); the only "soft" dynamic input is the JSON config string that picks `*FileServer` out of the registered set.
