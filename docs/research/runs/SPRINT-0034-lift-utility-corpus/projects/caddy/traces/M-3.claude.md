## Activation path for caddy/M-3

### Entrypoint

`cmd/caddy/main.go:40` — `main()` invokes `caddycmd.Main()`, which builds and executes the Caddy CLI; the `caddy run` subcommand boots the HTTP app and from there each inbound request drives the activation chain. The `_ "github.com/caddyserver/caddy/v2/modules/standard"` blank import (line 37) is what causes `caddyauth`'s `init()` (basicauth.go:32) to fire and register `HTTPBasicAuth` in the module registry — the registry is what lets the Authentication middleware's interface field eventually resolve to the region's owning type.

### Step 1: `main` calls into the CLI library

- **From:** `cmd/caddy/main.go:41` — the only statement in `main()` is `caddycmd.Main()`.
- **To:** `cmd/main.go:66` — `caddycmd.Main()`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Fully resolved at compile time by the linker; no analysis needed beyond import resolution.

### Step 2: cobra CLI dispatches the `run` subcommand

- **From:** `cmd/main.go:72` — `defaultFactory.Build().Execute()` runs the cobra root command, which parses argv and invokes the matching subcommand's `RunE`.
- **To:** `cmd/commandfuncs.go:172` — `cmdRun(fl Flags)`.
- **Edge type:** `function-value-in-struct-field`
- **Resolution notes:** `cmd.RunE = WrapCommandFuncForCobra(cmdRun)` is set during command registration at `cmd/commands.go:166` (inside the `CobraFunc` callback for the `run` command). cobra holds `RunE` as a struct field of type `func(*cobra.Command, []string) error` and calls it indirectly. A static analyzer would have to track all sites that assign to `cobra.Command.RunE` (or to the `Command.CobraFunc` callbacks consumed by `RegisterCommand`) and treat them as the call-graph successors of `Execute()`. Multiple subcommands exist; the actual one chosen depends on argv, but the static set of successors is finite and fully enumerable.

### Step 3: `cmdRun` boots the configured apps

- **From:** `cmd/commandfuncs.go:172` — `cmdRun` parses flags, loads the JSON config, and ultimately drives `caddy.Load` → `changeConfig` → `unsyncedDecodeAndRun` → `run` → `app.Start()` for every started app. (Within this monolift trace these inner calls are routine direct-function-calls and method-call-on-concrete-type edges.)
- **To:** `modules/caddyhttp/app.go:475` — `func (app *App) Start() error`. Caddy's `App` interface implementations are registered modules; for the HTTP app, the concrete type is `*caddyhttp.App`.
- **Edge type:** `interface-method-dispatch` (across the `caddy.App` interface, with the concrete impls discoverable through `caddy.RegisterModule` call sites)
- **Resolution notes:** Whole-program type analysis can find every type that satisfies `caddy.App` by scanning `caddy.RegisterModule(<value>)` invocations; the JSON config selects which app(s) to instantiate at runtime, but the candidate set is statically bounded.

### Step 4: HTTP app registers its `Server` as `http.Handler` and launches a goroutine per listener

- **From:** `modules/caddyhttp/app.go:489` — `srv.server = &http.Server{ ..., Handler: srv, ... }` stores `*caddyhttp.Server` in the stdlib `http.Server.Handler` field. Then `modules/caddyhttp/app.go:629` — `go srv.server.Serve(ln)` hands the listener off to the stdlib accept loop.
- **To:** stdlib `net/http` server loop, which (per accepted connection) eventually invokes `srv.ServeHTTP(w, r)` via the `http.Handler` interface stored in `http.Server.Handler`.
- **Edge type:** `goroutine-launch` plus `interface-handler-registration` (a struct-field assignment of an `http.Handler` interface value, later dispatched by the stdlib).
- **Resolution notes:** This is the standard "library calls back into our `ServeHTTP` via a stored interface" pattern. Static analysis must (a) recognise the `Handler:` struct-literal assignment, (b) treat the goroutine entry as `(*http.Server).Serve`, and (c) follow the stdlib's known dispatch through `Handler.ServeHTTP`. With models of `net/http` (or by treating the assignment as the effective call edge), the successor `(*caddyhttp.Server).ServeHTTP` is reachable.

### Step 5: stdlib invokes the Caddy `Server.ServeHTTP`

- **From:** stdlib `net/http` (boundary; the call site is in the standard library, but the receiver type is statically known from Step 4).
- **To:** `modules/caddyhttp/server.go:310` — `func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request)`.
- **Edge type:** `interface-method-dispatch`
- **Resolution notes:** Same as Step 4's tail — once the analyzer pins `Handler` to `*caddyhttp.Server`, this edge is fully concrete.

### Step 6: `Server.ServeHTTP` calls its private `serveHTTP`

- **From:** `modules/caddyhttp/server.go:389` — `err := s.serveHTTP(w, r)`.
- **To:** `modules/caddyhttp/server.go:471` — `func (s *Server) serveHTTP(w http.ResponseWriter, r *http.Request) error`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** Receiver type is statically `*Server`; trivial.

### Step 7: `serveHTTP` enters the precompiled middleware chain

- **From:** `modules/caddyhttp/server.go:497` — `return s.primaryHandlerChain.ServeHTTP(w, r)`.
- **To:** the wrapped chain, ultimately reaching the closure created in `wrapMiddleware` at `modules/caddyhttp/routes.go:332`.
- **Edge type:** `interface-method-dispatch` (over the `caddyhttp.Handler` interface) with the concrete value being a `HandlerFunc` closure built up at provisioning time.
- **Resolution notes:** `primaryHandlerChain` is a struct field assigned at `modules/caddyhttp/app.go:381` from the result of `srv.Routes.Compile(emptyHandler)` (`routes.go:238`), which folds `wrapMiddleware`/`wrapRoute` closures around each configured middleware. Static analysis needs to (a) follow the field assignment, (b) understand that `RouteList.Compile` produces a chain whose innermost links call back into each middleware's `ServeHTTP`, and (c) treat `HandlerFunc` (an unnamed `func` adapter) as itself implementing `Handler`.

### Step 8: middleware closure dispatches to the captured `MiddlewareHandler`

- **From:** `modules/caddyhttp/routes.go:337` — `return mh.ServeHTTP(w, r, next)` inside the closure returned by `wrapMiddleware`.
- **To:** `modules/caddyhttp/caddyauth/caddyauth.go:78` — `func (a Authentication) ServeHTTP(w http.ResponseWriter, r *http.Request, next caddyhttp.Handler) error`.
- **Edge type:** `interface-method-dispatch` via `closure-capture` (the closure binds `mh MiddlewareHandler` from `wrapMiddleware`'s parameter, and `mh` is sourced from `route.Handlers[i]`, which is a `MiddlewareHandler` field populated from JSON config through `caddy.RegisterModule` registrations).
- **Resolution notes:** The set of possible concrete types for `mh` is exactly the set of types registered with `caddy.RegisterModule` whose `CaddyModule().ID` lives in the `http.handlers.*` namespace. `caddyauth.Authentication` registers itself as `http.handlers.authentication` at `caddyauth.go:28` (init) / `caddyauth.go:56-61` (`CaddyModule()`), so it is a candidate. A whole-program analyzer can enumerate this set; the runtime selection is config-driven but bounded.

### Step 9: `Authentication.ServeHTTP` dispatches to the configured provider

- **From:** `modules/caddyhttp/caddyauth/caddyauth.go:84` — `user, authed, err = prov.Authenticate(w, r)` inside the `for provName, prov := range a.Providers` loop.
- **To:** `modules/caddyhttp/caddyauth/basicauth.go:143` — `func (hba HTTPBasicAuth) Authenticate(w http.ResponseWriter, req *http.Request) (User, bool, error)`.
- **Edge type:** `interface-method-dispatch` (over the `caddyauth.Authenticator` interface, defined at `caddyauth.go:114`)
- **Resolution notes:** `a.Providers` is a `map[string]Authenticator` populated in `Authentication.Provision` (`caddyauth.go:65–76`) by calling `ctx.LoadModule(a, "ProvidersRaw")` and asserting each loaded module to `Authenticator`. The candidate set is the set of types registered under the `http.authentication.providers` namespace; `HTTPBasicAuth` is registered there at `basicauth.go:32` (init) and `basicauth.go:71-76` (`CaddyModule()` returns `ID: "http.authentication.providers.http_basic"`). Static analysis must rely on the registry → namespace → interface-conformance chain to pin candidate impls; dynamic input narrows but does not extend it.

### Step 10: `HTTPBasicAuth.Authenticate` calls the region root

- **From:** `modules/caddyhttp/caddyauth/basicauth.go:157` — `same, err := hba.correctPassword(account, []byte(plaintextPasswordStr))`.
- **To:** `modules/caddyhttp/caddyauth/basicauth.go:165` — `func (hba HTTPBasicAuth) correctPassword(account Account, plaintextPassword []byte) (bool, error)`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** Receiver type is statically `HTTPBasicAuth` (value receiver on a concrete struct). This is the easy edge — exactly the kind of call site monolift needs to instrument with the in-process / remote dispatch decision.

### Region root reached

`modules/caddyhttp/caddyauth/basicauth.go:165` — `(HTTPBasicAuth).correctPassword`

### Summary

- **Path length:** 10 steps (entrypoint → region root). Steps 4–5 form a single conceptual hop across the `net/http` boundary.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field` (cobra), `interface-method-dispatch` (×4 — `caddy.App`, `http.Handler` to Caddy `Server`, `caddyhttp.Handler` chain, `caddyhttp.MiddlewareHandler`, `caddyauth.Authenticator`), `goroutine-launch`, `interface-handler-registration` (struct-literal assignment of `Handler:` field), `closure-capture`, `method-call-on-concrete-type` (×2).
- **Hardest edge:** Step 8 (`wrapMiddleware` closure → `Authentication.ServeHTTP`). It compounds three difficulties at once: (a) the closure captures an interface-typed parameter, so the analyzer must follow data flow into the closure environment; (b) the captured value originates from `Route.Handlers`, a `[]MiddlewareHandler` field whose entries are loaded from JSON config via the `caddy.RegisterModule` registry (i.e. resolution depends on enumerating module registrations across the whole program); and (c) `primaryHandlerChain` itself is built by composing N such closures, so reaching this particular `mh` requires a context-sensitive walk across the chain. Step 9 is similar in shape but slightly simpler because the receiver dispatch happens directly on a map value.
- **Static-analysis feasibility:** Yes, with whole-program analysis. Every interface dispatch on the path (App, Handler, MiddlewareHandler, Authenticator) has a candidate set bounded by `caddy.RegisterModule` invocations plus standard interface-implements analysis; cobra's `RunE` field can be resolved by tracking command-registration call sites; the `net/http` boundary is a known framework idiom (`Handler:` field). There is no `reflect.Call`, no Go plugin loading, and no runtime-supplied function pointer on this path. The configuration-driven selection of which `Authenticator` instance is invoked at runtime narrows the candidate set rather than extending it, so a sound over-approximation that includes the entire registered set (or a config-aware refinement) suffices for monolift's instrumentation needs. Alternative path: only one path exists in the binary as built — `correctPassword` has a single in-edge from `Authenticate`, which has a single in-edge from `Authentication.ServeHTTP`; the `hash-password` CLI subcommand (`caddyauth/command.go:89`) does not call `correctPassword`.
