## Activation path for caddy/M-5

### Entrypoint

`cmd/caddy/main.go:40` — `main()` is the program entrypoint of the `caddy` binary; it does nothing but call `caddycmd.Main()`.

A secondary, statically-visible entrypoint is `modules/caddyhttp/encode/encode.go:37` — `init()` calls `caddy.RegisterModule(Encode{})`, which inserts a `ModuleInfo{ID: "http.handlers.encode", New: func() caddy.Module { return new(Encode) }}` into the global module registry. This `init` does not call `(*Encode).ServeHTTP`, but it is what makes the runtime resolution at Step 11 below possible — without it, no JSON config could ever materialize an `Encode` handler.

### Step 2: Main runs cobra and lands in the `run` subcommand handler

- **From:** `cmd/main.go:72` — `defaultFactory.Build().Execute()` runs cobra, which dispatches on the user-supplied subcommand name to the matching `*cobra.Command.RunE` closure.
- **To:** `cmd/commandfuncs.go:172` — `func cmdRun(fl Flags) (int, error)`
- **Edge type:** `function-value-in-struct-field` (with a string-keyed indirection through cobra)
- **Resolution notes:** At `cmd/commands.go:166`, `cmd.RunE = WrapCommandFuncForCobra(cmdRun)` stores a closure over `cmdRun` in the cobra command's `RunE` field; the command is registered under name `"run"` (`cmd/commands.go:122`). Cobra's `Execute()` matches `os.Args` to a registered command and invokes its `RunE`. A static analyzer needs to (a) know cobra's dispatch semantics — that `Execute` calls `RunE` of the matched subcommand — and (b) follow the closure capture of `cmdRun` through `WrapCommandFuncForCobra` (`cmd/cobra.go:149`). With those two pieces, the edge is statically resolvable: the universe of reachable `RunE` closures is enumerable from `RegisterCommand` call sites.

### Step 5: App.Start hands the *Server to net/http as its Handler and Serves in a goroutine

- **From:** `modules/caddyhttp/app.go:483-489` — `srv.server = &http.Server{ ..., Handler: srv, ... }` and `modules/caddyhttp/app.go:629` — `go srv.server.Serve(ln)`.
- **To:** `modules/caddyhttp/server.go:310` — `func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request)` (called by `net/http`'s server loop on each accepted connection).
- **Edge type:** `goroutine-launch` + `struct-literal-field-assignment` + `interface-method-dispatch` (through `http.Handler` inside `net/http`).
- **Resolution notes:** Two compounded resolutions are needed. (1) `Handler: srv` assigns a `*caddyhttp.Server` value into the `Handler http.Handler` field of `http.Server`; static type analysis can see that `*Server` implements `http.Handler` because it defines `ServeHTTP(http.ResponseWriter, *http.Request)`. (2) `net/http.(*Server).Serve` (external to this codebase) eventually calls `c.server.Handler.ServeHTTP(rw, req)` for each accepted connection. A static analyzer that models `net/http`'s contract — or treats it as a known framework — can resolve this back to `(*caddyhttp.Server).ServeHTTP`. The `go` keyword adds a thread-of-control fork, but the call graph reachability is unchanged.

To know that any element points to `*Encode`, the analyzer has to follow the slice all the way back to `Route.ProvisionHandlers` (`routes.go:159`), where `r.Handlers = append(r.Handlers, handler.(MiddlewareHandler))` and the `MiddlewareHandler` value comes from the JSON-driven module loader (next step's boundary).

### Step 10: wrapMiddleware closure dispatches to the configured MiddlewareHandler

- **From:** `modules/caddyhttp/routes.go:337` — `return mh.ServeHTTP(w, r, next)` inside the closure returned by `wrapMiddleware`.
- **To:** `modules/caddyhttp/encode/encode.go:154` — `func (enc *Encode) ServeHTTP(...) error`
- **Edge type:** `interface-method-dispatch` over `MiddlewareHandler` (`modules/caddyhttp/caddyhttp.go:90`); the bound dynamic type of `mh` is determined by `reflective-type-instantiation-from-config` performed in `caddy.Context.LoadModule`.
- **Resolution notes:** This is the load-bearing edge. `mh` has the static type `MiddlewareHandler`; its dynamic type is fixed at config-provision time via this chain: (a) `Encode`'s `init()` registers itself in the global module table with ID `"http.handlers.encode"` (`encode.go:37-39`, `encode.go:61-65`); (b) at provision time, the JSON config supplies a handler block tagged `"handler": "encode"` which `Route.ProvisionHandlers` (`routes.go:160`) feeds to `ctx.LoadModule(r, "HandlersRaw")`; (c) `LoadModule` uses `reflect` to read the struct tag `caddy:"namespace=http.handlers inline_key=handler"`, looks up `"http.handlers.encode"` in the module registry, calls the registered `New` function (`encode.go:64`) to mint a `*Encode`, and unmarshals JSON into it; (d) the `Module` interface value is then type-asserted to `MiddlewareHandler` (`routes.go:165`) and stored in the `Handlers` slice. The set of dynamic types `mh` can take is bounded by `init`-time module registrations of types that satisfy `MiddlewareHandler` — a static analyzer can enumerate that set, but cannot tell *which* of them is actually used without modelling the JSON config string. From a pure-Go static-analysis perspective, the call site `mh.ServeHTTP(...)` can be conservatively resolved to the disjunction of all registered `MiddlewareHandler` implementations.

### Summary

- **Path length:** 10 steps from `main()` to `(*Encode).ServeHTTP`.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field` (cobra `RunE`), `interface-method-dispatch` (App, http.Handler, caddyhttp.Handler, MiddlewareHandler), `goroutine-launch`, `struct-literal-field-assignment` (the http.Server's `Handler: srv`), `method-call-on-concrete-type`, `closure-capture` (twice — `wrapPrimaryRoute`/`enforcementHandler` and `wrapRoute`/`wrapMiddleware`), and `reflective-type-instantiation-from-config` underpinning the final `MiddlewareHandler` dispatch. The companion `init-function` registration at `encode.go:37` is what populates the resolvable set for the last edge.
- **Hardest edge:** Step 10 — the `mh.ServeHTTP(...)` call at `routes.go:337`. The dynamic type of `mh` is selected at runtime by reading a JSON string against a registry populated by `init()` functions, then materialized by `reflect`. A static analyzer can over-approximate `mh` to "any registered `MiddlewareHandler`" but cannot prove the exact binding without parsing/specializing on a specific config file. Cobra's `Execute` indirection at Step 2 is a milder version of the same shape, but is bounded by a small in-binary set of registered commands.
- **Static-analysis feasibility:** Most of the path (Steps 1, 3, 4, 6–9) is statically resolvable with standard whole-program type analysis and closure-capture tracking, modulo a known model of `net/http`'s `Server.Serve → Handler.ServeHTTP` contract. The two indirections that resist pure static resolution are (i) the cobra `RunE` map and (ii) the JSON-driven module wiring at Step 10. For the compiler-instrumentation use case, a workable strategy is to instrument the *call site* at `routes.go:337` (which is fixed in the source tree) and gate the dispatch on the dynamic type of `mh` being `*Encode`, rather than trying to prove a single static path that ends at `Encode.ServeHTTP`. There are no truly unresolvable boundaries (no plugin loading via Go plugins, no `reflect.Call` of arbitrary methods); the reflection involved is bounded by the registered-modules table.

**Alternative paths considered:** Caddy ships a few subcommands (`caddy file-server`, `caddy reverse-proxy`) that synthesize their own configs and instantiate `*caddyhttp.Server` directly (e.g. `modules/caddyhttp/fileserver/command.go:171`, `modules/caddyhttp/reverseproxy/command.go:257`). These reach `App.Start` via the same `caddy.Run`/`Run` path as `cmdRun` does, so they share Steps 4–10 and only differ in Steps 2–3. The `caddy run` route via JSON config is the canonical and shortest path.
