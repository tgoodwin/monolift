### Summary

- **Path length:** 12 steps from `main()` to the region root.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field`, `method-value-as-callback`, `goroutine-launch + closure-capture-of-callback-parameter`, `indirect-call-through-parameter`.
- **Hardest edge:** Step 10 (`goroutine-launch + closure-capture-of-callback-parameter`) is the trickiest. It composes three things at once: a goroutine boundary, a closure capturing a function-typed parameter, and the need to flow a method-value argument across two function calls (`CreateRecurringTask` → `createTask`) before it is invoked. A naive callgraph builder that treats `func()` parameters as opaque will lose the edge here. Step 3 (cobra `RunE` dispatch) is a close second, but it is a single struct-field-function-value pattern that points-to analysis handles routinely.
- **Static-analysis feasibility:** The whole path is statically resolvable. Every "indirect" edge (cobra `RunE`, both method values, the goroutine's captured callback, and the `handler` parameter) has a single non-test producer in the production binary, so a points-to / flow-sensitive callgraph (e.g. `golang.org/x/tools/go/callgraph/vta`) can recover the path end-to-end with no dynamic gap.
- **Alternative paths considered:** A second route to `InitEmailBatching` exists at `server/channels/app/server.go:439-441`, where a config-change listener closure calls `s.EmailService.InitEmailBatching()`. That route is strictly longer (it also runs through `NewServer`, then adds a `callback-registration` edge on `platform.AddConfigListener` plus a closure invocation when the listener fires) and only triggers on subsequent config reloads, so the path through `email.NewService` → `InitEmailBatching` documented above is the minimal activation path.
