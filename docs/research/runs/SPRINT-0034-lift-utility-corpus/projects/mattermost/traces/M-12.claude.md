## Activation path for mattermost/M-12

### Entrypoint

`server/cmd/mattermost/main.go:19` — `main()` delegates to `commands.Run(os.Args[1:])`, which invokes the Cobra root command. The default root `RunE` (set via `init()` in `commands/server.go:36`) is `serverCmdF`, which boots the Mattermost server.

### Step 1: Cobra dispatches the default subcommand to `serverCmdF`

- **From:** `server/cmd/mattermost/main.go:20` — `commands.Run(os.Args[1:])` calls `RootCmd.Execute()` (`commands/root.go:17`).
- **To:** `server/cmd/mattermost/commands/server.go:39` — `serverCmdF(command, args)` runs because `RootCmd.RunE = serverCmdF` was assigned inside `init()` at `commands/server.go:36`.
- **Edge type:** `struct-field-function-value-set-at-init`
- **Resolution notes:** Cobra reads its `RunE` field at request-dispatch time. A static analyzer must recognize that `init()` writes a function value into `RootCmd.RunE` and that `Execute()` reads it back; it then resolves the call by tracking all writes to the field across the program. Equivalent to a function pointer dropped into a struct during package initialization.

### Step 2: `serverCmdF` boots the server via `runServer`

### Step 5: `InitPost` registers `createPost` as the `POST /api/v4/posts` HTTP handler

- **From:** `server/channels/api4/post.go:24` — `api.BaseRoutes.Posts.Handle("", api.APISessionRequired(createPost)).Methods(http.MethodPost)`.
- **To:** `server/channels/api4/post.go:96` — `createPost(c *Context, w http.ResponseWriter, r *http.Request)` is stored as the dispatchable handler for that route.
- **Edge type:** `http-handler-registration`
- **Resolution notes:** A static analyser must (a) walk every `Router.Handle(pattern, handler)` site reachable from an entrypoint, and (b) treat the handler argument as call-reachable from any future `ServeHTTP` invocation. The handler argument here is built by wrapping `createPost` (a top-level function value) in `APISessionRequired`, which stores it in a `web.Handler` struct — see Step 6.

### Step 6: `APISessionRequired` wraps `createPost` into a `web.Handler` whose `HandleFunc` field is later invoked

- **From:** `server/channels/api4/handlers.go:50` — `APISessionRequired` constructs `&web.Handler{... HandleFunc: h, ...}` (line 53), with `h == createPost`.
- **To:** `server/channels/web/handlers.go:355` — at request time, `Handler.ServeHTTP` invokes `h.HandleFunc(c, w, r)`, calling back into `createPost`.
- **Edge type:** `function-value-in-struct-field`
- **Resolution notes:** The function value is written to `web.Handler.HandleFunc` in a struct literal at `handlers.go:53` and read back in `ServeHTTP` at `handlers.go:355`. Static resolution requires field-sensitive analysis: enumerate every assignment to `web.Handler.HandleFunc` reachable from `main`, and treat the read site as a call to any of those targets. Combined with Step 5, this connects the gorilla/mux router invocation (driven by the live HTTP server inside `Server.Start`) back to `createPost`.

### Step 11: `SendNotifications` schedules the per-recipient send on a worker goroutine

- **From:** `server/channels/app/notification.go:437` — `a.Srv().Go(func() { if _, err := a.sendNotificationEmail(rctx, notification, profileMap[id], team, senderProfileImage); err != nil { ... } })`.
- **To:** the closure body that calls `a.sendNotificationEmail(...)` at `server/channels/app/notification.go:438`. `Server.Go` (`server.go:820`) forwards to `PlatformService.Go` (`platform/goroutines.go:10`), which contains the literal `go func() { f(); ... }()` (`platform/goroutines.go:13`).
- **Edge type:** `goroutine-launch-with-closure-capture`
- **Resolution notes:** This is the trickiest edge in the path. A static analyser must (a) treat the func-literal at `notification.go:437` as a callable value passed to `Server.Go`, (b) follow it through `PlatformService.Go`, and (c) recognise that the `go` statement on line 13 of `platform/goroutines.go` invokes the captured `f`. Closure capture also needs to track the bound variables (`a`, `rctx`, `notification`, `profileMap[id]`, `team`, `senderProfileImage`) so the analyser knows which receiver and arguments flow into `sendNotificationEmail`. The captured map index `profileMap[id]` is opaque at compile time but irrelevant for reachability — only the call edge matters for activation-path resolution.

### Summary

- **Path length:** 12 steps (entrypoint → region root).
- **Edge types encountered:** `struct-field-function-value-set-at-init`, `direct-function-call`, `method-call-on-concrete-type` (×6), `http-handler-registration`, `function-value-in-struct-field`, `goroutine-launch-with-closure-capture`.
- **Hardest edge:** Step 11 (`goroutine-launch-with-closure-capture` chained through `Server.Go` → `PlatformService.Go` → `go func(){ f() }()`). The compiler must connect the func-literal at the call site to the eventual `go f()` two indirections away, while preserving the closure's captured receiver and arguments. Step 6 (`function-value-in-struct-field`) is also non-trivial because the handler value flows through a struct literal in one package and is invoked from a method on that struct in another.
- **Static-analysis feasibility:** Fully resolvable in principle by a whole-program Go analyser with field-sensitive points-to, function-pointer/closure tracking, and HTTP-router awareness — there is no `reflect.Call`, plugin loading, or runtime-supplied function pointer between `main` and the region root. A short alternative path exists via the local-mode API (`api4/api.go:500` → `InitPostLocal` → `web.APILocal(createPost)` plus a parallel `web.Handler.ServeHTTP` dispatch); shape and edge-type set are identical, so picking either yields the same compiler obligations. There is no shorter path that bypasses HTTP — every non-test caller of `sendNotificationEmail` reaches it through `SendNotifications` inside the `CreatePost`/`UpdatePost` request flow.
