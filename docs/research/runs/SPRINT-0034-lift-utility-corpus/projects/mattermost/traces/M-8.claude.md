## Activation path for mattermost/M-8

### Entrypoint

`server/cmd/mattermost/main.go:19` — `main()` for the `mattermost` server binary. The function's only job is to forward the command-line args to the package-level cobra command runner: `commands.Run(os.Args[1:])`.

### Step 1: main hands args to the commands runner

- **From:** `server/cmd/mattermost/main.go:20` — `main()` calls `commands.Run(os.Args[1:])`.
- **To:** `server/cmd/mattermost/commands/root.go:15` — `func Run(args []string) error`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Imported package, exported package-level function, fully qualified call. Trivial static edge — name resolution + import graph is enough.

### Step 2: Run invokes the cobra command tree

- **From:** `server/cmd/mattermost/commands/root.go:17` — `Run` calls `RootCmd.Execute()` after `RootCmd.SetArgs(args)`.
- **To:** `github.com/spf13/cobra.(*Command).Execute` — the cobra entry that walks the registered command tree and dispatches to the matched subcommand.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** `RootCmd` is a package-level `*cobra.Command` (declared at `root.go:20`). Receiver type is statically known; selector resolves directly to `(*cobra.Command).Execute` in the cobra dependency. No interface dispatch.

### Step 3: cobra's Execute reaches the server subcommand's RunE

- **From:** Inside `cobra.(*Command).Execute` — after parsing `args`, cobra locates the matched leaf subcommand and invokes its `RunE` field. For `mattermost server` (or the bare `mattermost` invocation), the matched RunE is `serverCmdF`.
- **To:** `server/cmd/mattermost/commands/server.go:39` — `func serverCmdF(command *cobra.Command, args []string) error`.
- **Edge type:** `function-value-in-struct-field` (selected from a registered set; reachability established by `struct-literal-field-assignment` + `init-function` wiring).
- **Resolution notes:** Three pieces of static evidence wire this edge:
  1. **struct-literal-field-assignment** at `server.go:27–32`: `var serverCmd = &cobra.Command{ ... RunE: serverCmdF, ... }`. `serverCmdF` is bound by name into the `RunE` field of the package-level `*cobra.Command` at package-init time.
  2. **init-function** at `server.go:34–37`: `init()` calls `RootCmd.AddCommand(serverCmd)` and additionally assigns `RootCmd.RunE = serverCmdF` directly. Either path lands at `serverCmdF`. Go runs this `init()` before `main()`.
  3. The runtime selection of *which* `RunE` runs depends on `os.Args`, so a sound call graph treats every registered `RunE` as a possible callee of `Execute`. For this candidate the analyzer only needs the path through `serverCmdF`. No `reflect`, no plugin lookup.

### Step 4: serverCmdF delegates to runServer

- **From:** `server/cmd/mattermost/commands/server.go:57` — `serverCmdF` returns `runServer(configStore, interruptChan)` after building `configStore`.
- **To:** `server/cmd/mattermost/commands/server.go:60` — `func runServer(configStore *config.Store, interruptChan chan os.Signal) error`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Same package, named function. Static name resolution.

### Step 5: runServer constructs the App server

- **From:** `server/cmd/mattermost/commands/server.go:73` — `runServer` calls `app.NewServer(options...)`.
- **To:** `server/channels/app/server.go:191` — `func NewServer(options ...Option) (*Server, error)`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Imported package, exported package-level constructor. Variadic of named option functions; option-function values are themselves named (`app.StartMetrics`, `app.ConfigStore(configStore)`, etc.) so the static call graph through the options is unambiguous.

### Step 6: NewServer wires up the push-notifications hub

- **From:** `server/channels/app/server.go:368` — inside `NewServer`, the receiver `s` (a `*Server` allocated earlier in the function) calls `s.createPushNotificationsHub(request.EmptyContext(s.Log()))`.
- **To:** `server/channels/app/notification_push.go:393` — `func (s *Server) createPushNotificationsHub(rctx request.CTX)`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** `s` has static type `*app.Server`; the selector `s.createPushNotificationsHub` resolves directly to the method declared on `*Server` in the same package. No interface, no field-stored function value.

### Step 7: createPushNotificationsHub spawns the hub loop

- **From:** `server/channels/app/notification_push.go:404` — after building the `PushNotificationsHub` struct literal, `createPushNotificationsHub` runs `go hub.start(rctx)` and stores the hub on `s.PushNotificationsHub` (`:405`).
- **To:** `server/channels/app/notification_push.go:408` — `func (hub *PushNotificationsHub) start(rctx request.CTX)`.
- **Edge type:** `goroutine-launch` (over a `method-call-on-concrete-type`)
- **Resolution notes:** `hub` is a local `PushNotificationsHub` value, so `hub.start` is a method on a known concrete type. The `go` statement makes this an asynchronous edge — the call is statically resolvable, but the callee runs on a different goroutine and will outlive `createPushNotificationsHub`. A static call graph just adds an edge; a precise compiler must additionally model that `start` is now live for the lifetime of the server.

### Step 8: hub.start spawns a per-notification worker goroutine

- **From:** `server/channels/app/notification_push.go:424` — inside `start`'s `for { select { case notification := <-hub.notificationsChan: ... } }` loop, after sema-acquire bookkeeping the function runs `go func(notification PushNotification) { ... }(notification)`.
- **To:** the anonymous closure body at `server/channels/app/notification_push.go:424–457`.
- **Edge type:** `goroutine-launch` (over an `inline-anonymous-closure`, with the received `notification` value passed as a captured-by-value argument).
- **Resolution notes:** The closure is defined inline, so the function literal is statically known to the analyzer at the launch site. The argument is passed positionally — no closure-over-loop-variable hazard. Two things flow into the closure that drive the next edge: (a) `notification.notificationType`, the discriminator the closure switches on, and (b) `hub.app`, the `*App` receiver used to dispatch the per-type sync method. Both are static-typed.

### Step 9: switch on notificationType selects sendPushNotificationSync

- **From:** `server/channels/app/notification_push.go:433–447` — the closure executes `switch notification.notificationType { ... case notificationTypeMessage: err = hub.app.sendPushNotificationSync(rctx, notification.post, notification.user, notification.channel, notification.channelName, notification.senderName, notification.explicitMention, notification.channelWideMention, notification.replyToThreadType) ... }`.
- **To:** `server/channels/app/notification_push.go:70` — `func (a *App) sendPushNotificationSync(rctx request.CTX, post *model.Post, user *model.User, channel *model.Channel, channelName string, senderName string, explicitMention bool, channelWideMention bool, replyToThreadType string) *model.AppError`.
- **Edge type:** `tagged-union-dispatch` over `method-call-on-concrete-type`. The discriminator is the `notificationType` field of the `PushNotification` value carried through the channel; each `case` is a direct, named method call on `hub.app` (a `*App`).
- **Resolution notes:** Statically, all four switch arms are visible and each resolves to a named method on `*App`. There is no virtual dispatch — the only "indirection" is the data-flow choice of which arm fires. A sound call-graph builder must add edges from this site to all of `clearPushNotificationSync`, `sendPushNotificationSync`, and `updateMobileAppBadgeSync`; for *this* candidate only the `notificationTypeMessage` arm matters. The arm's discriminator is set by the channel sender — most commonly `App.sendPushNotification` at `:283`-region (which writes `notificationType: notificationTypeMessage` into a `PushNotification` struct literal that is then `<-` into `notificationsChan`). The compiler does not need to back-trace senders to establish the call edge: forward-reachable type analysis is sufficient.

### Step 10: sendPushNotificationSync calls into the region

- **From:** `server/channels/app/notification_push.go:90` — after `BuildPushNotificationMessage` returns the `*model.PushNotification`, `sendPushNotificationSync` returns `a.sendPushNotificationToAllSessions(rctx, msg, user.Id, "")`.
- **To:** `server/channels/app/notification_push.go:93` — `func (a *App) sendPushNotificationToAllSessions(rctx request.CTX, msg *model.PushNotification, userID string, skipSessionId string) *model.AppError`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** `a` has static type `*App`; the selector resolves directly to the method declared on `*App` in the same file. Textbook static method call.

### Region root reached

`server/channels/app/notification_push.go:93` — `(*app.App).sendPushNotificationToAllSessions`.

### Summary

- **Path length:** 10 steps (entrypoint → region root).
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field` (with supporting `struct-literal-field-assignment` + `init-function`), `goroutine-launch` (twice — once on a named method, once on an inline anonymous closure), `tagged-union-dispatch` (a switch on a discriminator field that selects among statically-named methods).
- **Hardest edge:** Step 8–9, taken together. The per-notification work runs on a goroutine that the hub spawns *for each item it dequeues from a channel*, and the actual selection of `sendPushNotificationSync` is a `switch` on the `notificationType` field of the channel-carried `PushNotification` value. Each piece is statically resolvable in isolation — the goroutine launches an inline closure, the channel is single-typed, the switch arms are named methods — but a precise activation analysis has to model: (a) the asynchronous lifetime of `hub.start` after `createPushNotificationsHub` returns, (b) the discriminator-driven branch, and (c) the data-flow from the senders that write `notificationTypeMessage` into the struct literal pushed onto `notificationsChan`. Step 3 (cobra `RunE` dispatch) is the second-hardest, but cobra's `AddCommand` + named-`RunE`-field pattern is well-known and modellable as "store-then-call-by-name".
- **Static-analysis feasibility:** Yes — every edge is statically resolvable. There is no `reflect.Call`, no Go plugin, no runtime-supplied function pointer on the path. A whole-program call-graph that recognises (i) cobra's `AddCommand`/`RunE` registration pattern, (ii) the `go f()` and `go func(){...}()` goroutine-launch forms, and (iii) named-method calls on concrete receivers can connect `main` to `(*App).sendPushNotificationToAllSessions` end-to-end. The plugin-side caller (`PluginAPI.SendPushNotification` at `server/channels/app/plugin_api.go:1473`) is intentionally excluded from this trace because plugin code is loaded via Go-plugin / RPC at runtime — that path crosses a dynamic boundary and is not what a Monolift compiler would instrument from `main`.
- **Alternative paths considered:** The same region root is also reachable from two sibling sync functions in the same file: `clearPushNotificationSync` at `:349` and `updateMobileAppBadgeSync` at `:379`. Both call `sendPushNotificationToAllSessions` directly and are themselves selected by *other* arms of the same `switch` in `hub.start` — so they share Steps 1–8 with the trace above and only differ in which `case` of Step 9 fires. The traced `notificationTypeMessage` arm is the canonical post-creation path that drives M-8 in production load. Outside the hub, the only static caller of the region root is `PluginAPI.SendPushNotification`; that path is shorter on paper but requires modelling the plugin RPC bridge and is therefore not the intended activation path for a compiler that lifts in-binary regions.
