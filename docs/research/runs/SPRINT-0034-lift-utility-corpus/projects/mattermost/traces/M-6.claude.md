### Summary

- **Path length:** 12 steps from `main()` to the region root.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field`, `method-call-on-concrete-type`, `struct-literal-field-assignment`, `interface-method-dispatch`.
- **Hardest edge:** Step 2 (cobra `RunE` dispatch) and the Step 5/6/7 trio (route registration → `http.Handler` interface call → field-call into the handler function). The cobra step is hardest in the small: a generic compiler must understand that cobra's `Execute` calls `*Command.RunE`, which is a framework convention the analyzer would have to either special-case or model via "any function value stored in the `RunE` field of any `cobra.Command` reachable from `RootCmd`." The HTTP routing step is hardest in the large because the `http.Handler` interface in Step 6 is satisfied by many types in the program; pruning the callgraph requires noting that only `web.Handler.HandleFunc` (set at registration) reaches `createEphemeralPost`.
- **Static-analysis feasibility:** Fully resolvable in principle. Every edge is one of: a direct call, a method on a known concrete type, or a function value assigned to a struct field at known program points (route registration, cobra `RunE`). There is no `reflect.Call`, no plugin boundary, and no runtime-supplied function pointer on the path. A whole-program type+points-to analysis (e.g. Go's SSA + RTA/VTA) can build the connected callgraph by enumerating struct-literal assignments to `web.Handler.HandleFunc` and `cobra.Command.RunE`. Alternatives: the same region is also reachable from `createPost` (one extra hop through `CreatePostAsUser` → `CreatePost` → `getEmbedsAndImages`), from `updatePost` and `patchPost` via `App.UpdatePost`, from `content_flagging.go:349`, and from the WebSocket-revealed-post path (`app/post.go:3552`); all share the same edge-type vocabulary, so picking a different entrypoint does not introduce harder static-analysis obligations.
