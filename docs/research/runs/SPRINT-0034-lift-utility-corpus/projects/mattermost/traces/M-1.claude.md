### Step 7: HTTP request dispatch invokes `web.Handler.ServeHTTP`

A whole-program type analysis sees that the `*web.Handler` value (and its `Handler`-by-value receiver method set) is the only implementation in this binding chain, so the interface call resolves to `web.Handler.ServeHTTP`. No dynamic registry of handlers — the implementation set is closed at link time.

### Summary

- **Path length:** 13 steps from `main` to the region root.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field`, `method-call-on-concrete-type`, `http-handler-registration`, `interface-method-dispatch`, `closure-capture`, `goroutine-launch`.
- **Hardest edge:** Step 11 (closure-capture + goroutine-launch). The compiler must (a) tie the literal closure to the `f` parameter that ends up at `go f()` two frames deeper inside `platform.PlatformService.Go`, which means tracking a function value across two `func()`-typed parameter passes, and (b) treat the goroutine-launched edge as a real call edge despite the asynchronous boundary. Both are tractable with per-call-site closure tracking and a "goroutine-launch is a call" rule, but it is meaningfully harder than the rest of the path, which is local-call or interface analysis with a small concrete cone.
- **Static-analysis feasibility:** Fully resolvable with whole-program type analysis, mux-aware HTTP handler-registration recognition, and goroutine-aware call-graph construction. There are no reflective calls, no plugin-loaded code, no runtime-determined function pointers, and no work-item channels on the path; every edge is a named function or a closure with a unique flow site.
- **Alternative paths considered:** (i) `extract_content` job worker (`server/channels/jobs/extract_content/worker.go:71`) reaches `docextractor.Extract` via an `AppIface` interface call inside a worker `execute` closure stored in a `SimpleWorker` and launched by the jobs scheduler — strictly longer, and the interface-call adds another resolution step. (ii) `(*App).UploadFileX` at `server/channels/app/file.go:862` and the second handler at `file.go:1129` use the same `Srv().GoBuffered`/`Go` → `ExtractContentFromFileInfo` pattern as Step 11–13 from a sibling HTTP route; same length, same edge types.
