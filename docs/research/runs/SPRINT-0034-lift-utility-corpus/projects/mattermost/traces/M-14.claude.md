### Summary

- **Path length:** 13 steps.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field`, `http-handler-registration`, `interface-method-dispatch`.
- **Hardest edge:** Step 7 / Step 8 together — the gorilla/mux registration boundary. The handler is stored in two layers of struct-field function values (`web.Handler.HandleFunc` and the `mux.Router`'s string-keyed routing table) and only invoked at HTTP request time. To prove that `updatePassword` is reachable from `main`, the analyzer must (a) recognize that `api.BaseRoutes.User.Handle(path, http.Handler)` registers a handler value addressable from the program's HTTP entry, and (b) chase the function value through `APISessionRequired` into the `Handler.HandleFunc` field. Step 13's interface dispatch is intricate but tractable: a flow-sensitive points-to pass on the package-level `latestHasher` initializer is enough to pin the concrete type to `PBKDF2`.
- **Static-analysis feasibility:** Yes, the entire path is statically resolvable for the `production` build with type analysis + a points-to pass over package-level variables and over the mux registration sites. There is no reflection, no runtime function-pointer table, no plugin loader, and no `go:linkname` shim on this path. The cobra `RunE` field, the mux handler field, and the `latestHasher` interface are all written to by code in the same binary, so a whole-program analyzer can enumerate the writes and bound the dispatch precisely.
