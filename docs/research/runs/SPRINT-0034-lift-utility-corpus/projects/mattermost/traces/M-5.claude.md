## Activation path for mattermost/M-5

### Entrypoint

`server/cmd/mattermost/main.go:19` — `main()` for the `mattermost` server binary. The function's only job is to forward the command-line args to the package-level cobra command runner: `commands.Run(os.Args[1:])`.

### Step 1: main hands args to the commands runner

- **From:** `server/cmd/mattermost/main.go:20` — `main()` calls `commands.Run(os.Args[1:])`.
- **To:** `server/cmd/mattermost/commands/root.go:15` — `func Run(args []string) error`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Imported package, exported package-level function, fully qualified call. A trivial static edge — name resolution + import graph is enough.

### Step 2: Run invokes the cobra command tree

- **From:** `server/cmd/mattermost/commands/root.go:17` — `Run` calls `RootCmd.Execute()` after binding args via `RootCmd.SetArgs(args)`.
- **To:** `github.com/spf13/cobra.(*Command).Execute` — the cobra entry that walks the registered command tree and dispatches to the matched subcommand.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** `RootCmd` is a package-level `*cobra.Command` (declared at `root.go:20`). The receiver type is statically known, so the call resolves directly to `(*cobra.Command).Execute` in the cobra dependency. No interface dispatch is involved at this site.

### Step 3: cobra's Execute reaches the BulkExport subcommand's RunE

- **From:** Inside `cobra.(*Command).Execute` — after parsing `args`, cobra locates the matched leaf subcommand and invokes its `RunE` field.
- **To:** `server/cmd/mattermost/commands/export.go:123` — `bulkExportCmdF`, the function value stored in `BulkExportCmd.RunE`.
- **Edge type:** `function-value-in-struct-field` (selected from a registered set; reachability is established by `struct-literal-field-assignment` + `init-function` wiring described below)
- **Resolution notes:** Three pieces of static evidence wire this edge:
  1. **struct-literal-field-assignment** at `export.go:34–41`: `var BulkExportCmd = &cobra.Command{ ... RunE: bulkExportCmdF, ... }`. `bulkExportCmdF` is assigned by name into the `RunE` field of the package-level `*cobra.Command` value at package-init time.
  2. **init-function** at `export.go:43–58`: `init()` calls `ExportCmd.AddCommand(BulkExportCmd)` and `RootCmd.AddCommand(ExportCmd)`, splicing the export subtree into `RootCmd`'s children slice. Go runs this `init()` before `main()`.
  3. The runtime selection of *which* `RunE` runs depends on `os.Args` (the user typing `mattermost export bulk <file>`), so a sound call graph must treat every `RunE` reachable from `RootCmd`'s subcommand tree as a possible callee of `Execute`. For *this* candidate the analyzer only needs to keep the one path through `BulkExportCmd.RunE`.
  A whole-program analyzer that models cobra's `AddCommand`/`RunE` pair as "store-then-call-by-name" can resolve this statically without running the program. There is no `reflect` or plugin lookup on the path.

- **Resolution notes:** The static type of `a` is the concrete pointer `*app.App` (the return type of `InitDBCommandContextCobra` is annotated as `*app.App` in its signature). The selector `a.BulkExport` therefore resolves directly to the method declared on `*App`. No interface table, no field-stored function value — a textbook static method call.

### Region root reached

### Summary

- **Path length:** 4 steps (entrypoint → region root).
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field` (with supporting `struct-literal-field-assignment` and `init-function` registration edges), `method-call-on-concrete-type` (again).
- **Hardest edge:** Step 3 — the cobra subcommand dispatch. The actual call from `cobra.Execute` to `bulkExportCmdF` flows through a function-valued struct field whose value is assigned in a package-level struct literal and whose containing `*cobra.Command` is spliced into `RootCmd`'s subcommand tree by `init()`. A static analyzer must model both the field-assignment and the `AddCommand` registration to know that `bulkExportCmdF` is reachable from `RootCmd.Execute`. Cobra additionally uses `os.Args` to choose *which* `RunE` runs, so a sound-but-imprecise analysis would over-approximate by treating every registered `RunE` as reachable; a precise analysis would need to model the command-name-to-subcommand match.
- **Static-analysis feasibility:** Yes — every edge is statically resolvable. There is no `reflect.Call`, no Go plugin, no runtime-supplied function pointer on the CLI path. A whole-program call graph that recognises (a) named-function values assigned into struct fields and (b) cobra's `AddCommand` registration pattern can connect `main` to `(*App).BulkExport` end-to-end.
- **Alternative paths considered:** The same region root is also reachable from the running server via the `export_process` background job worker at `server/channels/jobs/export_process/worker.go:72`, which calls `app.BulkExport` through an `AppIface` interface (`worker.go:18–23`). That path is materially longer: it requires tracing `main → server bootstrap → JobServer construction → MakeWorker registration → scheduler dispatch → execute closure → AppIface.BulkExport`, and adds an `interface-method-dispatch` edge whose resolution to `*app.App` requires whole-program type analysis. The CLI path traced above is the shortest and was chosen for that reason.
