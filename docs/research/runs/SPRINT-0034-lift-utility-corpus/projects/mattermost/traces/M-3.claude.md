### Summary

- **Path length:** 14 steps (entrypoint → region root).
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field`, `method-call-on-concrete-type`, `interface-method-dispatch`, `closure-capture`, `goroutine-launch`.
- **Hardest edge:** Step 6 → Step 7 (handler registration meeting HTTP runtime dispatch). The function value `createPost` is parked in `web.Handler.HandleFunc` and the `*web.Handler` is parked inside gorilla mux's runtime routing table keyed by URL pattern. Connecting `Server.Start()` to a particular `ServeHTTP`/`HandleFunc` invocation requires (a) field-flow tracking through the registration call, and (b) a conservative assumption that any registered handler may be invoked once the HTTP server runs — gorilla mux's per-pattern dispatch is opaque to pure type analysis.
- **Static-analysis feasibility:** Resolvable end-to-end with whole-program type analysis + call-graph construction over closures and struct-field function values, plus a conservative model of the HTTP server treating any registered `http.Handler` as reachable. No genuinely dynamic gaps (no `reflect.Call`, no plugin lookup, no runtime-determined function pointer) lie on this path.
- **Alternative paths considered:** `(*App).TriggerWebhook` is reached only via `handleWebhookEvents` → `handlePostEvents` → `CreatePost`. The final three method-call edges (Steps 12–14) are forced. `CreatePost` itself has many in-tree callers (e.g. `(*App).CreatePostMissingChannel`, scheduled-post job at `scheduled_post_job.go:193`, channel/team/bot system messages, content-flagging flows). The HTTP-handler chain via `createPost` → `CreatePostAsUser` → `CreatePost` was selected as the canonical and shortest user-facing route; the scheduled-post job route would replace Steps 6–9 with a job-scheduler registration but adds at least one extra hop through the cron/job dispatcher.
