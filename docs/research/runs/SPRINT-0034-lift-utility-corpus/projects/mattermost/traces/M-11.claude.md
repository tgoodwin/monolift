`server/cmd/mattermost/main.go:19` — `main()` is the binary entrypoint for the `mattermost` CLI/server. It calls `commands.Run(os.Args[1:])` and exits on error. The same binary serves the long-running server, the job server, and CLI subcommands; which one runs is selected by argv via cobra's command tree.

### Step 3: cobra invokes the matched subcommand's RunE function value

- **From:** Inside `cobra.(*Command).Execute` — cobra reads the `RunE` field of the matched subcommand and calls it.
- **To:** `server/cmd/mattermost/commands/import.go:104` — `bulkImportCmdF(command *cobra.Command, args []string) error`.
- **Edge type:** `function-value-in-struct-field`
- **Resolution notes:** The function value is bound at `commands/import.go:36` via the struct literal field `RunE: bulkImportCmdF` on `BulkImportCmd`. `BulkImportCmd` is wired into the tree by `ImportCmd.AddCommand(BulkImportCmd, ...)` at `commands/import.go:45-48` and `RootCmd.AddCommand(ImportCmd)` at `commands/import.go:49`, both inside the `init()` at `commands/import.go:39`. A static analyzer would (a) treat each package-init as runnable, (b) collect all `RunE` field assignments on values reachable from `RootCmd`, and (c) treat each as a possible callee of `Execute()`'s indirect call through the field. The actual selection at runtime is driven by argv string matching, which is data-dependent and not statically resolvable, but for whole-program reachability the analyzer simply admits every registered `RunE` as a possible target — which is sufficient to reach `bulkImportCmdF`.

### Summary

- **Path length:** 5 steps.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field`.
- **Hardest edge:** Step 3 (cobra's dispatch through the `RunE` struct field). It is the only edge that is not a directly named call: cobra performs argv-driven matching to pick which subcommand's `RunE` to invoke, so a static analyzer cannot tell *which* `RunE` will fire. It can, however, soundly enumerate all reachable assignments to `RunE` (including `import.go:36`) by tracking field stores and the `AddCommand` graph rooted at `RootCmd`. That is enough for compile-time reachability, but it is the only edge that needs more than ordinary call-graph construction.
- **Static-analysis feasibility:** Fully feasible with type analysis plus a points-to/field-sensitive call-graph pass — no `reflect`, no plugins, and no runtime function pointers on this path. Cobra's argv-driven selection is data-dependent but does not break static reachability, since every candidate `RunE` is statically a function literal/identifier assigned to the field.

### Alternative paths (not chosen)

- **Import-process job worker.** `server/channels/jobs/import_process/worker.go:136` also calls `app.BulkImportWithPath` from inside an `execute` closure that becomes `(*jobs.SimpleWorker).execute`. Reaching it from `main()` requires going through the job-server registration (`MakeWorker` at `worker.go:37`), the scheduler/registry that selects workers by `model.JobType` (a string-keyed dispatch table), and a `closure-capture` of the `app AppIface` parameter — and the call into `app.BulkImportWithPath` at `worker.go:136` is via the `AppIface` interface (`worker.go:33`), so it would add an `interface-method-dispatch` edge as well. Strictly longer and harder for static analysis than the CLI path above.
- **Tests** (`channels/app/import_test.go`, `channels/app/export_test.go`, `channels/app/import_bulk_insert_test.go`) call `BulkImport`/`BulkImportWithPath` directly, but they originate from `go test` entrypoints and are not part of the production binary.
