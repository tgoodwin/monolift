- **Edge type:** `function-value-in-struct-field` (composed with `init-function` for the registration step)
- **Resolution notes:** Three pieces of static information must be combined:
  1. `SlackImportCmd` is a `*cobra.Command` declared at `import.go:23-29`; its `RunE` field is set to `slackImportCmdF` via struct-literal field assignment.
  2. The `init()` at `import.go:39-50` registers the command tree: `ImportCmd.AddCommand(BulkImportCmd, SlackImportCmd)` then `RootCmd.AddCommand(ImportCmd)`.
  3. At runtime, `Execute()` walks that tree using `args` and invokes the matched command's `RunE` field.

  A static analyzer must (a) recognize cobra's `AddCommand` + `RunE` pattern as a dispatch table — or (b) over-approximate by treating every function value assigned to a `RunE`/`Run` field of any `cobra.Command` reachable through `AddCommand` registrations as an out-edge of `RootCmd.Execute()`. The leaf selection itself depends on `args` (external input), so this is the dynamic gap; the *set* of possible callees is fully knowable, only the selection is not.

### Summary

- **Path length:** 4 steps (entrypoint → step 1 → step 2 → step 3 → step 4 → region root).
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field` (with an `init-function` registration), `method-call-on-concrete-type`.
- **Hardest edge:** Step 2 (cobra dispatch). The link from `RootCmd.Execute()` to the concrete `slackImportCmdF` requires modeling cobra's runtime tree-walk: the analyzer must recognize that any function value assigned to a `RunE`/`Run` field of a `*cobra.Command` reachable via the `AddCommand` chain is a possible callee. The exact callee depends on `os.Args`, so the analyzer can only enumerate the candidate set, not pick one.
- **Alternate paths considered:** A second path runs through the HTTP API: `POST /api/v{4}/teams/{team_id}/import` is registered at `server/channels/api4/team.go:69` (handler `importTeam` at line 1438) which calls `c.App.SlackImport(...)` at line 1510, joining this same trace at Step 3. The handler registration uses the same pattern as cobra (function value installed in a routing table via `mux.Handle`), but the dispatch from URL → handler is across an external HTTP boundary (gorilla mux + HTTP server), so it is *longer* than the CLI path and crosses an additional dynamic boundary. The CLI path is shorter and was therefore chosen.
- **Static-analysis feasibility:** Resolvable with whole-program type analysis plus framework-aware modeling of (a) cobra's `AddCommand`/`RunE` pattern and (b) the concrete-method dispatch chain after the cobra hop. There is no `reflect`, no plugin loader, no runtime-determined function pointer between the entrypoint and the region root — only the cobra struct-field dispatch, which is a syntactically recognizable pattern. The unresolved part is *which* CLI command argv selects, not *what set of functions* it could reach.
