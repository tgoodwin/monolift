### Step 7: StartWorkers launches each registered worker in its own goroutine

- **From:** `server/channels/jobs/server.go:87` — `srv.workers.Start()` → `server/channels/jobs/workers.go:52` — `go w.Run()`

- **Edge type:** `goroutine-launch` over `interface-method-dispatch` (the loop variable `w` has static type `model.Worker`)
- **Resolution notes:** This is the hardest edge in the path. To resolve `w.Run()` to `(*common.IndexerWorker).Run`, a static analyzer needs to:
  1. Track every value flowing into `Workers.workers map[string]model.Worker` via `AddWorker` (`workers.go:38`), called from `JobServer.RegisterJobType` (`server.go:72`). The IndexerWorker enters via `server/channels/app/server.go:1499`: `s.Jobs.RegisterJobType(model.JobTypeElasticsearchPostIndexing, builder.MakeWorker(), nil)`.
  2. Resolve `builder` — `builder := jobsElasticsearchIndexerInterface(s)` (`server.go:1498`). `jobsElasticsearchIndexerInterface` is a package-level `func` variable assigned at package init: `app.RegisterJobsElasticsearchIndexerInterface(...)` from `server/enterprise/elasticsearch/init.go:24` sets it to a closure that returns `&elasticsearch.ElasticsearchIndexerInterfaceImpl{Server: s}` (or the OpenSearch sibling, depending on a runtime config flag).
  3. Resolve `builder.MakeWorker()` — interface method on `ejobs.IndexerJobInterface`; for the ES backend it dispatches to `(*ElasticsearchIndexerInterfaceImpl).MakeWorker` at `server/enterprise/elasticsearch/elasticsearch/indexing_job.go:25`, which returns the value built by `common.NewIndexerWorker(...)` at `server/enterprise/elasticsearch/elasticsearch/indexing_job.go:38`. That constructor (`server/enterprise/elasticsearch/common/indexing_job.go:39`) returns a `*IndexerWorker`.
  4. Combine those facts to conclude that the registered worker for `JobTypeElasticsearchPostIndexing` is `*common.IndexerWorker`, hence `w.Run()` invokes `(*IndexerWorker).Run`.
  This requires whole-program type analysis, package-init ordering, and tracking config-driven branching (ES vs. OS) — a standard but non-trivial RTA/0-CFA problem. The `go ...` itself is a goroutine spawn; the call edge is preserved but execution is concurrent.

### Summary

- **Path length:** 11 steps.
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field`, `method-call-on-concrete-type`, `goroutine-launch`, `interface-method-dispatch`, `channel-receive` (auxiliary control transfer at Step 8).
- **Hardest edge:** Step 7 (`workers.Start` → `(*IndexerWorker).Run`). It combines (a) goroutine spawn, (b) interface dispatch on `model.Worker`, (c) a worker registry populated through a package-level `func` variable (`jobsElasticsearchIndexerInterface`) wired at `init()` time, and (d) another nested interface dispatch on `IndexerJobInterface.MakeWorker()`. Resolving the concrete `*IndexerWorker` requires whole-program type/value flow plus package-init ordering and accepting both ES/OS backend branches.
- **Static-analysis feasibility:** Feasible end-to-end with standard whole-program analysis (RTA/0-CFA + field-sensitive flow over `cobra.Command.RunE` and `Workers.workers`) — there is no `reflect`, no `plugin`, and no user-supplied function pointer. The only "dynamic" gap is the inter-goroutine channel handoff at Step 8, which is a *scheduling* boundary, not a call-graph one; the analyzer can include the edge unconditionally.

  - `server/channels/app/platform/license.go:185` re-invokes `ps.Jobs.StartWorkers()` after a license change at runtime — same downstream path, different trigger.
