(1) The `http.ServeMux` lookup from a request URL/method to a handler is pattern-table-driven; a whole-program analyzer must over-approximate by treating any `mux.HandleFunc` site as a possible target reachable from `Server.Serve`. (2) Once inside the registered closure, resolving `v.Action` requires tracking the `*Route` value built by `sub.POST("/upload", backupUpload, ...)` — i.e. data-flow from the function reference passed into `POST` into the `Action` field of the `*Route` struct, then through the `routeHook.Trigger(event, v.Action)` indirect call.

### Summary

- **Path length:** 10 steps.
- **Edge types encountered:** `method-call-on-concrete-type`, `function-value-in-struct-field` (cobra `RunE`), `direct-function-call`, `struct-field-assignment-of-handler` (`http.Server.Handler`), `http-handler-registration`, `closure-capture`, `interface-method-dispatch` (`blob.DriverWriter`), `goroutine-launch`.
- **Hardest edge:** Step 5 (the `http.ServeMux` → handler closure → captured `v.Action` chain). It composes three independently tricky resolutions: (a) HTTP pattern-string routing performed by the stdlib mux at runtime; (b) data-flow from a function literal/reference into a struct field (`Route.Action`) that is later read inside a separately-constructed closure; (c) the indirect call `handlers[i](event)` inside `Hook.Trigger` (`tools/hook/hook.go:169`) where `handlers[i]` is an element of a slice of `func(T) error` populated from both a `Hook.handlers` list and one-off args. Step 8's `blob.DriverWriter` interface dispatch is the next-hardest, but it is a textbook receiver-set narrowing once the whole program is in view.
- **Static-analysis feasibility:** The entire path is statically resolvable in principle with whole-program type analysis plus a call-graph that models (i) cobra's `RunE` field-dispatch, (ii) `http.ServeMux` registration as an unconditional reachability edge from `Server.Serve` to every registered handler, (iii) `blob.Driver`/`DriverWriter` interface implementations, and (iv) `go func(){...}()` launch sites — there is no `reflect.Call`, plugin loading, or runtime-loaded function pointer on this path. A compiler producing the activation wiring for `s3.Uploader.Upload` would over-approximate at the HTTP-mux and `Hook.Trigger` indirections but converge on a single concrete callee at the region root because `*s3.Uploader` is the only type instantiated for the captured `uploader` field.
- **Alternative entrypoints:** `(*filesystem.System).Upload` is also reached from `core/field_file.go:534` (the record-save flow that uploads attached file fields) and from `core/base_backup.go:109` (a scheduled-backup routine that uploads each chunk). Both ultimately funnel into the same Steps 7–10 chain; the backup-upload HTTP handler chosen above is the shortest because it is one user-triggered HTTP route hop away from `(*filesystem.System).UploadFile`, whereas the field-file path requires several additional record-save and DAO indirections.
