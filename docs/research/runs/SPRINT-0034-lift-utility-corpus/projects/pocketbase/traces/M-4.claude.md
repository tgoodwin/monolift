### Summary

- **Path length:** 12 steps from `main()` to `archive.Create`.
- **Edge types encountered:** `method-call-on-concrete-type`, `struct-literal-field-assignment`, `function-value-in-struct-field`, `direct-function-call`, `interface-method-dispatch`, `closure-passed-as-argument`.
- **Hardest edge:** Step 7 (the route → mux → http.Server handoff) is the most demanding for static analysis. The function value `backupCreate` flows across three abstraction layers (the framework's `Route.Action` field → its custom `BuildMux` walker → `http.ServeMux`'s internal map → eventual call from `(*http.Server).Serve`). Connecting the registration call site to the actual invocation requires field-sensitive points-to that follows function values through struct fields and map values across package boundaries. Step 9 is a close runner-up because the one-off closures handed to `Hook.Trigger` are placed into a slice and invoked indirectly through chained `event.Next()` thunks, which a less precise analysis might lose.
- **Static-analysis feasibility:** Resolvable with whole-program type analysis (CHA/RTA) plus a points-to / call-graph pass that tracks function values stored in struct fields, slices, and maps — there is no reflection, no plugin loading, and no runtime-decided function pointer along this path. Alternative entry: the same `(*BaseApp).CreateBackup` is also reachable from a cron-scheduled closure registered in `(*BaseApp).registerAutobackupHooks` (`core/base_backup.go:308`, wired into `(*BaseApp).OnSettingsReload`/`OnBootstrap` at lines 370 and 380); that path adds a `callback-registration` edge into the cron table but is otherwise comparable in length and tractability.
