### Summary

- **Path length:** 13 steps (`main` → region root).
- **Edge types encountered:** `method-call-on-concrete-type`, `struct-literal-field-assignment`, `function-value-in-struct-field`, `direct-function-call` (×5), `http-handler-registration`, `function-value-call-from-registry`, `closure-capture` (×2, including a variadic-callback variant), `goroutine-launch`.
- **Hardest edge:** Step 9 (the hook `Trigger` indirection). The finalizer is passed as a variadic `func(T) error`, then re-wrapped through the per-event `nextFunc` field that is rewritten in a loop. A static analyzer must follow the variadic slice into `Trigger`, model the per-event function-value field, and recognize that the closure is eventually called via `event.Next()`. The goroutine-launch in Step 11 and the cobra `RunE` field-call in Step 3 are similar in shape but simpler (single, fully-visible field assignment).
- **Static-analysis feasibility:** Yes — the entire path is statically resolvable with type analysis plus a function-value (closure / field) points-to analysis. Every "indirect" edge (cobra `RunE`, router handler registry, hook `nextFunc`, `FireAndForget`'s `f` parameter, the goroutine closure) is a Go function value whose set of producers is visible in the source tree; no `reflect.Call`, plugin loading, or runtime-determined function pointer is on this path. The four alternative entry points into the region — `SendRecordVerification` (registered at `apis/record_auth.go:53`), `SendRecordChangeEmail` (line 60), `SendRecordOTP` (line 39), and `SendRecordAuthAlert` (called from `apis/record_helpers.go:633`) — share the same call-graph shape and the same conclusion.
