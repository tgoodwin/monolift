### Summary

- **Path length:** 13 steps.
- **Edge types encountered:** `method-call-on-concrete-type`, `struct-literal-field-assignment`, `function-value-in-struct-field` (with `command-line-arg-dispatch` flavor), `goroutine-launch` (Step 3, secondary), `direct-function-call`, `http-handler-registration`, `closure-capture`, `function-value-call`, `interface-type-assertion`, `interface-method-dispatch`, `method-value-return`.
- **Hardest edge:** Step 11 (`interface-method-dispatch` on `SetterFinder` after a runtime type assertion). The dispatch target depends on the concrete element type of `collection.Fields`, which is determined by collection schema loaded from the database. A sound over-approximation enumerates all in-tree `SetterFinder` implementers (made discoverable by the `_ SetterFinder = (*X)(nil)` compile-time assertions in each `field_*.go`); a precise analysis needs schema-aware reasoning that goes beyond pure type analysis. Step 7's `mux.HandleFunc` indirection is comparable in difficulty in principle but is well-understood for the std `net/http` pattern.
- **Static-analysis feasibility:** Reachable end-to-end with whole-program type analysis plus standard models for (1) cobra `RunE` dispatch as "any registered RunE is callable from `RootCmd.Execute`", (2) `net/http.ServeMux.HandleFunc` as "any registered handler is callable from the server", and (3) interface dispatch over `SetterFinder` enumerated by the `_ SetterFinder = (*X)(nil)` checks. No reflection, plugin loading, or runtime function-pointer construction is on this path. Alternative (longer) paths exist via `bindRecordCrudApi` → record create/update handlers → `record_upsert.go` form binding → `record.Load(...)` → `m.Set("password", ...)` (also through the same Step 11–13 tail), and via OTP request (`apis/record_auth_otp_request.go:94`); both are equal-or-greater in length and add reflection-based form binding, so the password-reset-confirm path is the cleanest minimal trace.
