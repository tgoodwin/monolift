### Summary

- **Path length:** 12 steps.
- **Edge types encountered:** `method-call-on-concrete-type`, `function-value-in-struct-field` (cobra `RunE`), `direct-function-call`, `closure-capture`, `http-handler-registration`, `function-value-from-route-table`, `interface-method-dispatch`, `closure-passed-as-callback-arg`, `function-value-from-slice`.
- **Hardest edge:** Step 2 (cobra `RunE` invocation). `RunE` is a `func` field assigned in a struct literal in `cmd/serve.go:24`, then handed off through `AddCommand` into `RootCmd.commands`, and finally invoked by `cobra.Command.Execute` after argv-driven subcommand resolution. Recovering the closure target requires both struct-field flow analysis and modeling the cobra dispatch loop. By contrast, Step 9 (`function-value-from-slice` inside `Hook.Trigger`) is mechanical once you accept that all flows into `handlers` come from the variadic argument and the registered hook list at the same call site.
- **Static-analysis feasibility:** Resolvable end-to-end with type analysis + a points-to / call-graph builder that models (a) cobra's `RunE` field and command tree, (b) HTTP route registration as a kind of indirect-call table, and (c) function-valued slices in the hook system. There is no `reflect.Call`, no plugin path, and no runtime-only function pointer in the production serve path; all targets are statically enumerable. Alternative shortest paths from other HTTP entrypoints exist (`recordView`, `recordCreate`, `recordUpdate`, batch and realtime APIs, all of which funnel through `EnrichRecord`/`EnrichRecords` — see `apis/record_crud.go:199, 355, 494` and `apis/realtime.go:556`); they share the same edge-type profile and have similar lengths, so picking any other entrypoint does not change the static-analysis difficulty.
