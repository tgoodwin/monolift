### Summary

- **Path length:** 8 steps.
- **Edge types encountered:** `method-call-on-concrete-type`, `function-value-in-struct-field`, `direct-function-call`, `http-handler-registration`, `closure-as-callback-argument`, `type-asserted-method-call`.
- **Hardest edge:** Step 5 (`http-handler-registration`). The handler function travels from a `(*RouterGroup).POST` registration into a custom router structure, gets compiled into an `http.ServeMux` pattern via `BuildMux`, is assigned to `http.Server.Handler`, and is then invoked by Go's standard HTTP dispatch loop on a path/method match driven by a string literal. A static call graph has to thread through three layers (custom router DSL → `net/http` mux → request-time pattern match) and link the literal `"/auth-with-password"` to the handler value.
- **Static-analysis feasibility:** Yes, with whole-program type analysis plus modeling of (a) `cobra.Command.RunE` field-value dispatch, (b) `(*RouterGroup).POST` handler registration, and (c) the `Hook.Trigger` slice-of-function-values dispatch, every edge resolves to a fully-known function value. There is no `reflect.Call`, plugin loading, or runtime-supplied function pointer along this path, so the activation path is statically resolvable end-to-end.
