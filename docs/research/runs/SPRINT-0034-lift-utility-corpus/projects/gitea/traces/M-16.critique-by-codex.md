# Trace critique for gitea/M-16 by codex

## Critique of claude's trace

### Path
- **Correct:** partially — The web login path is real and reaches `Argon2Hasher.HashWithSaltBytes` when the stored user hash algorithm is Argon2, but the trace skips the explicit `NewMainApp`/`newWebCommand` construction edge and compresses the `hash.Parse` factory/interface-field flow.
- **Minimal:** no — The admin `change-password` path reaches `SetPassword`/`Hash` without HTTP routing, auth-source dispatch, or the `VerifyPassword` type-test fallthrough. Within the chosen web path, `(*db.Source).Authenticate` is a trivial forwarding wrapper that could be collapsed.

## Critique of gemini's trace

### Path
- **Correct:** partially — It sketches the same real web login path, but many citations are off and several required edges are skipped or conflated: `main` is at `main.go:39`, `RunMainApp` calls `app.Run` at `cmd/main.go:160`, `Routes` starts at `routers/web/web.go:256`, and `registerWebRoutes` is called at `web.go:313`.
- **Minimal:** no — It uses the longer web login path instead of the admin `change-password` path, includes the trivial `(*db.Source).Authenticate` forwarding wrapper, and omits the non-trivial `hash.Parse` registry/factory/interface-field steps.

### Other notes
Step 1 also omits `main.go:44` calling `cmd.NewMainApp`, which is needed to justify the later `Action` target. The trace's summary misses the string-keyed hasher registry edge entirely, even though its prose mentions registration maps.

## Cross-trace observations

Both foreign traces converge on the web login path: CLI `web` action, POST `/user/login`, `UserSignIn`, DB auth, `ValidatePassword`, `VerifyPassword`/`Hash`, then the embedded hasher dispatch. They diverge from the canonical minimal path because the admin `change-password` route avoids HTTP routing, auth-source dispatch, and verification fallback. Claude's trace is closest among the two foreign traces, but the canonical minimal path is the admin path in codex's trace.
