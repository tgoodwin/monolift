### Liveness of the closure (why the body in Step 7 actually runs)

The closure created at Step 7 is not called by `Init` directly; it is registered with the queue subsystem and later invoked by worker goroutines. For a static analyzer to certify that the call at line 488 is *reachable*, it must additionally connect these edges (none of which lengthen the entrypoint→region path, but all of which the compiler must resolve to prove liveness):

- `queue.CreateUniqueQueue[T](..., handler)` (`modules/queue/manager.go:98`) → `createWorkerPoolQueue` → `NewWorkerPoolQueueWithContext` (`modules/queue/workerqueue.go:217`), which assigns `w.origHandler = handler` (line 242) and wraps it as `w.safeHandler = func(t ...T) { ... w.origHandler(t...) ... }` (lines 243–257). **Edge type: `function-value-in-struct-field`** (the closure is parked in `WorkerPoolQueue.origHandler` and `WorkerPoolQueue.safeHandler`).
- `services/pull/check.go:497` — `go graceful.GetManager().RunWithCancel(prPatchCheckerQueue)`. **Edge type: `goroutine-launch`** combined with **`interface-method-dispatch`**: `RunWithCancel` takes a `RunCanceler` interface (`modules/graceful/manager.go:27`) and calls `rc.Run()` (line 77), which resolves to `(*WorkerPoolQueue[T]).Run` (`modules/queue/workerqueue.go:184`).

### Summary

- **Path length (entrypoint → region root, body-of-closure path):** 7 steps.
- **Edge types encountered (entrypoint→region path):** `direct-function-call`, `struct-literal-field-assignment`, `function-value-as-argument`, `higher-order-call`.
- **Edge types required to prove the closure actually runs (liveness):** `function-value-in-struct-field`, `goroutine-launch`, `interface-method-dispatch`, `method-call-on-concrete-type`, `channel-send-receive`.
- **Hardest edge:** Step 2 (cli `Action` field dispatch) and the queue-subsystem `function-value-in-struct-field` chain are the two hardest. The cli edge crosses a third-party module boundary where the call to `Action(...)` lives in `urfave/cli/v3`; a static analyzer needs either inter-module flow or a model of the cli library to know the registered `runWeb` is invoked. The queue chain is a generic container parking a closure in a field and invoking it from a different goroutine — recovering precision requires per-instance field-sensitivity through a generic type and across goroutine boundaries.
- **Alternative paths considered:** None — `checkPullRequestMergeable` (lowercase, unexported) is referenced exactly once in the codebase: from inside the closure on `services/pull/check.go:488`. Producers that *enqueue* work to that closure (e.g. `AddPullRequestToCheckQueue`, `StartPullRequestCheckImmediately`, the `InitializePullRequests` background sweeper, and HTTP handlers in `routers/web/repo/pull.go` and `routers/api/v1/repo/pull.go`) drive runtime activation but do not constitute a different *static* path to the region root — they all funnel through the same closure.
- **Static-analysis feasibility:** Feasible end-to-end with no dynamic-language gaps (no `reflect.Call` of user input, no plugin loading, no runtime function pointer reassignment). The entire path is statically resolvable given (a) modeling of the urfave/cli `Action` field dispatch, (b) field-sensitive flow through the generic `WorkerPoolQueue[T]` struct (`origHandler`/`safeHandler`), and (c) interface-method analysis for `RunCanceler.Run`. Direct calls dominate the entrypoint→region chain; the indirection lives in proving the closure's invocation, not in reaching its definition.
