### Summary

- **Path length:** 13 steps from `main()` to `runSync`.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `struct-literal-field-assignment`, `function-value-stored-in-struct-field`, `goroutine-launch`, `interface-method-dispatch`, `closure-capture`, `type-tag-switch` (guard).
- **Hardest edge:** Step 10 — the queue worker's invocation of `q.safeHandler`, which is a closure stored in a struct field that internally dispatches through another function-valued struct field (`q.origHandler`). Proving statically that the `mirror` queue's `origHandler` is `queueHandler` requires (a) generic instantiation of `WorkerPoolQueue` for `*SyncRequest`, (b) tracing the `handler` parameter through three constructor frames (`CreateUniqueQueue` → `createWorkerPoolQueue` → `NewWorkerPoolQueueWithContext`), and (c) a single-assignment / escape-analysis result for `origHandler`. This is feasible but non-trivial — it is the canonical "indirect call resolvable only after data-flow over generics + struct fields" pattern. Step 8 is the registration site for the same indirect call, and Step 9's goroutine + interface dispatch on `RunCanceler.Run()` are also non-trivial but easier (the `RunCanceler` interface has very few implementers in this codebase).
- **Static-analysis feasibility:** Resolvable end-to-end with whole-program type analysis, generic monomorphisation, and conservative function-pointer flow analysis. There are no reflection calls, no plugin loaders, and no user-supplied function pointers along the path. The two indirect dispatches (cli Action field, queue origHandler field) are both single-assignment from package-level function literals/identifiers, which is exactly the pattern static call-graph builders (Andersen-style points-to or Go's existing `golang.org/x/tools/go/callgraph/vta`) handle well. Alternative reachability paths (e.g. the cron-driven `services/cron/tasks_basic.go:41` `mirror_service.Update` → enqueue → same queue worker, or the HTTP API path `routers/api/v1/repo/mirror.go:72` `AddPullMirrorToQueue` → enqueue → same queue worker) all converge on Step 10 and would not be shorter; they would only add prefix steps for cron registration or HTTP route registration before reaching the queue handoff.
