### Summary

- **Path length:** 12 steps
- **Edge types encountered:** `direct-function-call`, `function-value-in-struct-field` (cli `Action`), `http-handler-registration`, `interface-method-dispatch`, `method-call-on-concrete-type`, `string-keyed-registry-lookup` (with `init-function` registration), `interface-type-assertion-fallthrough`
- **Hardest edge:** **Step 10** — the string-keyed registry lookup in `hash.Parse`. The selector string (`u.PasswdHashAlgo` from the DB row, or `setting.PasswordHashAlgo` from `app.ini`) is not knowable statically, so a precise pointer/call-graph analysis must (a) collect every `MustRegister`/`Register` call site from package-level `init()`s as the closed set of map values, (b) follow the factory closure (`hash.go:101–104`) to its captured `newFn`, (c) infer the concrete return type `*Argon2Hasher`, and (d) propagate that into the embedded interface field of `PasswordHashAlgorithm` so that the later `algorithm.HashWithSaltBytes(...)` call (Step 12) can be resolved. This is the typical "registry of constructors keyed by a runtime string" pattern and requires the analyzer to model the registry as a multi-target edge.
- **Static-analysis feasibility:** Feasible. Every step is statically resolvable in principle — the factory-registry indirection collapses to a finite, statically-enumerable set of targets via init-driven registrations, and all other edges are direct calls, concrete-method calls, interface dispatches against a closed set of registered implementations, or function-valued struct fields whose assignments are visible in source. There are no `reflect.Call`, plugin, or runtime-generated code boundaries on this path.
