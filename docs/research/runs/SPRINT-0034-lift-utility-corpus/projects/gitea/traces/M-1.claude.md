### Summary

- **Path length:** 13 steps.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field`, `function-value-as-argument`, `function-value-as-argument-stored-in-struct-field`, `goroutine-launch`, `interface-method-dispatch`, `channel-send-receive`, `closure-capture`.
- **Hardest edge:** Step 6 (handler registered into `WorkerPoolQueue.origHandler`) compounded with steps 11–12 (`safeHandler`/`origHandler` invocation). The function value `webhook.handler` flows through three layers of generic helpers before being stored in a struct field, then is later invoked indirectly via that field on a goroutine-spawned worker. Connecting the registration site to the invocation site requires a flow- and field-sensitive points-to analysis that distinguishes individual `WorkerPoolQueue[int64]` instances; a context-insensitive analysis would conservatively merge handlers across every `CreateUniqueQueue`/`CreateSimpleQueue` call site in the program. Step 8's `RunCanceler.Run()` interface dispatch is structurally similar but easier — only a handful of types implement that interface.
- **Static-analysis feasibility:** Statically resolvable end-to-end. Every edge is a typed Go construct (struct field, interface method, goroutine, channel, closure) — no reflection, no plugin loading, no string-keyed function registries on the activation path. A whole-program, context- and field-sensitive call-graph builder (e.g. `golang.org/x/tools/go/callgraph/vta` or a points-to analysis like Andersen with on-the-fly call-graph construction) can connect `main` to `Deliver` without any dynamic gap. The two complications a compiler must handle are (a) urfave/cli's reflective-looking but actually typed `Action` field (step 3), and (b) the queue's deferred handler invocation across goroutine and struct-field boundaries (steps 6–12).

There is no shorter path.
