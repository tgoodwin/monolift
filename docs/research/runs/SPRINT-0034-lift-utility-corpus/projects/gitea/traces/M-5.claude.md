### Summary

- **Path length:** 9 edges (entrypoint → 9 steps → region root).
- **Edge types encountered:** `function-value-in-struct-field`, `direct-function-call`, `function-value-as-parameter`, `function-value-call-via-parameter`, `closure-capture`, `goroutine-launch`.
- **Hardest edge:** Step 7+8 combined — the closure is captured inside `Init`, threaded through generic queue construction, stored in two struct fields (`origHandler`, then wrapped via `safeHandler`), and finally invoked on a worker goroutine. A precise call graph for the `index` call therefore requires field-sensitive points-to over a generic struct type *and* whole-program reasoning across goroutine boundaries. By contrast, the cli `Action` dispatch in Step 1 is structurally similar (function-value-in-struct-field) but easier because the field is set to a named top-level function rather than a closure.
- **Static-analysis feasibility:** Fully statically resolvable. Every edge is principle-resolvable with whole-program type analysis plus field-sensitive points-to; nothing on the path goes through `reflect.Call`, runtime plugins, or user-supplied function pointers. There are also alternative reachability paths into `index` (e.g. via `populateRepoIndexer` at `modules/indexer/code/indexer.go:298`, or the public `UpdateRepoIndexer` at `:240`, both of which `Push` items onto the same `indexerQueue` whose handler closure ultimately calls `index`); the path traced above is the shortest because it goes from queue construction directly to the call site of `index` inside the registered handler closure, without an intermediate `Push`.
