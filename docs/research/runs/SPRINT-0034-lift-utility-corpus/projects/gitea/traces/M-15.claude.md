## Activation path for gitea/M-15

### Entrypoint

`main.go:39` — `main()` builds a `urfave/cli` command tree via `cmd.NewMainApp` and dispatches via `cmd.RunMainApp(app, os.Args...)`. With no subcommand the default (`webCmd.Name`) runs the long-lived web server.

> Path chosen: the HTTP-triggered "Synchronize Now" button on a repository's Mirror Settings page. This is the shortest path: HTTP request → mirror queue → worker → `StoreMissingLfsObjectsInRepository`. The cron-driven path (`update_mirrors` task → `mirror_service.Update`) converges on the same queue worker; it is one indirection longer (gocron schedule → `Task.fun` closure → `Update` iterates pending mirrors → `PushToQueue`). Both paths share Steps 7–13 below.

### Step 1: cli sub-command dispatch to the web server's Action

- **From:** `cmd/main.go:115` and `cmd/web.go:44` — `webCmd := newWebCommand()` constructs a `*cli.Command` whose `Action` field is the function value `runWeb`.
- **To:** `cmd/web.go:251` — `runWeb(ctx, cmd)` is invoked by the `urfave/cli/v3` library when it routes the (default) `web` subcommand.
- **Edge type:** `function-value-in-struct-field`
- **Resolution notes:** `Action: runWeb` stores `runWeb` in a struct field on `*cli.Command`. The cli library reads that field and calls it. A static analyzer needs to model field-sensitive points-to (or just track which functions are assigned to the `Action` field of any `*cli.Command`) plus a single library-internal call site that invokes `cmd.Action`.

### Step 2: web bootstrap → installed-mode bring-up

- **To:** `cmd/web.go:166` — `serveInstalled` is the long-running web initialization function.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Static, fully resolved at compile time.

### Step 3: route registration tree built and bound to the HTTP listener

- **From:** `cmd/web.go:228` — `webRoutes := routers.NormalRoutes()` builds the router; `cmd/web.go:229` — `listen(webRoutes, true)` hands it to `http.Server`.
- **To:** `routers/init.go:189` — `r.Mount("/", web_routers.Routes())` mounts the web sub-router, which (transitively) reaches `routers/web/web.go:1147–1150` where `m.Combo("").Get(repo_setting.Settings).Post(web.Bind(...), repo_setting.SettingsPost)` registers `repo_setting.SettingsPost` as the POST handler for `/{username}/{reponame}/settings`.
- **Edge type:** `http-handler-registration`
- **Resolution notes:** The static analyzer needs to model the gitea router DSL (`Group`, `Combo`, `Post`, `Mount`) — each of these stores a passed-in `any` handler value into chi's routing table. Once the analyzer recognizes that values passed to `Methods("POST", pattern, h...)` (router.go:204) end up dispatched on POST requests, the function is fully resolvable. There is no reflection — handlers are ordinary function values stored in a tree.

### Step 4: HTTP request dispatch into the registered handler

- **From:** `modules/web/router.go:219` (`Router.ServeHTTP`) → chi's mux matches POST `/{username}/{reponame}/settings` to the slot populated in Step 3.
- **To:** `routers/web/repo/setting/setting.go:105` — `func SettingsPost(ctx *context.Context)`.
- **Edge type:** `function-value-in-routing-table`
- **Resolution notes:** From a static-analysis standpoint this is essentially the same edge type as Step 3 (function-value-in-struct-field, but inside a tree-shaped routing table). The analyzer that resolved Step 3 already knows the set of functions reachable here.

### Step 5: in-handler `action` string switch

Static-analysis-trivial once the switch is identified.

### Step 7: goroutine launch wrapping the queue push

- **From:** `services/mirror/queue.go:64–68` — `go func() { if err := PushToQueue(syncType, referenceID); err != nil { log.Error(...) } }()`.
- **To:** `services/mirror/queue.go:72` — `func PushToQueue(mirrorType SyncType, referenceID int64) error` (executed on the goroutine).
- **Edge type:** `goroutine-launch` (with `closure-capture` of `syncType`, `referenceID`)
- **Resolution notes:** A static analyzer needs to (a) recognize `go <closure>()` as a separately-scheduled call site whose body still runs in this program, and (b) propagate the captured locals into the closure body. Otherwise statically resolvable — `PushToQueue` is a direct call inside the closure.

### Step 8: queue.Push serializes the request onto the worker queue's base store

- **From:** `services/mirror/queue.go:73` — `mirrorQueue.Push(&SyncRequest{Type: mirrorType, ReferenceID: referenceID})`. `mirrorQueue` is set at `queue.go:43` to `queue.CreateUniqueQueue(..., "mirror", queueHandler)`, instantiated as `*queue.WorkerPoolQueue[*SyncRequest]` (`queue.go:13`).
- **To:** `modules/queue/workerqueue.go:167` — generic method `func (q *WorkerPoolQueue[T]) Push(data T) error`. Body marshals `data` and calls `q.baseQueue.PushItem(q.ctxRun, q.marshal(data))` at `workerqueue.go:175`.
- **Edge type:** `method-call-on-concrete-type` (with `generic-instantiation` on `T = *SyncRequest`)
- **Resolution notes:** `Push` is monomorphized per type parameter; receiver type is statically known. The internal `baseQueue.PushItem` is `interface-method-dispatch` to a persistent or in-memory base implementation, but for the activation-path question this internal hop is a side-channel — what we care about is that the marshalled item then reappears on the consumer side via `popItemByChan`.

### Step 9: queue worker pool moves the item from the base queue to the in-process handler via channels

- **From:** `modules/queue/workergroup.go:295` — `wg.popItemChan, wg.popItemErr = popItemByChan(q.ctxRun, q.baseQueue.PopItem)`. `doRun` (`workergroup.go:287`) and `doDispatchBatchToWorker` (`workergroup.go:48`) push batches onto `q.batchChan` (`workerqueue.go:235`); workers consume them and invoke `doWorkerHandle` at `workergroup.go:92`, whose body calls `q.safeHandler(batch...)` at `workergroup.go:103`.
- **To:** `modules/queue/workerqueue.go:243` — `q.safeHandler` is the closure assigned at queue construction inside `NewWorkerPoolQueueWithContext`.
- **Edge type:** `channel-send-receive` (item value crosses `batchChan`) bridging the producer goroutine (Step 8) to a separately-scheduled worker goroutine started by `graceful.GetManager().RunWithCancel(mirrorQueue)` at `services/mirror/queue.go:47`.
- **Resolution notes:** This is the central asynchrony in the path. A static analyzer must (a) recognize `make(chan []T)` plus the `select { case items := <-q.batchChan: ... }` pattern in `doRun` to thread the data flow, and (b) connect the producer side (`Push` → marshal → `baseQueue.PushItem` → `PopItem` → `popItemByChan` → `batchChan`) to the consumer-side closure. The marshal/unmarshal round-trip preserves type because `T` is fixed by the queue's generic instantiation; with that, all of these channel hops carry `*SyncRequest` end-to-end. Statically resolvable in principle, but requires whole-program channel-flow + generic-instantiation analysis.

### Step 10: safeHandler closure invokes the registered origHandler

- **From:** `modules/queue/workerqueue.go:253–254` — body of `safeHandler` calls `w.origHandler(t...)`. `w.origHandler` is set at `workerqueue.go:242` to the `handler` argument of `NewWorkerPoolQueueWithContext`, which threads back through `CreateUniqueQueue` (`modules/queue/manager.go:98`) to the `queueHandler` argument passed at `services/mirror/queue.go:43`.
- **To:** `services/mirror/queue.go:31` — `func queueHandler(items ...*SyncRequest) []*SyncRequest`.
- **Edge type:** `function-value-in-struct-field` (via constructor parameter)
- **Resolution notes:** `origHandler` is a struct field of type `HandlerFuncT[T]`; its only writers are the `NewWorkerPoolQueueWithContext` constructor and the test helper, so a flow-sensitive analysis can identify the handler value at each callsite of the constructor. For our queue, the writer is `services/mirror/queue.go:43` and the value is `queueHandler` — fully resolvable.

### Summary

- **Path length:** 14 steps from `main()` to the region root.
- **Edge types encountered:** `function-value-in-struct-field`, `direct-function-call`, `http-handler-registration`, `function-value-in-routing-table`, `string-tag-dispatch`, `goroutine-launch`, `closure-capture`, `method-call-on-concrete-type` (with `generic-instantiation`), `channel-send-receive`, `enum-tag-dispatch`.
- **Hardest edge:** Step 9 (queue worker `channel-send-receive`). The producer goroutine writes a marshalled item to a chi-of-channels pipeline (`PushItem` → `popItemByChan` → `batchChan`), and the consumer goroutine reads back through `safeHandler`. Connecting producer to consumer requires whole-program channel-flow analysis combined with generic-type instantiation tracking (T = `*SyncRequest`). The marshal/unmarshal hop is benign because the queue is monomorphic per instantiation, but a context-insensitive analyzer that fans out across all generic uses of `WorkerPoolQueue[T].Push` would lose precision.
- **Static-analysis feasibility:** Yes — every edge is statically resolvable in principle. There is no reflection-based dispatch, no plugin-loaded code, and no runtime-supplied function pointer on this path; the cli `Action` field, the chi router, the queue's `origHandler`, and the typed-int enum dispatch are all writeable by code under analysis. A whole-program analyzer with field-sensitive points-to plus channel-flow plus generic-instantiation tracking can connect `main()` to `StoreMissingLfsObjectsInRepository`. The cron-driven alternative path adds one more `function-value-in-struct-field` edge (gocron's `Task.fun`) but introduces no new category.
