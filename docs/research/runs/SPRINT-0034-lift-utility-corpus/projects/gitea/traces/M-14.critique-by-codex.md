# Trace critique for gitea/M-14 by codex

## Critique of claude's trace

### Path
- **Correct:** partially - The API issue-creation path does reach `DetectWorkflows`, and the service/notifier tail verifies. The trace is not fully connected from entrypoint because it skips `NormalRoutes -> apiv1.Routes()` and the startup registration path `serveInstalled -> InitWebInstalled -> mustInitCtx(actions_service.Init) -> RegisterNotifier`.
- **Minimal:** no - Step 3 (`runHTTP`/`Router.ServeHTTP`) can be collapsed if the path is based on static route registration. After adding the missing API mount and notifier-registration edges, the path is roughly the same shape as the canonical notifier path, not a 10-step path.

### Edge types
| Step | claude's label | Verdict | Suggested label (if different) | Reasoning |
|---|---|---|---|---|
| 1 | `function-value-in-struct-field` | RENAME | `function-valued-field-dispatch` | The edge is not just storage in `cli.Command.Action`; it also requires resolving the later framework call of that function-valued field. |
| 3 | `interface-method-dispatch` | COLLAPSE | - | The `http.Handler` dispatch to `Router.ServeHTTP` is real, but it is unnecessary for the shortest static path when handlers are linked from route registration sites. |
| 4 | `callback-registration` | RENAME | `http-handler-registration` | The mechanism is route-table registration of an HTTP handler, not a generic callback. This label stays codebase-agnostic without naming chi/Gitea. |
| missing before 7 | - | ADD | `callback-registration` | The trace relies on `*actionsNotifier` being in `notifiers`, but does not include `actions_service.Init` at `routers/init.go:174` and `RegisterNotifier(NewNotifier())` at `services/actions/init.go:69`. |
| 7 | `interface-method-dispatch` | RENAME | `interface-method-dispatch-through-registered-slice` | Plain interface dispatch is too weak; the analyzer must combine interface type resolution with value-flow through the global `notifiers` registry. |

### Other notes
Claude's route citation at `routers/api/v1/api.go:1465` and handler/service tail lines are accurate. The unconnected jump from `NormalRoutes` to the API route should pass through `apiv1.Routes()` at `routers/init.go:190` and `routers/api/v1/api.go:865`.

## Critique of gemini's trace

### Path
- **Correct:** partially - The private post-receive push path is real in broad shape, but many citations are wrong: `RunMainApp` starts at `cmd/main.go:157`, `app.Run` is at `cmd/main.go:160`, `runWeb` starts at `cmd/web.go:251`, `private.Routes()` is mounted at `routers/init.go:191`, the post-receive route is at `routers/private/internal.go:68`, `HookPostReceive` starts at `routers/private/hook_post_receive.go:33`, and its `PushUpdates` call is at line 151. The trace also omits startup registration for both the push queue handler and the actions notifier.
- **Minimal:** no - This path is longer than issue/repository creation paths because it adds the asynchronous push queue. Steps 1-3 should be collapsed into one CLI function-valued dispatch edge, and the queue path requires extra registration edges that are not counted.

### Edge types
| Step | gemini's label | Verdict | Suggested label (if different) | Reasoning |
|---|---|---|---|---|
| 2 | `method-call-on-concrete-type` | COLLAPSE | - | `app.Run` alone does not reach `runWeb`; the useful edge is the combined CLI dispatch through the `Action` function field. |
| 3 | `callback-registration` | RENAME | `function-valued-field-dispatch` | `runWeb` is reached via `cli.Command.Action`; the target should be `cmd/web.go:251`, not the field assignment at `cmd/web.go:44`. |
| 6 | `http-handler-registration` | OK | - | The label is right, but the route citation should be `routers/private/internal.go:68` and the handler starts at `routers/private/hook_post_receive.go:33`. |
| missing before 8 | - | ADD | `queue-handler-registration` | `pushQueue.Push` can only be connected to `handler` through initialization: `repo_service.Init` calls `initPushQueue`, which passes `handler` to `queue.CreateSimpleQueue`. |
| 8 | `channel-send-receive` | RENAME | `async-queue-handler-dispatch` | `WorkerPoolQueue.Push` enqueues serialized work to a base queue; workers later call `safeHandler/origHandler`. This is broader than a direct channel send/receive. |
| missing before 11 | - | ADD | `callback-registration` | As in Claude's trace, `actions_service.Init -> RegisterNotifier(NewNotifier())` is required to justify the concrete `*actionsNotifier` receiver. |
| 11 | `interface-method-dispatch` | RENAME | `interface-method-dispatch-through-registered-slice` | The hard part is not just the Go interface call; it is resolving the registered concrete notifier in the package-level slice. |

### Other notes
The notify-helper tail has line drift: `Notify` is at `services/actions/notifier_helper.go:110`, the internal call is at line 113, and `notify` starts at line 118. `DetectWorkflows` is correctly cited at `modules/actions/workflows.go:120`.

## Cross-trace observations

Both foreign traces converge on the same tail: notify facade fan-out, `*actionsNotifier`, `notifyInput.Notify`, internal `notify`, then `DetectWorkflows`. They diverge mainly on event source: Claude picks API issue creation and is closer to a minimal foreign trace, while Gemini picks push handling and pays an avoidable async queue boundary. Both should model startup registrations explicitly; otherwise the interface/queue dispatch edges are asserted rather than derived from the entrypoint path.
