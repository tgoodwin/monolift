# Trace critique for gitea/M-1 by codex

## Critique of claude's trace

### Path
- **Correct:** partially — The main web-command path, `mustInit(webhook.Init)`, queue startup, and `handler -> Deliver` endpoint are real. It skips the `main.go:44 -> NewMainApp -> newWebCommand` construction/wiring edge, and Step 4 cites `cmd/web.go:205` as if it were in `runWeb`; that call is inside `serveInstalled`, reached from `runWeb` at `cmd/web.go:287`.
- **Minimal:** no — `runWeb -> serveInstalled -> InitWebInstalled` should not be silently collapsed; `serveInstalled` is not a trivial forwarding wrapper. Step 10 also combines worker creation, channel handoff, and handler dispatch into one compound edge.

## Critique of gemini's trace

### Path
- **Correct:** partially — The route through `RunMainApp`, `runWeb`, `serveInstalled`, `InitWebInstalled`, `webhook.Init`, and final `handler -> Deliver` exists, but the trace jumps from queue registration directly to `handler`. It also treats `mustInit(webhook.Init)` as a direct call and targets the CLI `Action` assignment instead of the eventual `runWeb` invocation.
- **Minimal:** no — This is over-collapsed rather than shortest: it omits the CLI construction/default-command wiring, `mustInit` invocation, queue handler storage, `go RunWithCancel`, interface dispatch, run loop, worker goroutine/channel handoff, and `safeHandler -> origHandler`.

### Edge types
| Step | gemini's label | Verdict | Suggested label (if different) | Reasoning |
|---|---|---|---|---|
| 2 | `function-value-in-struct-field` | FIX | `function-value-in-struct-field` targeting `runWeb` | The mechanism is right, but `cmd/web.go:44` is the registration site, not the invocation target; `runWeb` begins at `cmd/web.go:251`. The cited default-command line is also wrong: it is `cmd/main.go:144`, not 138. |
| 5 | `direct-function-call` | RENAME | `function-value-argument` | `InitWebInstalled` calls `mustInit(webhook.Init)` at `routers/init.go:159`; `mustInit` invokes its function parameter at line 61. |
| 6 | `callback-registration` | REPLACE | `function-value-argument` + `function-value-in-struct-field` | `callback-registration` is too framework/queue-semantic and hides the Go mechanisms: a function value is passed through generic helpers and stored in `WorkerPoolQueue.origHandler`/`safeHandler`. |

### Other notes
The missing queue execution path is the main issue. Registration at `services/webhook/deliver.go:330` does not by itself reach `services/webhook/webhook.go:78`; the trace must include `deliver.go:334`, `RunWithCancel`, `WorkerPoolQueue.Run/doRun`, worker dispatch over `q.batchChan`, and the `safeHandler/origHandler` calls.

## Cross-trace observations

Both traces converge on the production web-command startup path and the final same-package call from `services/webhook/webhook.go:98` to `services/webhook/deliver.go:153`. They diverge sharply in the queue middle: claude models most of the worker machinery but compresses several mechanisms, while gemini replaces the machinery with a high-level `callback-registration` label. Claude's trace is closest to the canonical minimal path after adding the skipped CLI construction and `serveInstalled` edges and splitting the compound queue step.
