## Summary

- **Path length:** 10 steps.
- **Edge types encountered:** `function-value-in-struct-field`, `direct-function-call`, `interface-method-dispatch`, `callback-registration`, `method-call-on-concrete-type`.
- **Hardest edge:** Step 4 (`callback-registration` for the chi/web route table) and Step 7 (`interface-method-dispatch` over the `notifiers` slice) are the two non-trivial edges. Step 4 is harder in the abstract because it bridges an HTTP-driven control transfer: the analyzer must treat every registered handler as reachable from `Router.ServeHTTP`, even though the per-request URL match is data-dependent. The mitigation is that all route registrations are static literal call expressions (`m.Post(..., repo.CreateIssue)`), so the *set* of reachable handlers is closed and discoverable by scanning the package's init/registration code paths. Step 7 is easier — Go interface dispatch with a closed set of concrete types added via a single registration function (`RegisterNotifier`).
- **Static-analysis feasibility:** Yes — a compiler with whole-program type analysis and a call graph that models (a) function-valued struct fields, (b) callback registrations into a router, and (c) interface dispatch over a registry slice can resolve this entire path. There is no `reflect.Call`, no plugin loading, no runtime function pointer on the path. The only "soft" edge is the URL → handler match inside `Router.ServeHTTP`, but that affects which handlers are reachable per-request, not whether the handler is statically known.
- **Alternative shortest paths considered:**
  - **Push event via API/web push hooks** (`services/repository/push.go:215` → `notify_service.PushCommits` → `actionsNotifier.PushCommits` at `services/actions/notifier.go:541`+): same shape, but routes through an additional `pushQueue` worker (`services/repository/push.go:62-74`), introducing a `goroutine-launch` + `channel-send-receive` pair that this trace avoids.
  - **Pull request creation, release publish, package upload, ref create**: each reaches `DetectWorkflows` through the same Step 7–10 tail. The `notify_service.NewIssue` route was selected for being the most direct (handler → service → notify, no queue intermediary).
  - **`DetectAndHandleSchedules`** (`routers/api/v1/repo/repo.go:1005`) is a shorter handler chain but reaches `actions_module.DetectScheduledWorkflows` (`modules/actions/workflows.go:171`), *not* `DetectWorkflows` — so it does not satisfy this candidate.
