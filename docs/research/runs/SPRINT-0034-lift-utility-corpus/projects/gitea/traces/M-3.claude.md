### Summary

- **Path length:** 7 steps.
- **Edge types encountered:** `struct-literal-field-assignment`, `direct-function-call`, `http-handler-registration`.
- **Hardest edge:** Step 5 (`http-handler-registration`). It requires the analyzer to recognise that `user.UpdateAvatar` flows into a variadic `h ...any` parameter on `(*web.Router).Post`, gets stored in the router's internal handler table, and is later invoked when an HTTP request matches `POST /api/v1/user/avatar`. Connecting an arbitrary HTTP entry point to a specific handler is dynamic, but the *enumeration of reachable handlers* (what a compiler needs for activation) is static — every registration site is a literal package-level function reference.
- **Static-analysis feasibility:** Fully resolvable with whole-program type analysis plus a model of the routing/CLI-dispatch packages. There is no `reflect.Call`, no plugin loader, and no runtime-supplied function pointer on this path — every transition is either a direct call, a struct-field-stored function value set at a literal site, or a function value handed to a registration method. Alternative reachable paths exist (web profile upload at `routers/web/user/setting/profile.go:157`, OAuth signup at `routers/web/auth/oauth.go:316`, LDAP source authenticate/sync at `services/auth/source/ldap/source_authenticate.go:108` and `source_sync.go:144,184`, plus a parallel API path for orgs at `routers/api/v1/org/avatar.go:46` and a sibling repo path through `services/repository/avatar.go:22`); the API user-avatar path traced above is the shortest from `main` to the region root.
