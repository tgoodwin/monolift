## Activation path for gitea/M-15

### Entrypoint

`main.go:39` — `main()` constructs the Gitea CLI application and runs it. The CLI app's default command is the web server, so the shortest mirror-specific activation path goes through the web/API server.

### Step 1: CLI dispatch reaches the web command

- **From:** `main.go:44` — `main()` creates the CLI app with `cmd.NewMainApp(...)`; `main.go:45` then runs it with `cmd.RunMainApp(app, os.Args...)`.
- **To:** `cmd/web.go:44` — `newWebCommand()` stores `runWeb` in the CLI command's `Action` field; `cmd/main.go:144` makes that web command the default command, and `cmd/main.go:160` calls `app.Run(...)`.
- **Edge type:** `function-value-in-command-struct`
- **Resolution notes:** A static analyzer must connect the command struct literal's `Action: runWeb` field to the CLI framework's later invocation of that action. The default-command assignment is also static: `app.DefaultCommand = webCmd.Name`.

### Step 2: Web command starts the installed server path

- **From:** `cmd/web.go:251` — `runWeb` is the web command action.
- **To:** `cmd/web.go:166` — `runWeb` calls `serveInstalled(cmd)` at `cmd/web.go:287` after setup.
- **Edge type:** `direct-function-call`
- **Resolution notes:** This is a normal direct call once the CLI action has been resolved.

### Step 3: Server startup initializes the mirror queue

- **From:** `cmd/web.go:205` — `serveInstalled` calls `routers.InitWebInstalled(...)`.
- **To:** `services/mirror/queue.go:39` — `InitWebInstalled` calls `mirror_service.InitSyncMirrors()` at `routers/init.go:158`, which reaches `StartSyncMirrors`.
- **Edge type:** `startup-initializer-call`
- **Resolution notes:** This edge is a direct startup initialization chain. It matters because later request handlers push work into the global mirror queue created here.

### Step 4: Mirror queue registers its worker callback

- **From:** `services/mirror/queue.go:43` — `StartSyncMirrors` calls `queue.CreateUniqueQueue(..., queueHandler)`.
- **To:** `services/mirror/queue.go:31` — `queueHandler` is the callback stored for later queue processing.
- **Edge type:** `function-value-stored-in-generic-worker`
- **Resolution notes:** `CreateUniqueQueue` forwards the handler through `modules/queue/manager.go:98` and `modules/queue/manager.go:108`; `NewWorkerPoolQueueWithContext` stores it in `w.origHandler` at `modules/queue/workerqueue.go:242` and invokes it through `w.safeHandler` at `modules/queue/workerqueue.go:253`. The queue is launched with `go graceful.GetManager().RunWithCancel(mirrorQueue)` at `services/mirror/queue.go:47`, which calls `rc.Run()` at `modules/graceful/manager.go:77` and reaches `WorkerPoolQueue.Run` at `modules/queue/workerqueue.go:184`.

### Step 5: Web server registers the API mirror-sync route

- **From:** `cmd/web.go:228` — `serveInstalled` builds `routers.NormalRoutes()` before listening with that router at `cmd/web.go:229`.
- **To:** `routers/api/v1/repo/mirror.go:27` — `NormalRoutes` mounts `apiv1.Routes()` at `routers/init.go:190`; the API router registers `POST /mirror-sync` to `repo.MirrorSync` at `routers/api/v1/api.go:1324`.
- **Edge type:** `http-handler-registration`
- **Resolution notes:** The route table is statically constructed. Runtime HTTP input selects the route, but the handler target for the mirror-sync endpoint is statically visible.

### Step 6: API handler enqueues a pull-mirror sync

- **From:** `routers/api/v1/repo/mirror.go:72` — `MirrorSync` calls `mirror_service.AddPullMirrorToQueue(repo.ID)`.
- **To:** `services/mirror/queue.go:51` — `AddPullMirrorToQueue` is reached.
- **Edge type:** `direct-function-call`
- **Resolution notes:** The API handler target is concrete, and this call is direct.

### Step 7: Pull-mirror queue item is constructed in a goroutine

- **From:** `services/mirror/queue.go:52` — `AddPullMirrorToQueue` calls `addMirrorToQueue(PullMirrorType, repoID)`.
- **To:** `services/mirror/queue.go:72` — the goroutine closure launched at `services/mirror/queue.go:64` calls `PushToQueue(syncType, referenceID)` at `services/mirror/queue.go:65`.
- **Edge type:** `goroutine-launch-with-closure-capture`
- **Resolution notes:** The analyzer must carry the constant-like `PullMirrorType` argument and `repoID` through a closure captured by a `go func() { ... }()` launch.

### Step 8: Queue push reaches the registered queue handler

- **From:** `services/mirror/queue.go:73` — `PushToQueue` pushes a `SyncRequest` into the global `mirrorQueue`, including `Type: mirrorType` and `ReferenceID: referenceID`.
- **To:** `services/mirror/queue.go:31` — the worker queue eventually invokes the previously registered `queueHandler`.
- **Edge type:** `queue-work-item-dispatch`
- **Resolution notes:** This is the hardest connection: a static analyzer must link the global queue instance created in `StartSyncMirrors` to later `mirrorQueue.Push(...)` calls, then model the worker's pop/dispatch path. The relevant queue mechanics are visible at `modules/queue/workergroup.go:347`, `modules/queue/workergroup.go:355`, `modules/queue/workergroup.go:358`, `modules/queue/workergroup.go:174`, `modules/queue/workergroup.go:179`, and `modules/queue/workergroup.go:103`, which dispatch popped batches to `q.safeHandler`.

### Step 9: Queue handler dispatches pull mirror requests

- **To:** `services/mirror/mirror.go:17` — `doMirrorSync` is reached.
- **Edge type:** `direct-function-call`
- **Resolution notes:** After the queue callback target is resolved, this edge is direct.

### Step 10: Tagged work item selects pull mirror sync

- **Resolution notes:** The analyzer must propagate the `PullMirrorType` value from `AddPullMirrorToQueue` through the `SyncRequest.Type` field and the queue dispatch. With that field flow, the switch target is statically resolvable.

### Step 11: Pull mirror sync runs the mirror update body

- **To:** `services/mirror/mirror_pull.go:109` — `runSync` is reached.

### Step 12: Mirror update calls the LFS sync region

### Summary

- **Path length:** 12 steps
- **Edge types encountered:** `function-value-in-command-struct`, `direct-function-call`, `startup-initializer-call`, `function-value-stored-in-generic-worker`, `http-handler-registration`, `goroutine-launch-with-closure-capture`, `queue-work-item-dispatch`, `constant-tagged-work-item-switch`, `conditional-direct-function-call`
- **Hardest edge:** Step 8, because the compiler has to connect a global generic queue instance, a captured work item, asynchronous queue push/pop behavior, and a handler function stored during startup.
- **Static-analysis feasibility:** This path is statically resolvable in principle with whole-program type/points-to analysis plus models for CLI action dispatch, HTTP route registration, goroutine closure capture, and queue worker dispatch; I did not find a reflect/plugin boundary on this path.
- **Alternatives:** The scheduled mirror path registers `update_mirrors` at `services/cron/tasks_basic.go:31`, calls `mirror_service.Update` from the cron callback at `services/cron/tasks_basic.go:41`, and enqueues pull mirrors through `services/mirror/mirror.go:92` and `services/mirror/mirror.go:76`. The same region is also called from repository migration at `services/repository/migrate.go:164`, but that is not the mirror LFS sync path for this candidate.
