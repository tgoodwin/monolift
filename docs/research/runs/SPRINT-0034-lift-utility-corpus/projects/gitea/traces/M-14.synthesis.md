## Resolution notes

- **Step 1** (`function-value-in-struct-field`): the `Action` field of a `cli.Command` struct literal stores the function value `runWeb`; the cli framework invokes it indirectly via `app.Run`. Analyzer must propagate function values written into struct fields to their later indirect call site (1:1 resolution, not 1:N).
- **Step 2** (`direct-function-call`, collapsed): `runWeb → serveInstalled → NormalRoutes → listen → runHTTP` is a chain of direct package-internal calls that hands a `*web.Router` to `http.Server.Serve`; the per-request `http.Handler.ServeHTTP` virtual call is statically resolvable to `(*Router).ServeHTTP` by concrete-type analysis. Collapsed into one edge because no step changes dispatch shape.
- **Step 3** (`callback-registration`): every `m.Combo/Get/Post/...` registration site stores a function value into the chi-backed route table. Analyzer must scan all registration sites (closed set, all literal call expressions in `routers/**`) and treat each registered handler as reachable from `(*Router).ServeHTTP`. The per-request URL→handler match inside the router is data-dependent but does not affect static reachability of the registered handler. **Precondition for this edge** is that the route group containing `/api/v1/repos/.../issues` is mounted at `routers/init.go:190` (`r.Mount("/api/v1", apiv1.Routes())`).
- **Step 6** (`interface-method-dispatch`): the receiver is `notify_service.Notifier`. The concrete `*actionsNotifier` is appended to the package-level `notifiers` slice exclusively via `RegisterNotifier` (`services/notify/notify.go:23`).
