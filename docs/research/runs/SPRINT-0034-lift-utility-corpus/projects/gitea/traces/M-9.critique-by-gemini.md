### Path

- **Minimal:** yes — However, it is *too* minimal. Step 1 collapses `main` -> `RunMainApp` -> `app.Run` -> `runWeb`, which hides the complexity of the CLI dispatch logic that a compiler must resolve.

### Edge types
| Step | codex's label | Verdict | Suggested label (if different) | Reasoning |

| 4 | `http-subrouter-mount` | RENAME | `direct-function-call` | The edge is a call to `CommonRoutes()` whose return value is then passed to `Mount`. A static analyzer reaches the region via the constructor call. |
| 5 | `http-handler-registration-through-path-matcher` | RENAME | `http-handler-registration` | Unnecessarily verbose and framework-specific. |

### Other notes
- Codex's Step 3 label `direct-function-call-with-handler-result` is a good observation of the data flow (returning a router), but the edge itself is just a function call.

## Cross-trace observations

- **Convergence:** All traces agree on the sequence from `NormalRoutes` through `CommonRoutes` to the `UploadPackageFile` handler and finally to the region root.
- **Divergence:** The traces diverge on how to represent "non-direct" edges. Claude uses a data-flow resolution step as a path step (Step 2), while Codex aggressively collapses the CLI entry sequence. Gemini's trace (my own) maintains path continuity by representing the dispatch as the edge between the framework caller and the registered callee.
- **Canonical Path:** The canonical minimal path should include the CLI dispatch and the HTTP registration. Claude's inclusion of a "dispatch" step for HTTP is the most thorough for runtime modeling, but Codex's labels are the most descriptive of Gitea's specific routing abstractions.
