### Summary

- **Path length:** 6 steps
- **Edge types encountered:** `function-value-in-struct-field`, `direct-function-call`, `http-handler-registration`
- **Hardest edge:** Step 5 (`http-handler-registration`). Step 1 has the same shape — a function value stored in a struct field and dispatched by a framework — but the cli command tree is small and built in a single constructor, so once the analyzer models `Action` it can resolve the entrypoint with field-sensitive points-to. Step 5 is harder because the route handler is registered through several layers of variadic `...any` adapters (`r.Put → r.Methods → wrapMiddlewareAndHandler`) that erase the function's static type and store it inside chi's runtime trie keyed by method+path. To prove that `PUT /api/packages/.../upload` reaches `debian.UploadPackageFile`, the analyzer must (a) model the routing API as a table store/lookup, (b) track the URL prefix accumulated by nested `r.Group` closures (`/{username}` at line 130, then `/debian`, `/pool/{distribution}/{component}`), and (c) resolve the function identity through the `...any` boxing.
- **Static-analysis feasibility:** The whole path is statically resolvable in principle — every function identity is a named package-level symbol and there is no `reflect.Call`, plugin loader, or runtime-determined function pointer. A whole-program call-graph builder that models two patterns (cli `Action` field dispatch and HTTP routing-table registration) can connect `main` to the region root without any dynamic gap.
