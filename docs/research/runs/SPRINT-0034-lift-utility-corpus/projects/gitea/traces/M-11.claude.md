### Summary

- **Path length:** 8 steps.
- **Edge types encountered:** `direct-function-call`, `method-call-on-concrete-type`, `function-value-in-struct-field`, `function-value-passed-as-argument`.
- **Hardest edge:** Step 3 (the urfave/cli `Action`-field dispatch). The analyzer has to model the framework's internal dispatch — `(*cli.Command).Run` reads the matched subcommand's `Action func(ctx, cmd) error` field and calls it — and tie that to the concrete function (`runWeb`) installed via the struct literal in `newWebCommand`. Every subsequent edge is either a directly named call or a single-hop higher-order call inside this codebase, so the cli boundary is the only place that requires reasoning about a third-party library's invocation semantics.
- **Static-analysis feasibility:** Fully resolvable. Whole-program type analysis plus field-sensitive tracking of function values (for the cli `Action` field and for `mustInit`'s `fn` parameter) is sufficient — no `reflect.Call`, plugins, channels carrying functions, or runtime-determined function pointers appear on the path. Alternative entrypoints exist (e.g. integration tests via `tests/test_utils.go:127`, and `serveInstall` runs an installer flow that does *not* call `InitWebInstalled`), but the `web` subcommand is the shortest and only production binary path that activates this region.
