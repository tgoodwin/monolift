# Critique of gitea drafts by codex

## Verdicts on claude's draft

| Candidate ID | Verdict | One-paragraph reasoning |
|---|---|---|
| C-1 (Webhook delivery worker) | KEEP | rubric criterion satisfied: latency / failure. This is the same strongest region as codex C-1: queue-backed, bursty, one webhook task per unit, durable DB status updates, and outbound HTTP latency that can dominate the call. |
| C-2 (Repository archive generator) | KEEP | rubric criterion satisfied: compute envelope. This matches codex C-2 and is a large, bounded archive/bundle generation worker with queue/cached readiness semantics; the repo filesystem and pipe-to-storage topology are real risks but not disqualifiers if storage is virtualized. |
| C-3 (Mirror pull sync) | KEEP | rubric criterion satisfied: load profile. This matches codex C-5: mirror jobs are periodic but highly skewed by repo size and upstream churn, and the git/LFS/network work is already off the request path. |
| C-4 (Code indexer per-repo index) | KEEP | rubric criterion satisfied: latency / failure. This matches codex C-6: a queue worker over repo IDs with substantial git diff/blob/indexer work; backend choice matters, but ES mode and shared git storage make the lift story coherent. |
| C-5 (Issue indexer per-item handler) | KEEP | rubric criterion satisfied: latency / failure. This was not in my draft but passes: it is queue-backed, has explicit retry behavior, and can become heavy for issues with large comment/label histories even though common-case items are small. |
| C-6 (Mailer queue worker) | MODIFY | The lift target is real, but the draft names an anonymous queue closure rather than a named callable region. Reframe around the named mail send path, either `evaluation/gitea/services/mailer/sender/sender.go:17` (`send`) plus its SMTP implementation at `evaluation/gitea/services/mailer/sender/smtp.go:27`, with the queue closure at `evaluation/gitea/services/mailer/mailer.go:48` only as the caller. |
| C-7 (PR merge-and-push) | DROP | This falls below the rubric threshold on load profile, coherent unit, and state independence, and is structurally worse than codex C-3 (pull-request mergeability check). It is destructive, hook-coupled, temp-repo/filesystem-heavy merge machinery on a correctness-sensitive path; the background mergeability checker captures the expensive PR/git computation with a cleaner failure model. |
| C-8 (Repository migration) | KEEP | rubric criterion satisfied: compute envelope. This matches codex C-4: source-host API/git fetch plus uploader work can run for minutes and varies dramatically by repo and issue/PR history; the broad dependency closure is a risk, but the task shape is appropriate. |
| C-9 (Avatar image processing) | KEEP | rubric criterion satisfied: coherent unit. The image transform is a pure `[]byte -> []byte` CPU/memory region, and the inner `processAvatarImage` note is useful; load is less compelling than queue workers but still spikable during onboarding or LDAP/avatar sync. |
| C-10 (Diff parsing / ParsePatch) | MODIFY | The target is real but too narrowly framed. Replace `ParsePatch` with the adjacent render-level region from codex C-11, `evaluation/gitea/services/gitdiff/gitdiff.go:1333` (`GetDiffForRender`), because it owns git diff execution, patch parsing, attribute checks, generated/vendor detection, and full-file highlighting; `evaluation/gitea/services/gitdiff/gitdiff.go:631` is only the parser substep. |
| C-11 (Push-update worker) | KEEP | rubric criterion satisfied: load profile. This is a credible queue-backed region: push storms can produce large commit walks and downstream enqueue fan-out, and the unit is already a batch of value-shaped push update options. The git repository dependency keeps it medium-risk rather than clean. |
| C-12 (Markdown render / RenderString) | MODIFY | The candidate is useful but the root should be markdown-specific and buffer-return oriented. Use `evaluation/gitea/modules/markup/markdown/markdown.go:186` (`render`) or the string wrapper at `evaluation/gitea/modules/markup/markdown/markdown.go:270`, not the generic dispatcher at `evaluation/gitea/modules/markup/render.go:193`; latency/failure should stay `maybe`, not an unconditional pass. |

## Overlooked

None.

## Overall observations

The drafts converge cleanly on webhook delivery, archive generation, diff/markup rendering, and repo indexing as useful regions. Claude is stronger on queue-shaped operational seams and state-coupling caveats, but sometimes names anonymous closures or includes a too-risky PR merge path. Gemini finds useful pure-CPU regions, especially avatar and language stats, but is less rigorous about exact file:line citations and tends to treat CPU cost as sufficient even when latency/failure or region granularity should be downgraded.
