### Summary

- **Path length:** 8 steps (entrypoint → region root).
- **Edge types encountered:** `direct-function-call`, `struct-literal-field-assignment`, `http-handler-registration`, `method-value-as-callback-registration`, `interface-method-dispatch`, plus an implicit `goroutine-launch` for the HTTP server loop at `internal/http/server/server.go:260`.
- **Hardest edge:** Step 7 (`interface-method-dispatch` through the chain of nested `http.ServeMux` instances and middleware wrappers). Resolving it requires the analyzer to model `(*http.ServeMux).Handle` / `HandleFunc` as recording entries in a pattern table and `(*ServeMux).ServeHTTP` as looking up that table — i.e., stdlib-aware reasoning rather than ordinary type-flow.
- **Alternative paths considered (not taken):**
  - `POST /v1/feeds/{feedID}/entries/import` → `(*handler).importFeedEntryHandler` (`entry_handlers.go:401`) — same length, equivalent shape.
  - Worker/scheduler path: `cli.startDaemon` → `runScheduler` → `worker.Pool` goroutines → `reader/handler.RefreshFeed` → `processor.ProcessFeedEntries` (`processor.go:165`) — strictly longer (adds scheduler ticking, channel-send-receive of jobs into the worker pool, and an extra layer through `reader/handler`).
  - UI scraper: `ui.Serve` mux → `(*handler).fetchContentEntry` → `processor.ProcessEntryWebPage` → `SanitizeHTML` (`processor.go:221`) — comparable to the API path but one step longer.
- **Static-analysis feasibility:** Fully resolvable in principle. Every edge is statically determinable with whole-program type analysis plus stdlib-aware modeling of `net/http` (pattern→handler tables, `Handler.ServeHTTP` dispatch, `go srv.ListenAndServe()`). No `reflect`, plugin loading, or runtime-supplied function pointers appear on this path.
