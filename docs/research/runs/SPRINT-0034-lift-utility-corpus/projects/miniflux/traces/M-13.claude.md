### Summary

- **Path length:** 7 steps.
- **Edge types encountered:** `direct-function-call`, `struct-literal-field-assignment`, `interface-method-dispatch` (on `http.Handler`, implicit at Steps 4–5), `http-handler-registration`, `method-value-bind`.
- **Hardest edge:** Step 6 (`http-handler-registration` + `method-value-bind`). A naive call-graph walk from `main` would never visit `(*handler).fetchContent` — the function value is dropped into a routing table and only invoked when the listener dispatches a matching request. A compiler must (a) recognize `mux.HandleFunc(pattern, fn)` as a registration edge that adds `fn` to the reachable set of any handler that owns `mux`, and (b) bind the method-value `handler.fetchContent` to the concrete `*handler` constructed at `ui.go:26` so the receiver type is known. Once those two patterns are modeled the rest of the path is direct calls.
- **Static-analysis feasibility:** Fully feasible. Every edge resolves with standard Go SSA/call-graph analysis plus a small amount of framework-aware bookkeeping for `(*http.ServeMux).HandleFunc`. No reflection, no plugins, no user-supplied function pointers anywhere on the path. The only "dynamic" hop is the stdlib router's pattern-keyed dispatch, which is statically observable from the registration site itself.
