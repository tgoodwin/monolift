A static analyzer must (a) recognise `*http.ServeMux.HandleFunc` as a registration sink that promotes its argument to a reachable handler, (b) bind the method value `handler.fetchContent` to the concrete receiver `*handler` so the body is identified, and (c) understand that `http.Server.ListenAndServe` will eventually dispatch on the registered `http.Handler` via `ServeHTTP`. ### Summary

- **Path length:** 8 steps.
- **Edge types encountered:** `direct-function-call`, `struct-literal-field-assignment`, `http-handler-registration` (composed of `method-value-binding` + pattern-keyed `http.Handler`-interface dispatch).
- **Hardest edge:** Step 6 (`http-handler-registration`). All other hops are direct, package-qualified function calls. Step 6 is the only place where the call target is bound through a registration table rather than syntactically: a static analyzer must model `(*http.ServeMux).HandleFunc(pattern, fn)` as "`fn` is reachable whenever the enclosing `http.Server` is started" and bind the method value `handler.fetchContent` to the `*handler` instance constructed at `ui.go:26`. Once the analyzer recognises this stdlib registration shape, the resolution is fully static — pattern strings and method values are all known at compile time.
- **Static-analysis feasibility:** Fully feasible. The only non-trivial edge is `(*http.ServeMux).HandleFunc`, which is a well-known stdlib registration sink amenable to standard handler-aware call-graph extensions (analogous to how callers model `reflect`-free framework registries). No `reflect.Call`, no plugin loading, no runtime-computed function pointers anywhere on this path.
- **Alternative paths (not the shortest, listed for completeness):**
  - **REST API path (same length):** `main` → `cli.Parse` → `startDaemon` → `StartWebServer` → `newRouter` → `api.NewHandler(store, pool)` (`routes.go:37`) → `(*handler).fetchContentHandler` (`internal/api/entry_handlers.go:486`) → `processor.ProcessEntryWebPage` → `scraper.ScrapeWebsite`. Identical hop count and edge-type profile to the UI path; the only difference is the sub-mux owner.
  - **CLI -refresh-feeds path:** `main` → `cli.Parse` → `refreshFeeds` (`cli.go:239`) → `goroutine-launch` + `closure-capture` + `channel-send-receive` (`refresh_feeds.go:47-69`) → `feedHandler.RefreshFeed` (`handler.go:207`) → `processor.ProcessFeedEntries` (`handler.go:329`) → `scraper.ScrapeWebsite` at `processor.go:111`. Adds the goroutine + channel hops in exchange for losing the `http-handler-registration` hop; comparable difficulty.
  - **Daemon worker pool:** `main` → `cli.Parse` → `startDaemon` → `worker.NewPool(...)` → goroutine bodies inside the worker pool dispatch `feedHandler.RefreshFeed` (`internal/worker/worker.go:40`) → `ProcessFeedEntries` → `ScrapeWebsite` (`processor.go:111`). Longest of the four; combines the daemon-bringup chain with the goroutine-launch + channel-receive hops.

  The UI handler path traced above is tied for shortest with the REST API path. Both reach the same `ScrapeWebsite` symbol at `scraper.go:21` and both share the same single non-direct edge (`http-handler-registration`); the UI path is presented as the canonical trace.
