### Summary

- **Path length:** 5 steps.
- **Edge types encountered:** `direct-function-call`, `goroutine-launch`, `closure-capture`, `channel-send-receive`.
- **Hardest edge:** Step 3 (`goroutine-launch` + `closure-capture`). The call itself is trivial because the closure body is a literal at the `go` site, but the *fork* means a naive single-threaded call-graph walk from `main` would never visit `RefreshFeed`. A compiler must recognise `go <funclit>(args)` as a reachability edge into the literal's body and propagate the captured-variable types into that body's scope. Once that is done, the rest is direct calls.
- **Static-analysis feasibility:** Fully feasible. Every edge resolves with standard Go SSA/call-graph analysis — package-qualified calls plus goroutine-as-extra-entry-point handling, with no reflection, plugins, or runtime function pointers. The channel hop in Step 4 is informational, not a dispatch decision.
- **Alternative paths (not the shortest, listed for completeness):**
  - **Daemon worker pool:** `main` → `cli.Parse` → `startDaemon(store)` (cli/cli.go:248) → `internal/worker` pool → `Worker.Run` → `feedHandler.RefreshFeed` at `internal/worker/worker.go:40`. Adds a daemon-bringup step, a worker-struct method dispatch on a concrete type, and a goroutine launch.
  - **HTTP API:** `main` → `cli.Parse` → `startDaemon` → HTTP server → router → `(*handler).refreshFeedHandler` at `internal/api/feed_handlers.go:67`. Adds `http-handler-registration` plus `interface-method-dispatch` (`http.Handler`) on top of the daemon path.
  - **HTML UI:** symmetric to the API path via `internal/ui/feed_refresh.go:21`.

  All three reach the same `RefreshFeed` symbol at `handler.go:207` via a `direct-function-call` at the leaf, but the CLI path traced above is the shortest and the only one that does not require resolving `http.Handler`-style interface dispatch.
