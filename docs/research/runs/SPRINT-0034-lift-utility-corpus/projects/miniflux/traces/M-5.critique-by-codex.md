# Trace critique for miniflux/M-5 by codex

## Critique of claude's trace

### Path
- **Correct:** partially — The daemon/API feed-creation route is real, and the cited project lines mostly match the source. It elides the actual `http.Server`/`ServeMux` dispatch boundary, so it is more a reachability path through handler registration than a complete activation trace.
- **Minimal:** no — The CLI `--refresh-feeds` route reaches `RefreshFeed(..., false)` and then the icon helper in fewer steps. Within the HTTP route, Step 4 also combines the direct `newRouter` construction call with a separate handler-field callback fact.

### Edge types
| Step | claude's label | Verdict | Suggested label (if different) | Reasoning |
|---|---|---|---|---|
| 2 | `direct-function-call` | RENAME | `condition-guarded-direct-call` | `startDaemon(store)` is the default/fallthrough branch after earlier flag branches return. The target is static, but the path is mode-guarded. |
| 3 | `direct-function-call` | RENAME | `condition-guarded-direct-call` | `StartWebServer` is guarded by `config.Opts.HasHTTPService()` at `daemon.go:37`. |
| 4 | `struct-literal-field-assignment` | SPLIT | `direct-function-call`; separately `handler-field-callback-registration` | The cited edge to `newRouter` is an immediate direct call inside a struct literal. Storing its result in `http.Server.Handler` is a later callback-dispatch fact. |
| 5 | `http-handler-registration` | SPLIT | `condition-guarded-direct-call`; separately `callback-registration` | The edge to `api.NewHandler` is a direct call guarded by `HasAPI()`. The `ServeMux.Handle` storage is real, but should be a separate framework-agnostic callback-registration edge. |
| 6 | `http-handler-registration` | RENAME | `method-value-callback-registration` | The key mechanism is a bound method value stored in a callback table. Avoid baking `http` into the schema label. |
| 8 | `method-call-on-concrete-type` | OK | — | The chained constructor returns `*iconChecker`, so the method dispatch is monomorphic. |

### Other notes
Claude's alternative-path summary incorrectly treats the CLI one-shot path as longer; it is the closest minimal path, though it requires modeling a local goroutine and channel. Prefer labels like `callback-registration`, `callback-dispatch`, and `method-value-callback-registration` over `http-handler-registration` for schema portability.

## Critique of gemini's trace

### Path
- **Correct:** partially — It follows the real CLI refresh path, but skips the `jobQueue` send/receive needed to activate the worker-loop call at `refresh_feeds.go:56`. Two line citations drift: `Parse` begins at `cli.go:40`, and the worker receive loop is at `refresh_feeds.go:49`, not line 51.
- **Minimal:** no — The apparent 6-step path is short because it omits the channel edge. The minimal complete CLI path has a `channel-send-receive` step between goroutine launch and `RefreshFeed`.

### Edge types
| Step | gemini's label | Verdict | Suggested label (if different) | Reasoning |
|---|---|---|---|---|
| 2 | `direct-function-call` | RENAME | `condition-guarded-direct-call` | `refreshFeeds(store)` is reached only under the `flagRefreshFeeds` branch at `cli.go:238-239`. |
| 3 | `goroutine-launch` | RENAME | `goroutine-launch-of-closure` | The `go` statement targets a function literal that captures `store` and `jobQueue`; closure modeling is the relevant static-analysis work. |
| between 3 and 4 | — | ADD | `channel-send-receive` | Jobs are sent at `refresh_feeds.go:68` and received by `for job := range jobQueue` at line 49 before the call at line 56 is reachable. |
| 5 | `method-call-on-concrete-type` | OK | — | The receiver comes from `icon.NewIconChecker` at `handler.go:356`; the `false` argument from line 56 selects this branch. |
| 6 | `method-call-on-concrete-type` | OK | — | Same concrete receiver; the `HasFeedIcon` runtime guard does not obscure the static target. |

### Other notes
Gemini's summary should include `channel-send-receive` among encountered edge types, and the hardest edge is the goroutine plus channel handoff, not goroutine launch alone.

## Cross-trace observations

The traces diverge on entry mode: claude uses daemon HTTP feed creation, while gemini uses CLI refresh. They converge only at the icon-checker region, with claude taking the direct create-feed update call and gemini taking the refresh-time missing-icon helper. Gemini is closer to the canonical minimal path, but it is incomplete without the channel edge; claude is a valid alternate path but longer and less schema-clean in its HTTP labels.
