## Activation path for miniflux/M-6

### Entrypoint

`main.go:10` — `func main()` is the binary entrypoint. It does nothing but delegate to `cli.Parse()`, which dispatches on command-line flags to either run a one-shot maintenance task or start the long-running daemon.

The shortest static path to `parser.ParseFeed` is the `--refresh-feeds` CLI flag path: a single direct call to `cli.refreshFeeds`, which spawns a worker-pool goroutine that calls `handler.RefreshFeed`, which calls `parser.ParseFeed`.

### Step 1: `main` calls into the CLI dispatcher

- **From:** `main.go:11` — `main()` invokes the only function in its body.
- **To:** `internal/cli/cli.go:40` — `func Parse()`, the package-level CLI dispatcher.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Fully resolved at compile time: a named, exported, non-method function reference. No type analysis required.

### Step 2: CLI dispatcher branches to the refresh-feeds command

- **From:** `internal/cli/cli.go:239` — inside `Parse()`, the `if flagRefreshFeeds { refreshFeeds(store); return }` branch fires when the `-refresh-feeds` flag is set.
- **To:** `internal/cli/refresh_feeds.go:17` — `func refreshFeeds(store *storage.Storage)`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Same-package, statically named function. The dispatch is gated by a runtime boolean (`flagRefreshFeeds`), but the call target itself is fully known to the compiler — flag-gated control flow does not change static reachability.

### Step 3: `refreshFeeds` launches a worker goroutine

- **From:** `internal/cli/refresh_feeds.go:47` — `go func(workerID int) { ... }(i)` inside the per-worker `for` loop spawns N copies of an inline anonymous function.
- **To:** `internal/cli/refresh_feeds.go:47-64` — the body of that anonymous function (the goroutine entry).
- **Edge type:** `goroutine-launch`
- **Resolution notes:** The goroutine target is an inline function literal, so the compiler can resolve it without any indirection — there is no function value being passed around. The closure captures `store` and `jobQueue` from the enclosing scope; both are statically typed and require no further resolution. (The `for job := range jobQueue` channel receive that follows transports `model.Job` *data* but does not redirect call resolution — `RefreshFeed` is named directly in the goroutine body, so the channel is not on the call-resolution path.)

### Step 4: Worker goroutine calls the feed-refresh handler

- **From:** `internal/cli/refresh_feeds.go:56` — inside the goroutine body, `feedHandler.RefreshFeed(store, job.UserID, job.FeedID, false)`.

- **Edge type:** `direct-function-call`
- **Resolution notes:** `feedHandler` is a package import alias for `miniflux.app/v2/internal/reader/handler`; the call target is a named exported function. Static.

### Step 5: `RefreshFeed` parses the fetched feed body

- **Resolution notes:** Named exported function in the `parser` package, called by qualified identifier. The arguments include an `io.ReadSeeker` interface, but that affects what `ParseFeed` *does internally*, not how this call edge is resolved.

### Region root reached

`internal/reader/parser/parser.go:20` — `ParseFeed`

### Summary

- **Path length:** 5 steps
- **Edge types encountered:** `direct-function-call`, `goroutine-launch`
- **Hardest edge:** Step 3 (the `goroutine-launch`). Even so, it is straightforward to resolve because the goroutine target is an inline function literal rather than a function value pulled from a channel, struct field, or interface — the compiler sees the body in place. The only subtlety is the implicit "fan-out" (N copies of the same closure run concurrently), which matters for instrumentation semantics but not for call-graph reachability.
- **Static-analysis feasibility:** Fully feasible. Every edge is a directly-named call or an inline `go` of a function literal. No interfaces, no reflection, no plugin loading, and no function values stored in fields or channels are on this path. A whole-program call-graph builder with basic Go semantics can connect `main` to `ParseFeed` without dynamic-dispatch reasoning.

**Alternate paths (not chosen, all longer):** `ParseFeed` is also reached from (a) the long-running daemon's worker pool started by `cli.startDaemon` → `worker.Pool` (similar goroutine+channel pattern but with one extra layer of indirection through `worker.NewWorkerPool`); (b) HTTP handlers in `internal/ui/subscription_submit.go:91`, `internal/ui/subscription_choose.go`, `internal/ui/feed_refresh.go`, `internal/api/feed_handlers.go`, and `internal/googlereader/handler.go`, all of which require traversing HTTP route registration (`mux.Handle`-style `http-handler-registration` edges) and per-request handler dispatch before reaching `feedHandler.CreateFeed` / `RefreshFeed` / `CreateFeedFromSubscriptionDiscovery`. These paths add 4–6 additional steps each over the CLI path above.
