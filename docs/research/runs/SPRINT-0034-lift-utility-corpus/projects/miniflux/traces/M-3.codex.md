## Activation path for miniflux/M-3

Paths below are relative to `evaluation/miniflux/`. The minimal path I found is the `--refresh-feeds` batch mode path; it reaches the sanitizer with fewer static edges than the default daemon HTTP routing path.

### Entrypoint

`main.go:10` — `main()` starts the binary by calling the CLI parser at `main.go:11`.

### Step 1: Enter CLI parser

- **From:** `main.go:11` — `main()` calls `cli.Parse()`.
- **To:** `internal/cli/cli.go:40` — `Parse()` parses flags, initializes configuration/storage, and dispatches to command modes.
- **Edge type:** `direct-function-call`
- **Resolution notes:** The callee is a package-qualified function call with no interface or function-value indirection.

### Step 2: Dispatch refresh command

- **From:** `internal/cli/cli.go:239` — when `flagRefreshFeeds` is set, `Parse()` calls `refreshFeeds(store)`.
- **To:** `internal/cli/refresh_feeds.go:17` — `refreshFeeds()` starts a worker batch over feeds selected from storage.
- **Edge type:** `cfg-guarded-direct-function-call`
- **Resolution notes:** The target is statically explicit, but the edge is guarded by command-line flag state. A conservative activation analysis can include this branch without resolving the runtime flag value.

### Step 3: Launch per-feed worker closure

- **From:** `internal/cli/refresh_feeds.go:47` — `refreshFeeds()` launches a function literal with `go func(workerID int) { ... }(i)`.
- **To:** `internal/cli/refresh_feeds.go:49` — the launched closure ranges over `jobQueue` and performs feed refresh work.
- **Edge type:** `goroutine-launch-of-closure`
- **Resolution notes:** The analyzer must treat the function literal passed to `go` as an asynchronously reachable function body. The channel controls which job values reach the loop, but the callable body and its later function call are statically visible.

### Step 4: Refresh one feed

- **From:** `internal/cli/refresh_feeds.go:56` — the worker closure calls `feedHandler.RefreshFeed(store, job.UserID, job.FeedID, false)`.
- **To:** `internal/reader/handler/handler.go:207` — `RefreshFeed()` fetches and parses the feed, then prepares updated entries.
- **Edge type:** `direct-function-call`
- **Resolution notes:** The import alias names a concrete package function. The analyzer only needs normal import resolution.

### Step 5: Process refreshed entries

- **From:** `internal/reader/handler/handler.go:329` — after parsing an updated feed, `RefreshFeed()` assigns `updatedFeed.Entries` and calls `processor.ProcessFeedEntries(...)`.
- **To:** `internal/reader/processor/processor.go:27` — `ProcessFeedEntries()` applies filtering, scraping, rewriting, and final content processing for entries.
- **Edge type:** `direct-function-call`
- **Resolution notes:** This is another package-qualified concrete function call. The call is nested under feed-modified control flow, but the callee is statically resolved.

### Step 6: Sanitize processed entry content

- **From:** `internal/reader/processor/processor.go:165` — `ProcessFeedEntries()` calls `sanitizer.SanitizeHTML(...)` after rewrite/filter processing.
- **To:** `internal/reader/sanitizer/sanitizer.go:217` — `SanitizeHTML()` is the region root.
- **Edge type:** `direct-function-call`
- **Resolution notes:** The sanitizer call is package-qualified and fully concrete. No interface dispatch, reflection, or function-value resolution is involved at this final edge.

### Region root reached

`internal/reader/sanitizer/sanitizer.go:217` — `SanitizeHTML(baseURL, rawHTML string, sanitizerOptions *SanitizerOptions) string`

### Summary

- **Path length:** 6 steps
- **Edge types encountered:** `direct-function-call`, `cfg-guarded-direct-function-call`, `goroutine-launch-of-closure`
- **Hardest edge:** Step 3, because the compiler analysis must include a function literal launched in a goroutine and connect its closure body back to the enclosing `refreshFeeds()` activation. The job channel affects data flow but not the static identity of the callee reached from the closure.
- **Static-analysis feasibility:** The whole path is statically resolvable with ordinary import/type resolution, CFG branch inclusion, and conservative goroutine call-graph construction; I found no reflect/plugin/runtime function-pointer boundary on this minimal path.

Longer alternatives also reach the same region. The daemon HTTP route goes through `internal/cli/cli.go:248`, `internal/cli/daemon.go:38`, `internal/http/server/server.go:49`, `internal/http/server/routes.go:37`, and API registrations such as `internal/api/api.go:55` or `internal/api/api.go:60`, then direct sanitizer calls at `internal/api/entry_handlers.go:401` or `internal/api/entry_handlers.go:314`. The scheduler path goes through `internal/cli/daemon.go:33`, `internal/cli/scheduler.go:18`, `internal/cli/scheduler.go:47`, `internal/worker/pool.go:41`, and `internal/worker/worker.go:40` before reaching `RefreshFeed()`. These are longer than the selected batch-refresh path.
