## Activation path for miniflux/M-9

### Entrypoint

`main.go:10` — `func main()` is the binary entrypoint. It immediately delegates to `cli.Parse()`, which parses flags and (in the absence of one-shot flags like `-refresh-feeds`) starts the long-running daemon.

### Step 1: main delegates to the CLI driver

- **From:** `main.go:11` — `main()` calls `cli.Parse()`.
- **To:** `internal/cli/cli.go:40` — `func Parse()` (package-level function).
- **Edge type:** `direct-function-call`
- **Resolution notes:** Fully resolved at compile time; `cli.Parse` is a package-level identifier with no receiver and no indirection.

### Step 2: CLI driver starts the daemon

- **From:** `internal/cli/cli.go:248` — at the bottom of `Parse()`, after flag-driven branches return, control falls through to `startDaemon(store)`.
- **To:** `internal/cli/daemon.go:23` — `func startDaemon(store *storage.Storage)`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Same package, package-level function. Trivially resolvable.

### Step 3: Daemon brings up the HTTP server

- **From:** `internal/cli/daemon.go:38` — `httpServers = server.StartWebServer(store, pool)` (gated by `config.Opts.HasHTTPService()` at runtime, but statically reachable).
- **To:** `internal/http/server/server.go:24` — `func StartWebServer(store *storage.Storage, pool *worker.Pool) []*http.Server`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Cross-package package-level call; resolvable from the import graph.

### Step 4: Server constructs the router

- **From:** `internal/http/server/server.go:49` — inside the `for _, t := range targets` loop, the `http.Server` literal sets `Handler: newRouter(store, pool)`.
- **To:** `internal/http/server/routes.go:18` — `func newRouter(store *storage.Storage, pool *worker.Pool) http.Handler`.
- **Edge type:** `direct-function-call` (return value flows into a `struct-literal-field-assignment` on `http.Server.Handler`, but the call edge itself is direct).
- **Resolution notes:** `newRouter` is package-local. The result is stored as an `http.Handler`-typed field on `http.Server`, but for activation-path resolution we only care that `newRouter` is invoked synchronously here.

### Step 5: Router mounts the UI subtree

- **From:** `internal/http/server/routes.go:46` — `appMux.Handle("/", ui.Serve(store, pool))`. `ui.Serve` is invoked eagerly to build the UI's `http.Handler`; the resulting handler is then registered under `/` on `appMux`.
- **To:** `internal/ui/ui.go:17` — `func Serve(store *storage.Storage, pool *worker.Pool) http.Handler`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Direct cross-package call. Note: `appMux.Handle` is itself a method-call on a concrete `*http.ServeMux`, but it is a sibling registration call, not on the path to `SendEntry` — what matters is that `ui.Serve` runs and registers the save-entry route inside the UI mux it returns.

### Step 6: UI registers `saveEntry` as the handler for `POST /entry/save/{entryID}`

- **From:** `internal/ui/ui.go:104` — `mux.HandleFunc("POST /entry/save/{entryID}", handler.saveEntry)`. Here `handler` is the local `*handler` constructed at `ui.go:26`, and `handler.saveEntry` is a method value: a closure that binds the receiver and exposes the method as a `func(http.ResponseWriter, *http.Request)`.
- **To:** `internal/ui/entry_save.go:14` — `func (h *handler) saveEntry(w http.ResponseWriter, r *http.Request)`.
- **Edge type:** `http-handler-registration` (concretely: a `method-value-as-callback-registration` — the bound method is stored inside `*http.ServeMux` keyed by the route pattern, to be invoked later when the mux matches a request).
- **Resolution notes:** Statically resolvable in principle: a whole-program analyzer that models `net/http.ServeMux.HandleFunc` as "the second argument becomes reachable from `(*ServeMux).ServeHTTP`" can connect this registration to the dispatch site. Practically, this requires either (a) a built-in summary for the `net/http` mux, or (b) following the `func` value through `ServeMux.m["POST /entry/save/{entryID}"]` and out via `ServeHTTP`. The receiver type of the method value (`*handler`) is statically known from the surrounding function, so there is no virtual-dispatch ambiguity inside the method itself.

### Step 7: HTTP server dispatches a matching request to `saveEntry`

- **From:** `net/http` runtime — `(*http.Server).Serve` → `(*ServeMux).ServeHTTP` (an `http.Handler` interface call), which looks up the registered `http.HandlerFunc` for the route and invokes it.
- **To:** `internal/ui/entry_save.go:14` — body of `(*handler).saveEntry` begins executing.
- **Edge type:** `interface-method-dispatch` over `http.Handler.ServeHTTP`, fed by the route table populated in Step 6.
- **Resolution notes:** This is the only edge on the path that actually crosses an interface boundary. Static resolution needs to know that `appMux` (an `*http.ServeMux`) is the `Handler` field of an `http.Server`, that `ServeMux.ServeHTTP` looks up handlers in its internal map, and that the handler stored under `POST /entry/save/{entryID}` is the method value from Step 6. Most realistic call-graph builders treat `net/http` routing as a known pattern; otherwise full points-to + map-keyed dispatch modeling is required.

### Step 8: `saveEntry` fans out to `SendEntry` on a new goroutine

- **From:** `internal/ui/entry_save.go:36` — `go integration.SendEntry(entry, userIntegrations)`.
- **To:** `internal/integration/integration.go:41` — `func SendEntry(entry *model.Entry, userIntegrations *model.Integration)`.
- **Edge type:** `goroutine-launch` wrapping a `direct-function-call`.
- **Resolution notes:** The callee is a statically named, package-level function, so the call target itself is fully resolved at compile time. The `go` keyword means it executes on a new goroutine — relevant to the runtime semantics (no return value flows back to the caller, errors are swallowed inside `SendEntry`) but not to static reachability. A compiler instrumenting this call site would treat the `go f(...)` form like any other `f(...)` call for the purposes of routing it through a dispatch decision, but would need to preserve the `go` semantics in the rewrite.

### Region root reached

`internal/integration/integration.go:41` — `func SendEntry(entry *model.Entry, userIntegrations *model.Integration)`.

### Summary

- **Path length:** 8 steps (main → Parse → startDaemon → StartWebServer → newRouter → ui.Serve → mux.HandleFunc registration → ServeMux dispatch → saveEntry → `go SendEntry`).
- **Edge types encountered:** `direct-function-call` (×5), `http-handler-registration` / `method-value-as-callback-registration` (×1), `interface-method-dispatch` (×1, through `net/http`), `goroutine-launch` over a `direct-function-call` (×1).
- **Hardest edge:** Step 6 → Step 7 — the `mux.HandleFunc` registration followed by the `(*ServeMux).ServeHTTP` interface dispatch. The call site of `SendEntry` is reachable only because a method value was stored in a routing map keyed by a string pattern and later retrieved when an interface method on `*ServeMux` is invoked. A naïve call-graph builder will lose the connection at this boundary; resolving it requires either a hand-crafted summary for `net/http` routing or a points-to analysis that models map values flowing out of `ServeMux.ServeHTTP`.
- **Static-analysis feasibility:** Yes, the entire path is statically resolvable — there is no `reflect`, plugin loading, or runtime-supplied function pointer between `main` and `SendEntry`. The only non-trivial edges are (i) the `net/http` mux registration→dispatch pair, which is a well-known pattern that can be modeled with a framework-aware summary, and (ii) the `go` launch of `SendEntry`, which is a direct call wrapped in a goroutine. Three other call sites reach `SendEntry` via different framework adapters (`internal/api/entry_handlers.go:264` under the REST API mux, `internal/googlereader/handler.go:315` inside the Google Reader API edit-tag flow, and `internal/fever/handler.go:461` inside the Fever `mark` flow). They all share Steps 1–4 of this trace and only diverge at Step 5 (where the corresponding subtree handler — `api.NewHandler`, `googlereader.NewHandler`, or `fever.NewHandler` — is mounted on `appMux` in `routes.go`); the UI path was chosen here as it is no longer than the alternatives and uses the same `mux.HandleFunc` + `go SendEntry` pattern.
