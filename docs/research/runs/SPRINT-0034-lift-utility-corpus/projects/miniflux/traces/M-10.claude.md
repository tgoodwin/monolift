## Activation path for miniflux/M-10

### Entrypoint

`main.go:11` — `main()` is the program's binary entrypoint and invokes `cli.Parse()`, the package-level CLI driver that ultimately starts the long-running daemon.

### Step 1: main delegates to the CLI package

- **From:** `main.go:11` — `main()` calls `cli.Parse()` unconditionally.
- **To:** `internal/cli/cli.go:40` — exported `Parse` function in package `cli`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** A package-qualified call to a top-level function. Fully static; trivial for any call-graph builder.

### Step 2: CLI dispatches to the daemon-start branch

- **From:** `internal/cli/cli.go:248` — final tail call inside `Parse()`, after flag parsing and one-shot mode early-returns.
- **To:** `internal/cli/daemon.go:23` — package-private `startDaemon(store *storage.Storage)`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Same package, unqualified call to a top-level function. Statically resolvable. Note that `Parse()` has several flag-driven early returns (e.g. `flagRefreshFeeds`, `flagRunCleanupTasks`); the daemon path requires none of those flags to be set, but a static analyzer does not need that semantic — the call edge exists unconditionally.

### Step 3: daemon starts the HTTP server stack

- **From:** `internal/cli/daemon.go:38` — `startDaemon` calls `server.StartWebServer(store, pool)`.
- **To:** `internal/http/server/server.go:24` — exported `StartWebServer(store *storage.Storage, pool *worker.Pool) []*http.Server`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Package-qualified call. Guarded by `config.Opts.HasHTTPService()`, but the edge is statically present. Fully resolvable.

### Step 4: server constructs its top-level router

- **From:** `internal/http/server/server.go:49` — `newRouter(store, pool)` invoked inside an `http.Server` struct literal as the value of the `Handler` field, called once per listen target.
- **To:** `internal/http/server/routes.go:18` — package-private `newRouter(store, pool) http.Handler`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** The call appears as the right-hand side of `Handler: newRouter(...)`. Even though the resulting `http.Handler` is then stored into a struct field, the call itself is a plain function invocation — statically resolvable. (The subsequent `srv.Serve(listener)` calls at `server.go:181/192/207` are how the runtime later dispatches into the stored handler; those are runtime edges, not static call edges, and we do not need to traverse them for reachability.)

### Step 5: router constructs the API sub-handler

- **From:** `internal/http/server/routes.go:37` — `appMux.Handle("/v1/", api.NewHandler(store, pool))` inside `newRouter`.
- **To:** `internal/api/api.go:20` — exported `NewHandler(store *storage.Storage, pool *worker.Pool) http.Handler`.
- **Edge type:** `direct-function-call`
- **Resolution notes:** Package-qualified call. Guarded by `config.Opts.HasAPI()` at runtime, but the call edge is unconditional from a syntactic standpoint.

### Step 6: API handler is bound to a route

- **From:** `internal/api/api.go:41` — inside `NewHandler`, `mux.HandleFunc("POST /v1/discover", handler.discoverSubscriptionsHandler)` registers the handler against an `*http.ServeMux`.
- **To:** `internal/api/subscription_handlers.go:20` — method `(*handler).discoverSubscriptionsHandler(w http.ResponseWriter, r *http.Request)`.
- **Edge type:** `http-handler-registration` (via a bound method value). The expression `handler.discoverSubscriptionsHandler` is a Go *method value*: it captures the concrete receiver `handler` (a `*handler` allocated three lines above) and produces a `func(http.ResponseWriter, *http.Request)` that the mux stores in its routing table.
- **Resolution notes:** This is the only edge in the path that crosses through a framework data structure. A static analyzer must (a) recognize that `(*http.ServeMux).HandleFunc` records its second argument into a routing table, and (b) recognize that the runtime call site `srv.Serve(listener)` will eventually invoke that stored value through `(*http.ServeMux).ServeHTTP`. With models of `net/http`, this is statically resolvable — the receiver type is concrete (`*handler`), the method is a regular declared method, and there is no reflection or string-keyed lookup of the method itself; only the URL-pattern lookup is data-driven, which is irrelevant for reachability.

### Step 7: handler body invokes the region root

- **From:** `internal/api/subscription_handlers.go:52` — inside `discoverSubscriptionsHandler`, the chained expression `subscription.NewSubscriptionFinder(requestBuilder).FindSubscriptions(...)`.
- **To:** `internal/reader/subscription/finder.go:44` — method `(*subscriptionFinder).FindSubscriptions(...)`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** `NewSubscriptionFinder` returns a concrete `*subscriptionFinder` (declared at `finder.go:30`), so the receiver type at the `.FindSubscriptions` call site is fully known to the type checker. No interface dispatch; trivially resolvable.

### Region root reached

`internal/reader/subscription/finder.go:44` — `(*subscriptionFinder).FindSubscriptions(websiteURL, rssBridgeURL, rssBridgeToken string) (Subscriptions, *locale.LocalizedErrorWrapper)`.

### Summary

- **Path length:** 7 steps from `main` to the region root.
- **Edge types encountered:** `direct-function-call` (5×), `http-handler-registration` (bound method value, 1×), `method-call-on-concrete-type` (1×).
- **Hardest edge:** Step 6, the `mux.HandleFunc` registration. Every other edge is a syntactic call; this one stores a function value into a framework-managed routing table and relies on the runtime to invoke it later. A compiler must model `net/http`'s mux as a callback registry to keep the edge in its call graph. The bound-method-value semantics (capturing the concrete `*handler` receiver) are themselves easy; the indirection through the mux is what raises the bar.
- **Static-analysis feasibility:** The whole path is statically resolvable. There is no reflection, no plugin loader, no runtime-determined function pointer, and no interface widening that would require pointer analysis to disambiguate. With a model of `net/http`'s registration/dispatch behavior plus standard call-graph + concrete-type analysis, a compiler can connect `main` to `FindSubscriptions` end to end. Two alternative entrypaths exist and are of equivalent length and shape: the Google Reader handler at `internal/googlereader/handler.go:357` (registered at `internal/http/server/routes.go:31–33`) and the UI submit handler at `internal/ui/subscription_submit.go:72` (registered via `ui.Serve` at `routes.go:46`); both reach `FindSubscriptions` through the same `direct-function-call` → `http-handler-registration` → `method-call-on-concrete-type` shape, so the analytic burden is the same.
