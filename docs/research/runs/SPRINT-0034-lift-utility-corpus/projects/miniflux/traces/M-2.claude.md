### Entrypoint

`main.go:10` — `main()` is the program entrypoint. It does nothing but delegate to the CLI parser, which is what wires every subsequent execution mode (daemon, one-shot commands, migrations, healthcheck, etc.).

- **To:** `internal/cli/cli.go:40` — `func Parse()` (the package-level command-line dispatcher).

### Step 2: CLI flag dispatch selects the one-shot refresh command

- **From:** `internal/cli/cli.go:238–241` — when `flagRefreshFeeds` is true (set from `--refresh-feeds`, see `cli.go:75`), the parser calls `refreshFeeds(store)` and returns.

### Step 3: refreshFeeds spawns a worker pool of goroutines

- **From:** `internal/cli/refresh_feeds.go:47` — `go func(workerID int) { ... }(i)` is launched inside a `for i := range config.Opts.WorkerPoolSize()` loop.
- **To:** `internal/cli/refresh_feeds.go:47–64` — the anonymous function body, which captures `jobQueue` (a `chan model.Job` declared at line 39) and `store` (the outer parameter) by closure.
- **Edge type:** `goroutine-launch-with-closure`
- **Resolution notes:** The compiler must (a) recognize `go <fn>(...)` as a forked execution context that becomes reachable from program start, and (b) track the closure's captured free variables (`jobQueue`, `store`) so that calls inside the body can be resolved against the actual values they observe at launch. Both pieces are standard for Go static analysis — no dynamic dispatch, no `reflect`.

### Step 4: goroutine body invokes the feed-refresh handler

- **From:** `internal/cli/refresh_feeds.go:56` — inside `for job := range jobQueue { ... }`, the goroutine calls `feedHandler.RefreshFeed(store, job.UserID, job.FeedID, false)`.

- **Resolution notes:** `feedHandler` is just a renamed import of `miniflux.app/v2/internal/reader/handler` (`refresh_feeds.go:13`). The receive from `jobQueue` is a synchronization gate on *when* the call fires and on the argument values, not on *which* function is called — the callee is a hard-coded package symbol and is fully resolvable at compile time.

### Summary

- **Path length:** 5 steps.
- **Edge types encountered:** `direct-function-call`, `goroutine-launch-with-closure`.
- **Hardest edge:** Step 3, the goroutine launch. Not because it's unresolvable — it's a textbook anonymous-function `go` statement — but because it is the only edge whose semantics extend beyond the call graph: the compiler must recognize that the closure body is reachable as an independent execution flow and that its captured `jobQueue`/`store` are the data carriers that connect outer state to the inner direct calls. Every other edge is a vanilla static call.
- **Static-analysis feasibility:** Fully resolvable with intra- and inter-procedural call-graph + closure-capture analysis on the Go source tree. There is no interface dispatch, no `reflect`, no plugin, and no runtime-set function pointer anywhere on this path; a Monolift-style compiler can wire dispatch at the call site in `handler.go:329` (or hoist it further) without any dynamic gap.
- **Alternative paths considered (briefly):**
  - **Default daemon path** (`main → cli.Parse → startDaemon → worker.NewPool → go worker.Run → channel-receive → feedHandler.RefreshFeed → processor.ProcessFeedEntries`, ~6–7 steps): same edge-type vocabulary plus a `method-call-on-concrete-type` for `worker.Run` and one extra goroutine-launch level via `pool.go:41`. Equally statically resolvable, just longer.
  - **HTTP API path** (`main → cli.Parse → startDaemon → server.StartWebServer → mux registration → POST /v1/feeds handler → feedHandler.CreateFeed → processor.ProcessFeedEntries`, see `internal/api/feed_handlers.go:45`): substantially longer and adds an `http-handler-registration` edge for the route lookup. Strictly static but not the shortest.
  - **UI subscription path** (`internal/ui/subscription_submit.go:91/126` and `subscription_choose.go:47`): mirrors the HTTP API path with the same `http-handler-registration` style edge.
