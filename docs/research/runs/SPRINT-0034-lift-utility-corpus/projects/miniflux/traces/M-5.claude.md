`main.go:10` — `main()` invokes `cli.Parse()`, which is the single entrypoint for the miniflux binary. The binary has no other `main` package; all run modes (daemon, refresh-feeds, cleanup, etc.) are dispatched from inside `cli.Parse`.

### Step 4: Build the router and bind it as the server handler

- **From:** `internal/http/server/server.go:49` — `StartWebServer` constructs `&http.Server{...}` literals and assigns `Handler: newRouter(store, pool)`.
- **To:** `internal/http/server/routes.go:18` — `func newRouter(store *storage.Storage, pool *worker.Pool) http.Handler` body begins, and the returned `http.Handler` is stored in the `Handler` field of the `http.Server` struct literal.
- **Edge type:** `struct-literal-field-assignment` (of an `http.Handler` value produced by a `direct-function-call`)
- **Resolution notes:** Two pieces a compiler must connect: (a) the call to `newRouter` is a direct call, and (b) its return value is bound to `http.Server.Handler`. The runtime later invokes `Handler.ServeHTTP` from `http.Server.Serve`. To follow the activation path through the standard library boundary, a static analyzer must model `net/http`'s contract that whatever is assigned to `Handler` will eventually be dispatched on each request — i.e., it must treat field-stored handlers as called.

### Step 5: Register the API sub-handler under the `/v1/` prefix

- **From:** `internal/http/server/routes.go:37` — `appMux.Handle("/v1/", api.NewHandler(store, pool))` registers the API handler with the application `*http.ServeMux`.
- **To:** `internal/api/api.go:20` — `func NewHandler(store *storage.Storage, pool *worker.Pool) http.Handler` body begins, returning a `*http.ServeMux` that has been populated with route → handler bindings.
- **Edge type:** `http-handler-registration` (combining: direct call to `api.NewHandler` to build the value, plus `(*ServeMux).Handle` storing that value keyed by path prefix)
- **Resolution notes:** A compiler must (i) resolve `api.NewHandler` as the direct call producing an `http.Handler`, and (ii) recognise that `(*ServeMux).Handle(pattern, h)` is the standard library's way of recording `h` as a callback that will be dispatched on requests matching `pattern`. This is the same shape as a callback-registration table; the only difference is the dispatcher (`ServeMux.ServeHTTP`) does prefix matching at runtime.

### Step 6: Register the `POST /v1/feeds` HTTP handler

- **From:** `internal/api/api.go:42` — inside `NewHandler`, the line `mux.HandleFunc("POST /v1/feeds", handler.createFeedHandler)` registers the bound method value `handler.createFeedHandler` as the handler for the route.
- **To:** `internal/api/feed_handlers.go:21` — `func (h *handler) createFeedHandler(w http.ResponseWriter, r *http.Request)` body, which will be invoked when the mux dispatches a matching request.
- **Edge type:** `http-handler-registration` (specifically: `method-value` capture + registration in a `*ServeMux` route table)
- **Resolution notes:** Two static facts: (a) `handler.createFeedHandler` is a *method value* — a function value bound to the receiver `handler` (a `*handler` allocated four lines above). The receiver type is concrete, so the method target is unambiguous. (b) The call `mux.HandleFunc(pattern, fn)` adds an entry to the mux's pattern → handler map, which `ServeMux.ServeHTTP` later looks up by request URL and method. To resolve this edge, a static analyzer must (i) understand bound-method-value syntax in Go, and (ii) model `net/http.ServeMux` as a registry whose registered handlers may all be dispatched at runtime depending on the inbound request — i.e., conservatively treat each registration as a potential edge from server entry to the registered function.

### Summary

- **Path length:** 8 steps from `main()` to the region root.
- **Edge types encountered:** `direct-function-call`, `struct-literal-field-assignment`, `http-handler-registration`, `method-call-on-concrete-type`.
- **Hardest edge:** Steps 5–6 — the two `*http.ServeMux` registrations. The static call sites `mux.Handle(...)` / `mux.HandleFunc(...)` do not invoke the handler directly; they store it in an internal map that `ServeMux.ServeHTTP` consults later. To bridge this, a static analyzer must hard-code knowledge of `net/http.ServeMux` semantics (treating each registered handler as reachable from `Server.Serve`) — or more generally, a model of "callback tables keyed by string patterns." Step 6 also requires understanding Go *method values* (`handler.createFeedHandler` is a closure over `handler` of type `*api.handler`).
- **Static-analysis feasibility:** Yes, fully resolvable. There is no `reflect` use, no plugin loading, no runtime-determined function pointer on this path. The only non-trivial pieces are (a) modelling `net/http.ServeMux`'s pattern → handler registry as a set of potential dispatch edges, and (b) modelling `http.Server.Handler`'s field-store-then-runtime-call pattern. Both are well-known idioms; a Go-aware whole-program analysis with library annotations (or a small set of stdlib summaries) can produce a precise call graph through this entire path.
- **Alternative paths to the same region root (not the shortest):**
  - Web UI: `ui.Serve` → `subscription_choose.go:47` / `subscription_submit.go:91,126` → `feedHandler.CreateFeed` / `feedHandler.CreateFeedFromSubscriptionDiscovery` → `NewIconChecker(...).UpdateOrCreateFeedIcon()`. Same shape, one more handler-registration step than the API path.
  - Google Reader API: `googlereader.NewHandler` → `handler.go:430` `mff.CreateFeed`.
  - Background refresh: `worker.Pool` goroutines → `feedHandler.RefreshFeed` (handler.go:207) → `iconChecker.UpdateOrCreateFeedIcon()` / `CreateFeedIconIfMissing` at `handler.go:356–360`. Adds a `goroutine-launch` + `channel-send-receive` (the worker job queue), so strictly longer.
  - CLI one-shot: `flag --refresh-feeds` → `refreshFeeds(store)` → `feedHandler.RefreshFeed` (per `internal/cli/refresh_feeds.go:56`). Avoids the HTTP server but goes through the worker pool, so still longer.
