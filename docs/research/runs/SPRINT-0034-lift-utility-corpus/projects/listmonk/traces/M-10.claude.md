### Step 3: handler registration binds the BounceWebhook method to a route

- **From:** `cmd/handlers.go:235` — `g.POST("/webhooks/service/:service", a.BounceWebhook)`
- **To:** `cmd/bounce.go:117` — `func (a *App) BounceWebhook(c echo.Context) error`
- **Edge type:** `http-handler-registration` (with a bound-method-value as the registered callback)
- **Resolution notes:** Two things happen in one expression. (a) `a.BounceWebhook` is a Go *method value*: the receiver `a` (of concrete type `*App`) is captured into a function value whose target method is statically known — analogous to `func(c echo.Context) error { return (*App).BounceWebhook(a, c) }`. (b) `g.POST(path, handler)` stores that function value in the Echo router keyed by `(POST, "/webhooks/service/:service")`; the runtime later invokes it on a matching request. A static analyzer needs to (i) recognize the method-value expression and bind it to `(*App).BounceWebhook`, and (ii) model the framework's registration API as "this argument is a callback that the request loop will eventually invoke." This is gated by the runtime config check `a.cfg.BounceWebhooksEnabled` at `cmd/handlers.go:233`, but the registration itself is statically present in source.

The dispatch *into* this arm of the switch is selected at runtime by the URL path parameter `c.Param("service") == "sendgrid"` (`cmd/bounce.go:179`), but a static analyzer treats every arm as reachable — every concrete `ProcessBounce` reachable from `BounceWebhook` is a candidate, including this one.

### Region root reached

`internal/bounce/webhooks/sendgrid.go:53` — `(*Sendgrid).ProcessBounce`

### Summary

- **Path length:** 4 steps.
- **Edge types encountered:** `direct-function-call`, `direct-function-call`, `http-handler-registration`, `method-call-on-concrete-type`.
- **Hardest edge:** Step 3 (`http-handler-registration`). It combines two patterns a compiler must model: a Go *method-value* expression (`a.BounceWebhook` captures receiver `a` and yields a `func(echo.Context) error`) and a framework registration API (`g.POST(path, handler)`) that stores the callback in a router for later invocation by the request-handling loop. Steps 1, 2, and 4 are routine: same-package direct calls and a method call on a concrete struct field. Note that the Echo router itself is invoked indirectly via `srv.Start(...)` at `cmd/init.go:944`, which is launched in a `go func() { ... }()` goroutine — so the actual call into the registered handler crosses both a goroutine boundary and a framework-internal request-dispatch loop. The activation-path *registration* is static; the *invocation* edge from the framework's request loop back to `BounceWebhook` is what a compiler must abstract over.
- **Static-analysis feasibility:** Fully feasible. With package-level type analysis plus a model of Echo's `(*Group).POST` as "argument 2 is a callback registered for the matching route", a compiler can connect `main` → `BounceWebhook` → `(*Sendgrid).ProcessBounce` without any dynamic gap (no `reflect`, no plugins, no runtime-determined function pointers). The `a.cfg.BounceWebhooksEnabled` and `a.bounce.Sendgrid != nil` guards are runtime config gates, not static-analysis obstacles — the registration site and the call site are both unambiguous in source.
- **Alternative paths:** Only one entrypoint reaches the region. There is a second registration of `BounceWebhook` at `cmd/handlers.go:223` for the authenticated `POST /webhooks/bounce` route, but the Sendgrid arm at `cmd/bounce.go:179` is only entered when `c.Param("service") == "sendgrid"`, which the `:service` path param supplies — so in practice the `/webhooks/service/:service` registration at `cmd/handlers.go:235` is the relevant one. Path length is identical either way.
