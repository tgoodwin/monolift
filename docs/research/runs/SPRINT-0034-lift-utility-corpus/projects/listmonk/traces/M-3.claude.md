### Summary

- **Path length:** 3 steps (entrypoint → Run goroutine → worker goroutine → interface dispatch into `Emailer.Push`).
- **Edge types encountered:** `goroutine-launch`, `goroutine-launch`, `interface-method-dispatch` (with a `channel-receive` on `m.campMsgQ` in the same step but not part of the call-target resolution).
- **Hardest edge:** Step 3's `interface-method-dispatch`. The call site holds a `manager.Messenger` interface looked up by string key in a map populated transitively from another package's slice-returning constructor, so resolving it precisely requires whole-program type analysis plus points-to over the `messengers` map and the `[]manager.Messenger` slices flowing into `AddMessenger` from `initSMTPMessengers`/`initPostbackMessengers`.
- **Static-analysis feasibility:** Fully resolvable with type analysis + a standard call-graph algorithm (e.g. RTA/VTA/points-to). Every edge is statically determinable: the goroutine launches use concrete receivers, and the only interface dispatch is over a closed set of implementations registered at startup. There is no `reflect`, plugin, or runtime function-pointer indirection on this path.
