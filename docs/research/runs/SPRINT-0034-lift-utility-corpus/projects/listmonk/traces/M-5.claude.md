### Summary

- **Path length:** 4 steps (entrypoint → region root).
- **Edge types encountered:** `direct-function-call`, `direct-function-call`, `http-handler-registration` (which decomposes into `method-value-bound-to-receiver` + `closure-capture`), `goroutine-launch` over `method-call-on-concrete-type`.
- **Hardest edge:** Step 3, the HTTP handler registration. Two reasons. First, the analyzer must model Echo's router as a callback sink — `g.POST(path, handler)` does not produce a syntactic call edge to `handler`; the framework invokes it later. Second, the registered value is not the bare method but a `pm`-wrapped closure, so the analyzer has to look inside the wrapper to see that `next(c)` is the captured method value `a.ImportSubscribers`. Both sub-problems are tractable with whole-program type/closure analysis plus a small framework model, but they require more than naive call-graph construction.
- **Static-analysis feasibility:** Fully resolvable. Every edge is statically typed Go — no `reflect`, no plugins, no runtime-determined function pointers. With a model of Echo's router-registration pattern (treat `(*echo.Group).POST`'s second argument as reachable-from-entrypoints) and standard closure/method-value tracking, a compiler can construct an end-to-end call graph from `main` to `(*Session).LoadCSV`. The `go` keyword adds a concurrency edge but no dynamic gap. There is one alternate call site (`cmd/import.go:115`, ZIP branch) that an instrumenter would need to handle symmetrically; both branches resolve to the same region root.
