## Activation path for listmonk/M-2

### Entrypoint

`cmd/main.go:193` — `func main()` boots the listmonk binary: it constructs the campaign manager, attaches all configured messengers to it, and starts the manager's worker goroutines that drain message queues and dispatch to messenger backends.

The path below is the **shortest static path** from `main` to `(*postback.Postback).Push`. It has two interleaved aspects that a static analyzer must resolve together:

1. The **call chain** from `main` down through goroutines and a channel-driven worker loop to an interface call.
2. The **binding chain** that places a `*postback.Postback` into the `Manager.messengers` map under a string key, which the call chain later looks up.

I trace the call chain as the primary path and call out the binding chain as a sub-trace under the interface-dispatch step, because a compiler cannot resolve the interface call without resolving the binding.

### Step 1: main spawns the campaign manager goroutine

- **From:** `cmd/main.go:262` — `go mgr.Run()`
- **To:** `internal/manager/manager.go:265` — `func (m *Manager) Run()`
- **Edge type:** `goroutine-launch`
- **Resolution notes:** `mgr` is the `*manager.Manager` returned by `initCampaignManager(...)` at `cmd/main.go:216`. The receiver type is concrete (`*manager.Manager` is constructed by `manager.New` at `internal/manager/manager.go:150`), so the call target is statically resolved by type analysis on the receiver. The `go` keyword adds a fork edge to the call graph but does not change resolvability.

### Step 2: Run spawns N worker goroutines

- **From:** `internal/manager/manager.go:274` — `go m.worker()`
- **To:** `internal/manager/manager.go:462` — `func (m *Manager) worker()`
- **Edge type:** `goroutine-launch`
- **Resolution notes:** Method receiver is the same concrete `*Manager` value as Step 1; `worker` is an unexported method on that type. Trivially resolvable. `m.cfg.Concurrency` (loop bound at line 273) is irrelevant to call-graph resolution: at least one worker is always spawned because `New` clamps `Concurrency` to `>= 1` (lines 154–156).

### Step 3: worker drains a campaign-message channel

- **From:** `internal/manager/manager.go:468` — `case msg, ok := <-m.campMsgQ:`
- **To:** `internal/manager/manager.go:523` — body that calls `m.messengers[msg.Campaign.Messenger].Push(out)`
- **Edge type:** `channel-receive-dispatch`
- **Resolution notes:** This is intra-procedural control flow inside `worker()`, not a call edge. I record it explicitly because the *origin* of `msg` is via channel send rather than an argument: the static analyzer must connect this receive site to the corresponding sends to know the values that flow through. The relevant senders are `m.campMsgQ <- msg` at `internal/manager/pipe.go:104` (campaign batches) and `m.msgQ <- msg` at `internal/manager/manager.go:222` (transactional messages via `PushCampaignMessage`). A pointer/dataflow analysis must thread `models.Message` values from those send sites to this receive site through a typed `chan` of known element type — straightforward for a Go analyzer because channel types are statically declared on the `Manager` struct (`internal/manager/manager.go:84–86`).

### Step 4: worker invokes Messenger.Push via interface dispatch over a map lookup

- **From:** `internal/manager/manager.go:523` — `err := m.messengers[msg.Campaign.Messenger].Push(out)`
- **To:** `internal/messenger/postback/postback.go:97` — `func (p *Postback) Push(m models.Message) error`
- **Edge type:** `interface-method-dispatch` (composed with `map-keyed-receiver-selection`)
- **Resolution notes:** The receiver expression is `m.messengers[stringKey]`. `m.messengers` is declared as `map[string]Messenger` (`internal/manager/manager.go:67`), where `Messenger` is the interface declared at lines 49–54 with method `Push(models.Message) error`. To resolve this call to `(*postback.Postback).Push`, a static analyzer must:
  1. Enumerate types that implement `manager.Messenger` (whole-program scan for the `Push`/`Name`/`Flush`/`Close` method set). For listmonk this set is `{*email.Emailer, *postback.Postback}`.
  2. Determine which of those types can flow into the map. This is the **binding chain**, traced below.
  3. Treat the map key (`msg.Campaign.Messenger`, a `string` from a DB record) as opaque — the compiler cannot statically prove which key is used at runtime, so it conservatively assumes any registered messenger can be the callee. Both `*email.Emailer.Push` and `*postback.Postback.Push` are reachable; for this trace we follow the `*postback.Postback` branch.

  The analogous call at `internal/manager/manager.go:554` (`m.messengers[msg.Messenger].Push(msg)`, draining `m.msgQ`) is the same edge type and resolves the same way.

#### Binding sub-trace: how `*postback.Postback` reaches the messengers map

- **B1:** `cmd/main.go:213` — `msgrs = append(initSMTPMessengers(), initPostbackMessengers(ko)...)` collects all messengers into `[]manager.Messenger`. Edge type: `interface-conversion-on-return` (the `*postback.Postback` returned from `postback.New` is implicitly converted to `manager.Messenger` when appended).
- **B2:** `cmd/init.go:711` — `p, err := postback.New(o)` produces a fresh `*postback.Postback`. Edge type: `direct-function-call` (constructor returning a concrete type). Resolvable trivially.
- **B3:** `cmd/init.go:715` — `out = append(out, p)` stores the value into the slice that becomes `msgrs`. Edge type: `slice-append-of-interface-value`.
- **B4:** `cmd/main.go:216` — `mgr = initCampaignManager(msgrs, ...)` passes the slice into the constructor. Edge type: `direct-function-call` with a slice-of-interface argument.
- **B5:** `cmd/init.go:590–592` — `for _, m := range msgrs { mgr.AddMessenger(m) }`. Edge type: `iteration-over-interface-slice` followed by a concrete method call on `*manager.Manager`.
- **B6:** `internal/manager/manager.go:189` — `m.messengers[id] = msg` where `id := msg.Name()` (line 185). Edge type: `interface-method-dispatch` for `msg.Name()` plus `map-store-of-interface-value`. The string key is `(*postback.Postback).Name() == p.o.Name`, which is read from configuration (`item.String("name")` at `cmd/init.go:703`). Therefore the key is config-derived and not statically known — but the *value* (`*postback.Postback`) is statically known to be in the map after this assignment.

A whole-program type-flow / points-to analysis (e.g. RTA, VTA, or Andersen-style) can compose B1–B6 to prove that `*postback.Postback` is among the values held in `Manager.messengers`, and therefore that Step 4's interface dispatch can target `(*postback.Postback).Push`.

### Region root reached

`internal/messenger/postback/postback.go:97` — `func (p *Postback) Push(m models.Message) error`

### Summary

- **Path length:** 4 call-chain steps (entrypoint → Run → worker → channel-receive → interface-dispatch → region root), plus a 6-step binding sub-trace required to resolve the interface dispatch.
- **Edge types encountered:** `goroutine-launch` (×2), `channel-receive-dispatch`, `interface-method-dispatch` (composed with `map-keyed-receiver-selection`). Binding sub-trace adds: `direct-function-call`, `interface-conversion-on-return`, `slice-append-of-interface-value`, `iteration-over-interface-slice`, `map-store-of-interface-value`.
- **Hardest edge:** Step 4 (the interface dispatch over a map-keyed receiver). Two compounding difficulties: (a) the receiver is selected by a runtime string key that originates from a database column (`msg.Campaign.Messenger`), so the analyzer cannot prove a single concrete callee — it must over-approximate to "any messenger registered into the map"; (b) the set of registered messengers is established by a separate registration call chain (`initPostbackMessengers` → `AddMessenger`) that must be linked to the dispatch site by whole-program dataflow, not just by syntactic call-graph traversal.
- **Static-analysis feasibility:** Fully resolvable in principle with whole-program type analysis plus a points-to / RTA-style call graph. There are no `reflect.Call`, plugin loads, or runtime-generated function pointers on this path. The dispatch is over-approximate (it admits both `*email.Emailer.Push` and `*postback.Postback.Push`), but for the purpose of an activation-path lift the compiler can either instrument both candidate `Push` implementations or specialize the call site by the runtime string key. The activation-path resolver does not need the runtime key value; it only needs to enumerate the candidate concrete `Push` targets, which is a finite, statically determinable set.
- **Alternative paths:** The same `Push` is also reachable via `m.messengers[msg.Messenger].Push(msg)` at `internal/manager/manager.go:554`, fed by the `m.msgQ` channel. That branch is fed by `Manager.PushMessage` (`internal/manager/manager.go:201`), which is itself called from transactional-mail HTTP handlers in `cmd/tx.go` (an HTTP-handler-registration entrypoint). Path length is comparable; the structure of the interface dispatch is identical, so the chosen path generalizes.
