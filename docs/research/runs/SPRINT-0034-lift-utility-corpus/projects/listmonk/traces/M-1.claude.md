## Activation path for listmonk/M-1

### Entrypoint

`cmd/main.go:193` — `func main()` is the binary entrypoint. It builds the `App` struct and, among other things, launches the campaign manager as a background goroutine before starting the HTTP server.

### Step 1: Launch the campaign-manager goroutine

- **From:** `cmd/main.go:262` — `go mgr.Run()` is invoked. The local variable `mgr` was assigned at `cmd/main.go:216` from `initCampaignManager(...)`, which returns `*manager.Manager` (see `cmd/init.go:561`). The goroutine target is therefore the concrete method `(*manager.Manager).Run`.
- **To:** `internal/manager/manager.go:265` — `func (m *Manager) Run()`.
- **Edge type:** `goroutine-launch`
- **Resolution notes:** Static call graph needs to recognize `go x.Run()` as creating an edge to the function value `x.Run`, where `x` is statically typed `*manager.Manager`. No interface dispatch involved; the receiver type is concrete by the assignment at line 216 and the return type of `initCampaignManager`.

### Step 2: Run() pulls a `*pipe` off `m.nextPipes` and calls `NextSubscribers` on it

- **From:** `internal/manager/manager.go:279-280` — `for p := range m.nextPipes { has, err := p.NextSubscribers() ... }`. The channel `m.nextPipes` is declared as `chan *pipe` at `internal/manager/manager.go:84` and constructed at `manager.go:173`. The compiler can infer `p` has type `*pipe` from the channel element type.
- **To:** `internal/manager/pipe.go:76` — `func (p *pipe) NextSubscribers() (bool, error)`.
- **Edge type:** `channel-typed-method-dispatch` (channel-receive of a concrete-pointer value, immediately followed by a method call on that concrete type)
- **Resolution notes:** Two pieces of static reasoning compose in one statement: (a) channel-receive type inference — the value taken out of `chan *pipe` is `*pipe`; (b) method dispatch on a concrete pointer type, which resolves uniquely to `(*pipe).NextSubscribers`. Producers that send into this channel are `scanCampaigns` (`manager.go:448`) and `Run` itself (`manager.go:294`); their values are also typed `*pipe`, so the channel does not erase or widen the type.

### Step 3: NextSubscribers loops over fetched subscribers and builds a per-recipient message

- **From:** `internal/manager/pipe.go:96` — `msg, err := p.newMessage(s)` inside the per-subscriber loop (`for _, s := range subs`). Receiver `p` is `*pipe` (the method's receiver) and `s` is `models.Subscriber`.
- **To:** `internal/manager/pipe.go:172` — `func (p *pipe) newMessage(s models.Subscriber) (CampaignMessage, error)`.
- **Edge type:** `method-call-on-concrete-type`
- **Resolution notes:** Direct method dispatch on the concrete pointer type `*pipe`; trivially resolved by name + receiver type.

### Step 4: newMessage forwards into the manager's per-recipient render method

- **From:** `internal/manager/pipe.go:173` — `msg, err := p.m.NewCampaignMessage(p.camp, s)`. Field `p.m` is declared as `*Manager` in the `pipe` struct (`internal/manager/pipe.go:23`), and `p.camp` is `*models.Campaign` (`pipe.go:14`).
- **To:** `internal/manager/message.go:13` — `func (m *Manager) NewCampaignMessage(c *models.Campaign, s models.Subscriber) (CampaignMessage, error)`.
- **Edge type:** `method-call-on-concrete-type` (with a `struct-field-pointer-receiver` lookup to obtain the receiver)
- **Resolution notes:** The receiver is the struct field `p.m` whose declared type is `*Manager`. No interface or function-value indirection — type analysis on the `pipe` struct definition is sufficient to bind the call to `(*Manager).NewCampaignMessage`.

### Region root reached

`internal/manager/message.go:13` — `(m *Manager) NewCampaignMessage(c *models.Campaign, s models.Subscriber) (CampaignMessage, error)`. This is the per-recipient render: it constructs a `CampaignMessage` bound to a single `*models.Campaign` and `models.Subscriber` and immediately calls `msg.render()` (line 24), which executes the campaign's pre-compiled subject and body templates.

### Summary

- **Path length:** 4 steps (entrypoint + 4 edges).
- **Edge types encountered:** `goroutine-launch`, `channel-typed-method-dispatch` (channel-receive composed with concrete method dispatch), `method-call-on-concrete-type` (×2, one of which uses a struct-field pointer as receiver).
- **Hardest edge:** Step 2. It is the only step requiring composed reasoning — the analyzer must (a) flow the channel element type `*pipe` through `for p := range m.nextPipes`, then (b) dispatch the method call on that inferred type. It is still fully static because `m.nextPipes` is created with a literal `chan *pipe` type at `manager.go:173` and never reassigned to a wider type, but it forces the analyzer to track typed-channel data flow rather than purely lexical call edges. Steps 1, 3 and 4 are local syntactic resolutions.
- **Static-analysis feasibility:** Yes — the entire path is statically resolvable with a standard whole-program type/call-graph analysis. There is no `reflect`, plugin loading, or runtime function-pointer indirection on the way to the region root. The only non-trivial element is goroutine-launch (Step 1) and channel-typed value flow (Step 2), both of which are well-handled by Go's static type system because the goroutine target and the channel element type are concrete pointer types.
- **Alternative paths (not minimal):** `NewCampaignMessage` is also reachable from several HTTP handlers — `cmd/public.go:185` (`CampaignMessagePage`), `cmd/campaigns.go:183` and `:226` and `:653` (campaign preview / archive / view endpoints), `cmd/templates.go:251` (template preview), and `cmd/archive.go:166` and `:225` (public archive rendering). Each of those paths goes through Echo route registration (`http-handler-registration` — a function value stored in the router's trie at startup) and an HTTP-request-driven handler invocation, so they require an extra `function-value-in-struct-field` edge plus an inbound `runtime-driven` step before reaching the same region root. The campaign-manager goroutine path traced above is both shorter and the path that actually drives bulk campaign sending.
