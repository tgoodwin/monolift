- **From:** `cmd/handlers.go:235` — `g.POST("/webhooks/service/:service", a.BounceWebhook)`
- **To:** `cmd/bounce.go:117` — `func (a *App) BounceWebhook(c echo.Context) error`

- **Resolution notes:** `a.BounceWebhook` is a Go *method value*: at compile time it is desugared into a function value that captures the receiver `a *App` and dispatches statically to `(*App).BounceWebhook`. Echo stores this `echo.HandlerFunc` in its route trie keyed by `(POST, "/webhooks/service/:service")`. A whole-program analyzer needs (a) to recognize method-value capture so the receiver is known and (b) to model the framework's "handler stored in struct → invoked on matching request" dispatch — equivalent to `function-value-in-struct-field` plus URL-pattern matching. The conditional guard at `cmd/handlers.go:233` (`if a.cfg.BounceWebhooksEnabled`) is config-driven and runtime-dependent, but does not change the static target.

### Summary

- **Path length:** 5 steps.
- **Edge types encountered:** `direct-function-call` (×2), `method-value-handler-registration`, `function-value-in-struct-field` (router dispatch), `method-call-on-concrete-type`.
- **Hardest edge:** Step 3 → Step 4, the Echo route registration / dispatch pair. It requires the analyzer to (a) recognize method values so `a.BounceWebhook` resolves to `(*App).BounceWebhook` with a known receiver, and (b) model the framework idiom where a function value placed into a router struct is later invoked by the framework. Everything else is plain package-level calls or concrete-type method calls.
- **Static-analysis feasibility:** Fully resolvable with whole-program type analysis plus an Echo-aware (or generic "function value installed in container, then invoked") summary; no reflection, plugin loading, or runtime-determined function pointer is involved on this path.
- **Alternative paths considered:** The same `(*App).BounceWebhook` is also registered on the authenticated route `g.POST("/webhooks/bounce", pm(a.BounceWebhook, "webhooks:post_bounce"))` at `cmd/handlers.go:223`, but that endpoint is reached only when `service == ""` in the `BounceWebhook` switch, which never invokes `SES.ProcessBounce`. The public `/webhooks/service/:service` route is therefore the unique activation path for this region. There is no goroutine, cron, or mailbox call site for `SES.ProcessBounce` (the POP3 mailbox path produces bounces independently and never invokes the SES processor).
