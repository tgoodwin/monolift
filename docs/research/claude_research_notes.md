# The compiler eats the cloud: distributed applications in 2026

**Writing distributed software has stopped being an architecture problem and started being a compiler problem.** The decisive shift of the past two years is that the decomposition of an application into microservices, functions, or actors is no longer something developers hand-craft; it is a program transformation performed by a toolchain over a single source of truth. Service Weaver at Google, Monolift at UC Santa Cruz, Hydro at Berkeley and AWS, Encore in industry, and Restate and DBOS on the runtime side all express the same thesis: physical topology should be derived from logical code plus policy. That thesis is now backed by working compilers, durable-execution runtimes, WebAssembly component models, and LLM-assisted refactoring pipelines that together let one binary be sharded, replicated, or collapsed without rewrites. The result is a new center of gravity for the field — a layered stack in which application logic, distribution, resilience, and scheduling are separable concerns, each with a specialized system underneath.

This report synthesizes what that stack actually looks like in early 2026, where it works, and where it is still fragile. The evidence comes from PLOS '25, SOSP '24–'25, OSDI '23–'25, ICFP '23, CNCF project releases, and the industrial record of Google, Adobe, American Express, Fermyon, and OpenAI deployments.

## The core thesis: distribution as a compiler pass

The reframing is clearest in **Monolift** (Goodwin, Ramos, Quinn, Kuper, PLOS 2025), which treats distribution of a general-purpose program as **a compiler pass driven by lightweight comment directives**, with a runtime monitor that reshuffles the deployment in response to live performance metrics. The same intuition drives Google's **Service Weaver** (2023), whose tagline — "write your application as a modular monolith and deploy it as a set of microservices" — has been the most influential slogan in the space. Service Weaver's code generator produces either a local stub or a remote client/server for every component boundary, deciding at deploy time via a `colocate` configuration. The consensus critique, articulated in the "What Did Service Weaver Miss" postmortem, is that the logical-monolith model **forces single-language, monorepo, compile-time dependency management**, and therefore fits closed ecosystems (Google's internal stack) better than heterogeneous OSS estates. Service Weaver's momentum has slowed as a product, but its ideas propagate.

Berkeley and AWS's **Hydro project** pushes this further. The Hydro stack compiles Rust programs down to a **Dataflow Intermediate Representation (DFIR)**, a microbatch stream-processing runtime already shipping in production (GreptimeDB). Hellerstein, Laddad, Milano, Power, and Samuel show that primitives like **refactoring, replication, and partitioning** can be expressed as rule-driven rewrites over DFIR, with e-graphs discovering equivalent distributed plans automatically. The 2024 **Suki** DSL adds choreographic programming via staged Rust, and the **Flo** paper (2024) formalizes two streaming semantics — *streaming progress* and *eager execution* — that unify Flink, LVars, and DBSP. Hydro is now the reference implementation of the "compiler for distributed systems" agenda, and its io_uring backend is positioned to give zero-copy network I/O without changes to high-level logic.

The functional-programming branch has matured in parallel. **HasChor** (Shen, Kashiwa, Kuper, ICFP 2023) brought choreographic programming — where one program describes the global dance of all participants and endpoint projection derives per-node code — into mainstream Haskell as "just a library." Its 2024 successor **MultiChor** (Bates, Kashiwa, Near, et al.) fixes HasChor's broadcast inefficiency with **multiply-located values** and introduces **census polymorphism**, letting one choreography work for variable numbers of participants (critical for federated learning and secure multi-party computation, where MultiChor can express the full GMW protocol concisely). Alongside Choral (JVM, OO), Pirouette (higher-order typed), and PolyChorλ (full process polymorphism), these systems demonstrate that **deadlock-freedom by construction** is becoming a practical property, not a theoretical one.

## Durable execution: the new runtime substrate

If compilers handle where code runs, **durable-execution engines now handle what happens when it fails**. This is arguably the most consequential runtime-layer change since Kubernetes. The category — Temporal, Restate, DBOS, Inngest, Resonate, AWS Step Functions, Azure Durable Functions — treats every workflow step as a journaled event appended to a log; on crash, the replay engine reconstructs state from the log without re-executing completed steps. OpenAI's Codex runs on Temporal in production at millions of requests, and NVIDIA orchestrates its cross-cloud GPU fleet on it.

The technical contest is over how the log is implemented and how versioning is handled. **Restate** (Rust, single binary) uses a log-first architecture: each partition pairs a **Bifrost** distributed durable log with an in-process Tokio event loop whose partition-local state lives in RocksDB. A durable step commits in a single network round-trip to obtain a replication quorum, giving median step latencies of **3 ms under low load and 10 ms under high load**, with RocksDB durability happening asynchronously. Versioning in Restate resembles Step Functions' immutable-workflow model but with code-first ergonomics, avoiding Temporal's accumulating `patch` API. **DBOS**, commercialized out of Stonebraker, Kraska, and Zaharia's VLDB '22 work, is architecturally different: it runs in-process as a library, storing workflow and step state in Postgres or SQLite, and has become the default durable-execution integration for **Pydantic AI agents**. The deeper research ancestor, **Apiary** (VLDB '23), showed that tightly integrating FaaS execution with a transactional DBMS (rather than bolting a transaction manager onto remote storage like Beldi or Boki) reduces storage access time by up to **3×** while giving cross-function transactions and end-to-end exactly-once semantics.

The academic thread behind this industrial surge runs through **Boki** (Jia & Witchel, SOSP 2021), which introduced the **metalog** — a compact ordering structure decoupled from data throughput — and built fault-tolerant workflows, durable object storage, and message queues on a shared-log API, speeding stateful serverless workloads up to **4.7×**. Halfmoon (2024) later proved Boki's design was not log-optimal and achieved 20–40% lower latency by asymmetrically logging only reads or only writes depending on workload. The through-line is that **the log is displacing the database as the primary consistency primitive for distributed application state**, because logs map naturally onto replay-based recovery.

## WebAssembly components: the portable unit of distribution

The January 2024 stabilization of **WASI 0.2** and the **Wasm Component Model** reset the cloud-native packaging debate. Components differ from containers in a fundamental way: they abstract only the application logic, with no kernel or distro baggage. In practice this means **millisecond startup** (versus multi-second container cold starts), language-independent linking via WIT (Wasm Interface Types), and the ability to compose or distribute components at runtime without recompilation. **wasmCloud 1.0** (March 2024) and **Spin 3.0** (November 2024) are the two CNCF-anchored production runtimes; wasmCloud's **lattice** uses NATS for a flat-topology mesh and its **wRPC** protocol lets distributed components interact as if locally composed. Spin became a containerd shim in 2025, meaning Wasm workloads schedule natively through `kubectl` and Helm.

The production track record is real but narrow. Fermyon's edge platform handles **75 million requests per second**; Fastly Compute@Edge has 10,000+ users; **American Express built an internal FaaS platform on wasmCloud**; Adobe uses it to consolidate Kubernetes estates; Cloudflare Workers serves millions of requests with sub-millisecond cold starts. But — and the candid 2026 Java Code Geeks assessment is the clearest statement of this — **no one is running a general-purpose microservices backend on Wasm at scale**. Three structural gaps persist: absence of native multi-threading in server-side WASI (the shared-memory-plus-atomics proposal is browser-only), weak debugging (DWARF support exists but IDE integration is poor, and wasmCloud's **wadge** library is a workaround rather than a fix), and observability tooling that requires deliberate instrumentation rather than flowing naturally from the runtime. **WASIp3**, whose first RC shipped in Spin 3.5 (November 2025), adds native async and is the near-term unlock; it is the single most important upcoming milestone for whether Wasm eats the microservices backend or remains confined to edge/FaaS/plugin niches.

## AI in the decomposition loop

A credible research literature now exists for **using LLMs to decompose monolithic systems into microservices** — the pain point that frameworks like Service Weaver tried to avoid by making decomposition optional. The February 2025 **MonoEmbed** work (Sellami & Saied) fine-tunes LLMs with contrastive learning and LoRA to produce embedding vectors for monolithic components, then clusters them into candidate microservices, outperforming prior static-analysis baselines on cohesion and balance metrics. ICSA 2024's **MAGNET** uses graph neural networks at method granularity, and CARGO (2023) added AI-guided dependency analysis. Industrial practice, as documented in Medium's widely shared 2026 account of LLM-assisted monolith migrations, has moved developers up the stack: LLMs absorb the boilerplate refactoring, while humans focus on validating the decomposition plan and steering the boundaries. Systematic reviews (*Migration of monolithic systems to microservices*, Saucedo et al., *Information and Software Technology*, 2025) confirm the decomposition phase remains the hardest part of migration, but the gap between manual and LLM-assisted effort has closed sharply.

On the scheduling side, **Cilantro** (Bhardwaj et al., OSDI 2023) has become the reference for performance-aware resource allocation in microservices, using online learning to form feedback loops between each job's real P99 latency and its CPU allocation. On DeathStarBench's hotel-reservation benchmark (19 microservices, 160 CPUs), Cilantro cuts end-to-end P99 latency to **0.18× a resource-fair scheduler and 0.57× the next-best performance-aware baseline**. Kubernetes v1.35 (December 2025) landed the first **Workload API**, bringing gang scheduling and opportunistic batching in-tree; this is the concrete mainstream answer to a decade of research on learning-augmented schedulers, which is now bifurcating into two branches — LLM-inference-specific systems (DistServe, Llumnix, dLoRA, BlitzScale at OSDI '24/'25) and general microservice autoscalers like SCOOT and BAScaler.

## Observability and confidential computing as table stakes

Two formerly niche areas have crossed into the default toolkit. **eBPF-based observability** is now the standard approach for anything above a few dozen pods. **Cilium/Hubble** supplies L3–L7 network visibility and service maps; **Pixie** auto-parses HTTP, gRPC, MySQL, Postgres, Redis, and TLS traffic at the syscall level with no code changes; **Tetragon** handles runtime security; **Grafana Beyla** emits OpenTelemetry spans without SDK instrumentation. The combined resource overhead is striking: a 500-pod cluster on this stack uses roughly **12 GB RAM and 3–4 CPU cores total**, versus 15–20 GB and 8–12 cores for the equivalent sidecar (Istio + Datadog) model — an order-of-magnitude reduction. The practical constraint is kernel version: the full stack wants Linux **6.1+** (Amazon Linux 2023, Ubuntu 24.04, Bottlerocket, GKE COS), with 5.10 the realistic minimum.

**Confidential computing** graduated to general availability in 2024. Google Cloud made Confidential VMs GA on N2D with **AMD SEV-SNP** (June 2024), on C3 with **Intel TDX** (September 2024), and launched A3 Confidential VMs with **NVIDIA H100 GPU TEE** in preview (October 2024). A systematic SIGMETRICS 2025 measurement study (Misono et al.) found TDX has roughly **1–2% lower overhead** than SEV-SNP on memory-bound workloads, while SEV-SNP scales better per socket. Kubernetes Confidential Containers (CoCo) now ship as runtime classes via a standard operator, with Kata Containers providing the lightweight VM layer. The important shift is architectural: **GPU TEEs make confidential AI training and inference practical**, closing the gap that made CPU-only TEEs insufficient for the dominant cloud workload of 2025–2026.

## How the layers actually compose

The picture that emerges is a coherent four-layer stack, not a zoo of competing frameworks:

- **Layer 1 — Authoring.** Service Weaver, Encore, Monolift, Hydro/Suki, or HasChor/MultiChor write one program that a compiler or staged-DSL transforms into distributed code; choreographic approaches give deadlock-freedom, dataflow approaches give rewrite-based optimization.
- **Layer 2 — Resilience.** Restate, Temporal, DBOS, Boki, and AWS/Azure durable functions journal every step to a log so crashes become replays; this is now the default orchestration primitive for anything long-running or agentic.

Underneath sit **Layer 3 (the unit of deployment)** — OCI containers remain dominant, but Wasm components are eating edge, FaaS, and plugin niches — and **Layer 4 (the substrate)** — Kubernetes with eBPF observability, TEE-backed confidential VMs, and learning-augmented schedulers.

The old "monolith vs. microservices" debate has dissolved because every serious authoring model now lets you pick at deploy time. The real questions have moved up: *which properties* (consistency, availability, locality, confidentiality) you want your compiler to preserve, *which log* you trust for durability, and *how much* of your architecture you are willing to let an LLM propose.

## Conclusion: what changed, and what will change next

The last two years have delivered a quiet but decisive result: **the interesting intellectual work in distributed applications now happens in the compiler and the log**, not in the service mesh or the orchestration YAML. Monolift, Hydro, MultiChor, and Service Weaver's successors mean distribution is a derived property; Restate, DBOS, and Boki mean fault-tolerance is a derived property; Wasm components mean portability is a derived property; eBPF means observability is a derived property. Each layer is independently replaceable, and that composability is the actual advance.

Three things to watch in the next twelve months. First, **WASIp3 async** will determine whether Wasm components graduate from edge-and-FaaS to mainstream backends; if it does, the container-as-universal-deployable era begins to end. Second, **LLM-assisted decomposition plus durable-execution orchestration** is the likely dominant pattern for agentic systems — OpenAI Codex on Temporal is the template. Third, **confidential GPU computing** is the substrate that makes regulated-industry AI deployable in public clouds at scale; its adoption curve will shape where AI workloads run. The compiler ate the cloud; the question now is which runtime wins the layer below.
