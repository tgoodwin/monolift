# 01 — Monolift and Closest Comparisons

## The Monolift System

**Source:** `inspiration/papers/monolift-plos25.pdf`

### Core abstractions

- **Lift** — a code segment (function, interface, or class) that can execute locally or remotely.
  Defined p.2 §2.1: *"a code segment that can execute locally or remotely… a possible unit of distribution."*
- **Lift annotation** — a Go comment: `//monolift:offload metric=CPU threshold=75%` (p.3 Figure 2).
  Annotations are transparent to the stock Go toolchain; the program compiles and runs without Monolift.
- **Delegate expression** — embedded DSL inside the annotation that encodes the placement policy.
  Can be static (`always remote`) or dynamic, referencing live metrics: CPU%, MEM%, IPS (p.3 Table 1).
- **Lift point** — call-site wrapper generated by the compiler that consults the runtime and
  dispatches locally or via RPC (p.2 §2.2, p.4 §3.2).

### Compiler (§2.2, p.2–3)

Three tasks:
1. Produce a standalone binary per lifted segment (resolves dependencies from entrypoint).
2. Create a runtime monitor per lift tracking the metrics cited in its annotation.
3. Replace every call site with a lift point (AST node substitution — p.4 §3.2).

Serialization: JSON wire format generated automatically; compiler refuses lifts whose arguments
contain heap pointers or stateful package-level variables (p.3 §3.1, p.4 §3.2).

### Runtime (§2.3, p.2–3)

- Builds a **state transition model**: each state = a possible configuration of lift assignments.
- **Transition function** derived from composing delegate expressions across all lifts.
- Open problem (acknowledged p.3): *"composing the program's delegate expressions into a global
  transition function is challenging"* — this is the multi-agent oscillation problem.
  See also `docs/research/claude_comprehensive_research.md` lines 111–123.

### Evaluation (§4, p.4–5)

- Benchmark: DeathStarBench Social Network (Go port). 8-node Kubernetes cluster, 40-core servers.
  Reed98 social graph dataset. See `inspiration/papers/deathstarbench-asplos19.pdf`.
- 5 configurations: baseline (no distribution), full (4 services distributed), post-only,
  user-only, SG-only, TL-only (p.5 Table 2 / Figure 3).
- Key result: neither no-distribution nor full-distribution is optimal; partial lifts achieve
  lower latency at high load *and* monolith-level latency at low load (p.5 §4.1).

### Design-space position

From `docs/research/claude_comprehensive_research.md` line 11:
> *"Monolift's genuine novelty is… the conjunction of four properties: compile-time insertion into
> unmodified Go, a monotonic fall-back semantics where an un-lifted build still runs, a per-lift
> runtime-directed policy language, and Kubernetes-as-backend with no bespoke runtime."*

## Service Weaver — Primary Comparison

**Source:** `inspiration/papers/service-weaver-hotos23.pdf`
**Repo:** `inspiration/repos/weaver`

Ghemawat, Grandl et al., HotOS 2023. Google's Go framework for writing distributed apps as a
single modular binary.

### Key mechanism

- Components declared via `weaver.Implements[T]` struct embedding (p.112 Figure 2).
- Runtime decides co-location vs. RPC at deployment time from a TOML config — **not at runtime**.
- A code generator produces local stubs and RPC clients from the component graph.
- "Proclet" = application process linked with the Monolift runtime (p.113 §4.1 Runtime overview).

### Five challenges motivating Service Weaver (p.110 §1)

C1 performance, C2 correctness (cross-version failures), C3 manageability,
C4 API freeze, C5 slow development. Service Weaver's three tenets:
1. Write monolithic. 2. Runtime assigns components to processes. 3. Deploy atomically (p.110).

### Atomic rollouts (p.113 §4.4)

All component communication stays within one version; gradual traffic migration across versions.
Directly addresses C2 (cross-version interaction failures caused 2/3 of outages in a 100-system study).

### Differences from Monolift

| Dimension | Service Weaver | Monolift |
|-----------|---------------|---------|
| Adoption cost | Must adopt `weaver.Implements[T]` model | Comment annotations on existing Go |
| Placement | Static TOML config at deploy time | Runtime-directed via delegate expressions |
| Granularity | Component (interface) | Lift (call site) |
| Fallback | N/A | Unannotated binary runs as-is |

`docs/research/claude_comprehensive_research.md` lines 35–37 give the authoritative comparison.
Google abandoned direct adoption after one year citing rewrite burden (monolift-plos25.pdf p.2):
*"it was hard for users to adopt Service Weaver directly since it required rewriting large parts
of existing applications."*

## Ignis — Must-Cite Prior Art

**Source:** `inspiration/papers/ignis-pldi19.pdf`

Vasilakis, Karel et al., PLDI 2019. "Scaling Distribution-Oblivious Systems with Light-Touch Distribution."

### Key mechanism

Two components (p.1011 §2.2 / p.1012 §3.1):
1. **Transformations** — automated, operate at module boundaries; profile, spawn replicas, forward RPCs.
2. **Recipes** — *"lightweight annotations that guide the intended semantics of the resulting distribution"*
   (p.1012 §3.1). Expressed as a DSL embedded in the source language (JS/Lua `require` call).

Ignis interposes on `require()` at runtime (p.1011): *"introduced as a backward-compatible,
drop-in replacement of the language's module system."*

### Overlap with Monolift

| Ignis concept | Monolift analog |
|---------------|----------------|
| Distribution-oblivious | Unannotated binary still runs |
| Light-touch | Comment annotations |
| Recipes | Delegate expressions |
| Module boundary | Lift boundary |

### Decisive differences (`docs/research/claude_comprehensive_research.md` lines 53–55)

1. Ignis operates **at runtime** via `require` interposition in dynamic languages;
   Monolift operates **at compile time** on a statically-typed language → stronger sendability guarantees.
2. Ignis recipes are per-module policies for scaling/replication (uni-directional scale-out);
   delegate expressions make **bi-directional** local↔remote decisions on live signals.
3. Ignis targets distribution as a **bottleneck response**; Monolift frames it as an architectural
   choice with dual-dispatch semantics.
